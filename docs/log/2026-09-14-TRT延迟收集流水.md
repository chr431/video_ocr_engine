## 1. 设计与实现（TRT_DEFER_SYNC，默认关）

- **协议**：`_gpu_raw_submit`（prep+TRT+argmax+D2H 全链提交，pinned 双
  环槽 + 事件记录，不等待）→ 下一批提交后 `_gpu_raw_collect` 只同步
  **上一批**事件（当前批在飞）——CPU 提交链与 GPU 执行跨批重叠；
  结果滞后一批交付，`_defer_fifo`（提交序）保证乱序回退/穿插宿主批时
  交付顺序恒定；哨兵批收尾 collect 交付最后一批。
- **正确性基建**：单流次序天然串行化设备缓冲复用（TRT_N 写 dev_out →
  argmax_N 读 → TRT_{N+1} 写）；Y 帧 owner（`_DevBatch` GC 归还池契约，
  gpu/device.py:123）随批 `keep` 保活到 collect；`_prepare_shape` 幂等
  （同形批不碰 context 形状），异形/多子批/缓冲增长自动回退同步路径；
  引擎池 checkin 前 `drain_deferred` 护栏；`release` 释放 pinned 环+事件。
- 改动面：`video_ocr_engine/ocr/trt.py`（延迟环组）、
  `video_ocr_engine/ocr/native.py`（提交/收集协议）、
  `video_ocr_engine/pipeline/ocr_stage.py`（infer_worker 分支）、config 三件套（旋钮
  注册；顺带清掉 CUDA Graph 遗留的两行死 RunConfig 字段）。

## 3. 归因修正（本轮真正的结论）

深度 2 生效后（探针确认热轮 0 次同步回退、全部走 submit/collect），
每批墙钟**没有下降**：`collect` 的事件等待仍要等上一批 GPU 链走完——
即**残差不在 CPU 提交侧，而在 GPU 链自身时长**（prep+TRT+argmax 在与
解码/分段 kernel 并发争用下 ~12ms/批，是裸测 5.6ms 的两倍+）。立项轮
的「launch 裸奔」把**无争用微基准差**误读为可回收的提交空闲；实际与
CUDA Graph 轮 e2e 无收益互洽（图化折叠 launch 也救不回 GPU 链时长）。
⇒ **OCR 侧再提速只剩两条真路**：减 GPU 工作量（fp16 已做，−3%）或减
争用（解码/分段下 GPU）；多流并发预计同判（GPU 链已饱和在争用上）。
