## 1. P0：§8 证据固化（先量后做）

`_probe_cycle_quant.py`（bench/cycle_quant.json）：
- `process_time()` 20 万次重采**只有一种非零增量 0.015625s**（1/64s）——
  §8.4 的量化断言从"278 万次采样"复检为确定性事实。
- `QueryProcessCycleTime` 语义：sleep 0.5s 增量仅 0.1ms 等价（=CPU 时间）；
  线程隔离实验（主线程 sleep、worker 忙）证明进程计数=各线程之和。
- cycles/wall CV **0.014%**（corr 0.9988，比 §8.1 的 0.701% 更静的窗口）；
  **自校准频率换算**（全程 Δcycles/Δprocess_time）双窗口一致到 0.017%
  （2.493 vs 2.493 GHz）——resources.py 换算法的合法性证明。
- 附注：four_threads 实验撞 GIL（纯 Python 线程串行），恰与 §6 的
  gil_check 结论同向；"求和语义"以 thread_isolation 项为准。

`_probe_clock_gate.py`（bench/clock_gate.json）：
- 冷轮（round 0）sm_min 450MHz、wall 3.74s；热轮（1..7）sm_min 恒 2700、
  wall 3.0955~3.1060s。CV 含全部 6.647% → 弃前 2 轮 0.120%（**×55.6**，
  复测 §8.2 的 54×）。
- **门禁比率校准（关键发现）**：`nvmlDeviceGetMaxClockInfo` 给的 3105MHz
  是 boost 上限，负载热平台只有 2700（=0.870×max）。k=0.85 仅剩 2.3%
  余量、k=0.9 会把热轮全拒；冷轮 450/3105=0.145。分离带 [0.145, 0.870]
  宽阔，**取 k=0.75**（两侧 >10pp 余量）落进 bench.py。
- throttle 位全程为 0——主动压频位在本负载从未触发，门禁的主动信号是
  sm_min；throttle 位作为次级判据保留。

## 2. P1：bench 协议与判据降噪（tools/bench.py）

1. **每轮 GPU 时钟入账**：`cmd_run` 每轮包 `NvmlSampler`，registry 记录
   新增 `gpu: {sm_min, sm_p50, sm_max, throttle_bad, valid, gate}`。
   `_gpu_state()` 从 nvidia-smi 子进程（43ms/次）改 NVML 直读。
   纯 CPU 配置（decode∈{cpu}∧ocr=cpu）不判 GPU 时钟（空闲时钟恒低，
   判了只会全 invalid 再回退），gate 记 `off:纯CPU配置不判GPU时钟`。
   历史记录无 gpu 字段一律视为 valid（**不追溯改判**）。
2. **时钟门禁**：valid = 无主动压频 tick ∧ sm_min ≥ 0.75×最大SM 时钟；
   采样点不足判 valid（fail-open：门禁不能无证据剔除）；热轮聚合只收
   valid 轮，全剔则回退全收并警告（门禁不能替无数据）。
   `--no-clock-gate` 逃生门。记账修正：引擎冷启动的第 1 轮是既有排除
   口径，不计入"门禁剔除"数。
3. **ab 加固**：臂序逐对轮转（AB/BA 交替，对消轮内位置效应——先跑臂
   系统性慢 ~1.3% 的结论从 telemetry-check 推广到 ab）；自动判定 =
   逐对热轮中位配对差分 → 均值+SE+符号多数（≥0.70）vs `--hard` 阈值，
   B 显著慢 → 退出码 1；`--no-verdict` 逃生门；`ab --aa` 两臂同配置 →
   子进程协议噪声带标定。逐 span 归因表只展示不判（C-42：占比差分
   ≠可回收量）。
4. `--priority above_normal`（opt-in 默认关）：子进程自提优先级
   （`SetPriorityClass`，伪句柄 -1 直传绕开 restype 截断陷阱）。
5. `PI15_FLOOR_PCT` 抽成常量（原 0.30 硬编码在 `_limit_from_band`）。

冒烟验证：冷轮被标记剔除（sm_min 690 < 2329 = 0.75×3105）、热轮保留；
ab --aa 轮转/聚合/标定链路全通。

## 3. P2：引擎遥测提分辨率（只加键，report v3→v4）

1. **cycle 计数**（resources.py）：`_HostCounters` 加
   `QueryProcessCycleTime`；`per_phase()` 新增 `cores_avg_cycles =
   (Δcycles/Δwall) ÷ f_run`，`f_run = 全程 Δcycles/Δprocess_time`
   自校准（P0 证明双窗口一致 0.017%）。旧 `cores_avg` 保留（长相位仍准）。
   **实测对照**（p2-verify 轮）：GPU calibrate 相位旧口径 0.0（±100%
   量化伪影）→ 新口径 0.31；host decode 相位 16.42 vs 16.38（长相位
   两口径一致，互为校验）。
2. **TOTALS 全键 n/max**（metrics.py）：`PROFILE_TOTALS_N/_MAX` 从 2 个
   队列键扩到全部 7 键（consume_feed/emit.*/merge_pair +10 注册名），
   "偶发长停顿 vs 持续细碎"分诊口径推广。注册表 48→50 项（≤64）。
3. **span 卫生**：`gpu_calib_total` 的 t0 从 `_t_open` 改到 open 收口处
   （消除 pipeline.calibrate 与 pipeline.setup 的双计）；死指标出清 8 个
   （pipeline.producer、emit.h2d_bytes、emit.launches、pools.high_water、
   frame_batch.inflight/leaks、segment.emit/emit_batch——grep 全仓零产出，
   删除后报告外观不变）；审查后**不改**：注入引擎路径的 PI-10 短路
   （reuse=0 → 不判）是正确语义，伪造 engine_init=0 反而失真。
4. **覆盖缺口**：`device.py` CPU 解码分支补 decode_batch/gray_batch/
   stream_analyze（键语义与宿主对齐）；宿主补 consume_feed（每帧）/
   merge_pair / 'open' L1 边界；GPU `_put_q` 补 q_put_block（生产者背压
   此前无对应物）。实测新增覆盖立即兑现：GPU q_put_block 3001 次
   共 0.004s（生产者从不阻塞的直接证据）。
5. **report v4**：`span_relations`（静态父子表+路径标记）+ 派生 span
   `<parent>_other`（= parent.sum − Σ在场子项 sum，子项互不重叠硬约束：
   宿主 consumer 只减 decode.* 与 consume_feed，merge_pair/q_put 嵌套
   在 consume_feed 内不单列）。**产品化上午 §6 的手工算术**：上午
   "consumer 缺口 0.70s 只解释 3%"，本轮 consume_feed 入账后
   `pipeline.consumer_other` 仅剩 0.088s——缺口归因闭合。
6. **测试**：test_report 快照 v4 + 关系派生用例；test_metrics 死键清单
   同步 + N/MAX 成对断言；test_telemetry_cost 重放口径更新
   （+2200 TOTALS 逐事件计数，键 10→14/8→10），**≤2ms/run 上限不变**。

正确性门禁：两路径段数 1090/1090（与上午基线一致），成本守卫 36/36 过。

## 4. P4：trace/timeline 实验（用户裁决；宽成本、默认关、关=零成本）

- 旋钮 `diag.trace_file`（env `VOE_TRACE_FILE`，默认空=关，铁律 10）；
  `video_ocr_engine/domain/trace.py`：线程局部桶 `(name, t0, t1, tid)`，事件源 = `_prof_end`
  脊柱（**不改签名**，t1 复用已算好的 t0+elapsed）+ 编排三段近似锚点 +
  顶层 pipeline.run 真实锚点；开启时自带 NVML 0.2s 点列（同 perf_counter
  时间轴）。嵌套父子离线按同线程区间包含重建。
- **关闭零成本（结构性）**：`_prof_end` 尾部一次 `is not None` 判断；
  std 档 ≤2ms/run 守卫在 trace 代码在场但关闭时原样通过 = 守护。
  开启成本单测宽上限 50ms/2300 事件（实测 ~1ms 级；用户裁决放宽）。
- 视图探针 `_probe_trace_view.py`：文本甘特（60 桶密度）+ 线程重叠矩阵 +
  空洞清单 + NVML 时钟排 + on/off 成本对照。
- **验收（两路径，段数 1090/1090 一致）**：
  - host（cpu+openvino）：7363 事件/382KB；**会话线程忙 94.2% 其中
    q_get_wait 1.510s**、双推理线程各 ~65% 忙且互相重叠 45.4%（OpenVINO
    双实例并行结构直接可视）——聚合报告给不出的并发图。
  - GPU（nvdec+trt）：9494 事件/481KB；**decode.batch 2.938s 占满生产者
    线程（95.5%）**、会话线程 q_get_wait 3.019s（97.7%）、推理线程仅
    14.1% 忙、sm_clock 全程 2700 无压频——上午 §4 的全部结论在时间线上
    直接复现。
  - 成本：host on/off +1.14%、GPU +0.39%（**未交错**的同序两轮，落在
    噪声带内，不能当结论；µs 级单测 ~1ms/2300 事件）。NVML 采样线程
    +每事件一次 append 的墙钟影响在分辨力之下。
- **裁决：保留为 opt-in 实验工具（默认关）**。理由：诊断价值已被两路径
  验收证明，但常开成本含 NVML 线程与落盘（~0.5MB/run），且日常 A/B 的
  判据用不到时间线；按需开启（`VOE_TRACE_FILE=...`）零仪式感。
  转正（默认开）需要一次交错 A/B 级的成本证据，留复评。

## 5. P3：重标定与验收实验

### 5.1 PI-15 重标（新增遥测后的合规动作）

`telemetry-check --aa`（h264-gpu，n=25/inner=3，同进程交替）：均值 −0.038%
（旧 +0.072%）/ |Δ|p50 0.089% / |Δ|p95 0.734% / sd 0.286% / SE 0.057%。
|均值|+3×SE = 0.209% < 0.30% 地板 → **阈值维持 std +0.30% / full +1.20%**：
新增遥测面（TOTALS n/max、覆盖缺口、trace 关闭态判断）没有把噪声带推过地板。

### 5.2 ab 子进程协议 A/A（新协议：臂序轮转 + 时钟门禁 + 冷热分离）

- GPU（h264-gpu+trt，8 对）：均值 −0.241%、sd 0.254%、|Δ|p95 0.517% →
  建议 `--hard 0.55%`。对照旧口径：子进程 A/A |Δ|p95 2.33%（2026-09-11）、
  `_probe_dll_ab` 冷启 sd 4.6%——热轮口径下带收窄约一个量级。
- CPU（h264-cpu+openvino，8 对）：均值 −0.131%、sd 1.220%、p95 1.291% →
  建议 `--hard 1.45%`（纯 CPU 路径宿主调度敏感，共享桌面噪声面更大）。

### 5.3 验收实验：DECODE_THREADS=10 vs 32（上午 §7 遗留问题的裁决）

协议：`bench ab --config h264-cpu --ocr-backend cpu --repeat 8
--env-a DECODE_THREADS=10 --env-b DECODE_THREADS=32 --hard 1.45`
（臂有效性证据 = 两臂 decode.batch 结构差 5.6×，非静默回落）。

- **热池判定：不可判定**（均值 +0.97%、SE 2.23%、阈值 1.45%、符号 4/4
  无多数）→ 档位 10→32 无墙钟收益。
- **冷启动：t32 一致慢 +4.03%（8/8 符号）**——32 解码线程在引擎构建期
  有一致性损害。
- **机制**（span 归因；C-42：归因≠可回收）：t32 的 `decode.batch` 阻塞
  −82%（1.380→0.245s）、`q_get_wait` −96%（1.292→0.046s），但
  `consume_feed` +120%、`preprocess` +79%、`infer` +35%、`merge_pair`
  +65%——**瓶颈从解码移到 GIL 争用**（与上午 gil_check 判定同向：
  numpy/OpenVINO 内核被同进程解码线程串行化），净收益被完全吃掉。
- 上午 §7 不自洽的解：引擎内 `decode.batch`（1.356s）低于 10T 独立扫描
  （1.539s）= decord 内部预取线程使 get_batch **阻塞时间** < 独立扫描
  **总时间**——两口径本就不可直接比。
- 结论进 C-50：**维持 10 档**；档位依据从"ONNX 时代实测"更新为本轮
  交错 A/B（方向未变：升档无益且冷启有害）。

## 7. 续轮（同日第二段）：仪器闭合 + trace 转正裁决

> 问题（用户）："若要继续改进遥测，还有哪些可以做的？"→ 选做仪器闭合
> （W1 直方图 / W2 子相位 / W3 相位时钟）+ trace 转正评估（W4）。

### 7.1 W1：TOTALS 分布形状（report v5）

- **分箱设计**：按 2 的指数分箱（桶号 = `math.frexp(x)[1] + 20`，32 桶
  覆盖 ~0.95µs~2048s）。**为什么不用 16 个边界做循环扫描**：原型实测
  逐边界扫描 0.5µs/事件、乘数法 0.17µs/事件、frexp 0.165µs/事件——
  无界键的事件量是 6270/run，边界扫描会多吃 ~2ms。
- **档位约束（关键决策）**：直方图**只在 full 档插桩**。6270 事件 ×
  0.165µs ≈ 1.0ms，而 std 档的整条遥测路径预算是 2ms/run（当前实测
  0.691ms，余量 65%）——把直方图放进 std 会吃掉一半余量，为"形状信息"
  付这个价不值（std 档已有 n/max 两端）。full 档墙钟预算本来就是 ±1.2%
  量级，付得起。守卫 `test_full_tier_histogram_cost_is_bounded`（宽松
  上限 8ms = 实测 ~8 倍，只抓病理回退）+ 桶和 = 事件数（不丢事件）。
- report v5：`histograms`（仅 full 档出现，缺席≠空值）+ `histograms_meta`
  （分箱自述：n_buckets / exp_bias / 各桶下界秒值），读者可自证算术。
- **首次读数即产出新证据**（host full 档）：
  - `pipeline.q_get_wait_hist` 双峰清晰：244µs 档 129 次（正常等待）
    vs 7.8ms 档 68 次 + 15.6ms 档 60 次——**后者是 `process_time` 的
    15.625ms tick 整数倍**，即"等待期间宿主被调度器换出"的量化指纹
    （§8.4 的 tick 现象在事件分布上直接可见，v4 的 n/max 只看得到
    `max 41.6ms` 这个孤值，看不出"60 次都是同一个 tick 值"）。
  - `segment.merge_pair_hist`：503 次在 122µs 档、105 次在 488µs、
    53 次在 977µs——相似判定**本身**是双峰（内容变/不变的两种路径），
    v4 的 `max 3.2ms` 完全看不到这个结构。
  - GPU `emit.put_hist`：793/1090 集中在 15µs 档、尾部 8 次 >977µs。

### 7.2 W2：子相位闭合（`_other` 从"缺口"变"残差"）

- `ocr.infer` 内部此前只有 `ctc_decode` 一个子键，host 路径
  `ocr.infer_other` 高达 **2.83s**（占该 span 的 92%）——"缺口"其实混合
  了 TRT 提交/规约/拼接三件事。新增三键（**full 档专属**，per-子批 ×
  数十批属热路径）：`ocr.trt_enq`（execute_async_v3 提交）/
  `ocr.trt_reduce`（argmax 规约 + D2H，含流同步=等 GPU）/`ocr.trt_concat`
  （多子批拼接，纯宿主）。
- **效果**（GPU full 档）：`ocr.infer_other` **0.456 → 0.073s**（归因
  84%），子相位自身给出结构：`trt_enq 0.2502s` / `trt_reduce 0.1236s` /
  `trt_concat 0.0000s`——**提交（宿主侧）是等待（设备侧）的 2 倍**，
  与 C-47"残差=GPU 链争用主导"方向一致但更细：宿主被调度饥饿的时间
  超过等 GPU 的时间。
- relations 表扩展：host `consume_feed ⊃ merge_pair + q_put_block`
  （此前这两键挂在 consumer 下但实际嵌套在 consume_feed 内，v4 未声明）。
  **宿主实测闭合**：`consume_feed 0.5075 − merge_pair 0.2647 −
  q_put_block 0.0232 = consume_feed_other 0.2197`（状态机裸成本）——
  与派生值逐位一致，关系表算术自证。
- 边界（写进代码注释）：`submit_argmax_deferred` 的深度 2 路径**未打桩**
  （默认关；开时 `infer_other` 会重新变大，读者知悉）。

### 7.3 W3：相位边界带时钟（`sm_mhz_at_start/end`）

`_HostCounters.sample()` 在 NVML 会话**已存在**时读一次
`nvmlDeviceGetClockInfo(SM)`——GPU 路径必然已初始化（环境指纹/采样器），
**宿主纯 CPU 路径零成本不触发初始化**（`_NVML["state"]` 缓存态判据，
与 `_vram_bytes` 同款纪律）。`per_phase` 输出相位首尾两个读数：
"这一相位跑在什么时钟上"随报告自证，不必再事后跑 NVML 探针。
GPU 验证轮读数：decode 相位 2700/2700（热平台，与 P0b 标定一致）。
sources 里自述来源与"不主动初始化"的边界。

### 7.4 附带修复：`bench run --telemetry` 从未生效

W1 排查"full 档为什么没有 histograms"时暴露：`_round(..., telemetry, ...)`
**收下参数却从未使用**——引擎档位实际由 `VOE_TELEMETRY` 环境变量决定，
所以历史 `bench run --telemetry full` 全部静默按 std 跑（此前无功能依赖
它，故未被发现；报告 `tier` 字段一直是诚实的，只是与命令行不符）。
修法：`_round` 内 `os.environ["VOE_TELEMETRY"] = telemetry` + try/finally
复原（与 telemetry-check 的同进程口径一致）。**影响面**：历史 registry
里标 `"telemetry": "full"` 的记录其 `report.tier` 是 std——按 tier 字段
读报告的历史分析不受影响（tier 一直如实记录），按命令行参数读的需知悉。

### 7.5 W4：trace 转正裁决（交错 A/B 口径）

协议升级：前一轮只有"未交错同序两轮"（+0.39%/+1.14%），证据等级不足。
本轮按 `bench ab` 交错口径（臂序轮转 + 时钟门禁 + 热池分离）：

| 路径 | 对 | 热池 Δ% | 逐对符号 | 判定 |
|---|---:|---:|---|---|
| host（cpu+ov） | 8 | +1.36% | `+--++-++` | 不可判定（SE 1.16%，限 1.45%） |
| host（重跑） | 8 | +2.22% | `-+++++++` | 不可判定（符号 5/3） |
| **GPU（nvdec+trt）** | 8 | **+0.31%** | `++++++++` | 不可判定（均值 0.453% < 限 0.55%） |

- GPU 那份是三份里最干净的：**符号 8/8 一致指向 trace 略慢**，但幅度
  低于本机 GPU 协议的可分辨下限（0.55%）——即"有方向、无显著性"。
- host 两份符号都乱（`+--++-++`/`-+++++++`），说明其 +1.4~2.2% 的差值
  被共享桌面的宿主调度漂移主导，不能归给 trace。
- 口径提示：本轮 host 协议 A/A（6 对）实测 sd 2.63%，明显宽于上一轮
  8 对的 1.22%——**共享桌面的噪声面本身在漂移**，跨轮引用阈值需谨慎
  （这正是 C-51 把"换窗口/换机器重标"写进复评触发的原因）。
- **裁决：维持 opt-in（不转正默认开）**。理由：GPU 路径的方向性证据
  （8/8 符号、+0.3% 量级）已足够说明"在有预算敏感的 A/B 里不该默认开"，
  但也不构成"必须禁用"——诊断场合按需开启即可。转正若要做，需要
  锁频环境或 n≥30 才能给出显著结论。
