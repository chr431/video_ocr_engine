# 2026-09-19 decord 崩溃类彻底修复：工作线程异常零逃逸（decord 7ce38fa）

> 任务（用户）：decord 本轮崩溃需要警惕，分析根因，彻底修复并跑回归测试。
> 背景教训：窗口缺陷轮（486aeda）修掉了挂死/少交付，但**最初的 abort()
> 崩溃只是「不再复现」，根因从未钉死**——修复后不复现 ≠ 根因消除。

## 1. 根因链（本轮钉死）

**实证起点**：dmlc LOG(FATAL) 的分支选择——本构建 `DMLC_LOG_FATAL_THROW`
走 **throw 分支**（实证：send-after-flush 的 `Check failed: send_ret>=0`
曾以 DECORDError 形式传到 Python；若走 abort 分支会先打 stderr，而崩溃
现场 stderr 全空）。throw 分支把消息装进异常体。

**崩溃链条**：dmlc CHECK / 任何异常在**无 catch 包裹的线程**里抛出 →
`std::terminate` → `abort()`——MSVC 的 terminate 处理器不打印任何内容，
消息（在异常体里）随之丢失 → 静默死亡。Debug CRT 下表现为
「abort() has been called」弹窗（用户两次截图），Release 下静默退出。

**未包裹线程清点**（src/video 全站点）：`GpuWorkerLoop`、`UploaderLoop`
（hybrid；后者原始轮完全裸跑）——对比 CU `LaunchThread` 与 FFMPEG
`WorkerThread/FilterWorkerThread` 均有 try/catch。工作线程内的现实
throw 源：CU `Push` 的 `CHECK(run_.load())`（GPU 臂停止后续喂即炸）、
NDArray 分配的 bad_alloc 等。

**与窗口缺陷的关系**：486aeda 修的四个缺陷（排空早发/flush 后喂包/
未派 chunk 自旋/窗缘 kick 误丢）是**当时踩中 CHECK 的状态错乱源头**
——修复后崩溃不再复现。但崩溃类（异常逃逸=进程静默死）本身未关：
任何未来缺陷仍会以同样方式吞掉全部诊断信息。

## 2. 修复（decord 7ce38fa，异常零逃逸）

1. `GpuWorkerLoop` / `UploaderLoop` 全循环体 try/catch：`HybridTrap`
   记录原消息到 `g_hybrid_err_{msg,seen}`（顶部匿名命名空间）+ 打
   stderr 一份 + 唤醒消费者 + 退出线程（不再 rethrow=不再 terminate）。
2. `Pop` 入口检查错误槽 → `dmlc::Error("hybrid worker failed: " + 原消息)`
   → pybind → **DECORDError**——进程级静默死变成可诊断的干净失败，
   原始异常消息保留直达调用方。
3. `Start()` 安装 `std::set_terminate`（`std::once`）：打印
   `current_exception` 的 `what()` 到 stderr 再 abort——任何其他通道
   的逃逸异常至少留下诊断。
