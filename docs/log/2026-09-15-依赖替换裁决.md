# 2026-09-15 依赖替换裁决：换依赖已无剩余性能空间（瓶颈绑定取证）

> 命题（用户）：OpenVINO 替换 ONNXRuntime 是最近一次明显提升，**能否通过
> 更换其它依赖进一步优化性能**？
> 结论：**不能**——当前最高优先级瓶颈已分别绑定，且解码实现已超外部参考
> 实现。零产品性能变更；**顺带修掉一个真实打包缺陷**（见 §5）。

## 0. 方法论（为什么不能靠"占比"下结论）

见 C-42 判例：某环节占墙钟 21% 时短路它墙钟**无变化**（消费者空等吸收）。
所以本轮判定一律用**绑定实验**（把一侧换成零成本，看墙钟动不动），
不用 span 占比推算。三个新入口：

| 探针 | 作用 |
|---|---|
| `_probe_binding.py` | 把 OCR 推理 / 预处理分别换零成本 → Δwall |
| `_probe_decode_ceiling.py` | 外部参考实现（ffmpeg cuvid/软解）+ ROI-first 价值 + 批扫描 |
| `_probe_preproc_ab.py` | 替换候选的引擎级交错 A/B（独立子进程 + 段数/文本门禁） |

## 1. 绑定约束：GPU 全解码绑定 / CPU 生产者绑定

`_probe_binding.py`（每臂 3 轮取中位，热池，段数门禁全过）：

| 配置 | base wall | 零成本 OCR (Δwall) | 零成本预处理 (Δwall) | 判定 |
|---|---:|---:|---:|---|
| h264-gpu（nvdec+TRT） | 3.0904 | **+0.21%** | −0.05% | 全解码绑定 |
| hevc-gpu（nvdec+TRT） | 1.5022 | **+0.11%** | +0.45% | 全解码绑定 |
| h264-cpu（cpu+OV） | 2.2708 | **−18.35%** | −1.21% | 生产者绑定 |

即：**GPU 路径把整个 OCR 推理换成零成本，墙钟不动**（+0.1~0.2% 是噪声）——
OCR 侧任何依赖替换（换推理库、换量化、换模型档位）都不可能兑现墙钟。
h264-cpu 把 OCR 全换零成本也只 −18.35%，而**预处理换零成本仅 −1.21%**。

## 2. 解码侧：decord fork 已超外部参考，换封装没有上界

既然 GPU 路径是解码绑定，"换依赖"只可能在解码侧成立。三路取证
（`_probe_decode_ceiling.py`，test5 / 3000 帧 / ROI 105×32）：

| 口径 | 结果 |
|---|---|
| decord fork（NVDEC + ROI + gray） | **989 fps** |
| ffmpeg 自带 `h264_cuvid`（外部参考） | 901 fps |
| ffmpeg 软解（同窗口） | 2369 fps |
| ROI 解码 vs 全帧解码 | 2164 vs 1237 fps = **ROI-first 值 1.75×** |
| 批 64 vs 128 | 2152 vs 2142 fps（**无固定开销瓶颈**） |

**decord 已快过 ffmpeg 自己的 cuvid 通路**——任何"更标准"的 NVDEC 封装
（PyNvVideoCodec / PyAV / OpenCV cudacodec）的上界就是参考实现水平，
而它们全部**没有 ROI-first**，换过去先亏 1.75×。

## 3. PyNvVideoCodec（NVIDIA 第一方）实测：近 2× 慢

它是唯一有资格挑战的候选（NVIDIA 官方维护的 NVDEC 绑定，2026-08 的
§4 P2-3 表里还没有它）。给它**最有利口径**——独立进程、独占、无干扰：

| 口径 | 结果 |
|---|---|
| PyNv 批量取帧（独立进程） | **493 fps** |
| decord fork（同窗口，含 ROI+gray） | **989 fps** |

⚠️ 两个必须留档的发现：

1. **decord 与 PyNv 同进程 DLL 冲突**：先 `import decord` → PyNv
   `ImportError: DLL load failed while importing _PyNvVideoCodec:
   找不到指定的程序`（先 PyNv 后 decord 亦然）。**集成即不可能**，
   除非改成分进程——而分进程要重做零拷贝帧交付。
2. **它的三个 API 坑**（已刻进探针注释，避免下次重踩）：
   模块级 `nvc.CreateSimpleDecoder` 被同名 pybind 类**遮蔽**（直接调用报
   "incompatible function arguments"，必须用包装类 `nvc.SimpleDecoder`）；
   取帧方法名是 `get_batch_frames_by_index` 而非 `DecodeNextPacket`；
   CUDA 13 起 cudart 在 `bin\x64\` 且 PyNv 仅在 `CUDA_PATH` 存在时才
   `os.add_dll_directory`（本机默认为空 → 必须显式设置）。

（评估后已 `pip uninstall pynvvideocodec`，环境复原。）

## 4. 预处理替换：模型级快 19×，墙钟 −0.26%（C-42 复现）

当前实现的 `_np_resize` 是纯 numpy 逐轴 take（当年为砍 EXE 体积移除了 cv2）。
按**生产真实形状**（`--shapes` 采集：33×106→154×48 一类小图，
1090 次/3000 帧）做 µbench：

| 实现 | 加权 µs/段 | vs 基线 | 逐位一致 |
|---|---:|---:|---|
| numpy-take（当前实现） | 105.3 | — | 是 |
| **cv2.resize（INTER_LINEAR）** | **5.5** | **−94.7%** | 否（max\|Δ\| 4.6e-05） |
| numpy-separable（反例） | 62.5 | −40.7% | 否（改分组顺序） |

模型级快 **19×**。落地到引擎（`_probe_preproc_ab.py` 交错 A/B，
独立子进程，热池，段数/文本 sha 全过）：

| 指标 | A（基线） | B（cv2） | Δ |
|---|---:|---:|---:|
| `ocr.preproc_resize` | 0.4707 | 0.1906 | **−59.5%** |
| **墙钟** | 2.2491 | 2.2434 | **−0.26%**（符号 `--+`） |

resize 真省了 0.28s，但**墙钟只动 0.006s**，且逐对符号不一致（`--+`）——
低于本机可分辨下限（A/A |Δ|p95 0.484%）。**不采纳**：为一个不可分辨的
收益引入一个非逐位一致的依赖（且要重新过金标），不值。

> 这是 C-42 判例的第二次复现：**占比 ≠ 可回收**。

## 5. 顺带修掉：pyproject 依赖与实际引擎不一致（真实缺陷）

排查中发现 `pyproject.toml` 仍写着 `onnxruntime>=1.28`（C-48 已于
2026-09-14 移除 ORT，产品代码里**再无任何 onnxruntime import**），
而**唯一 CPU OCR 后端 openvino 根本没声明** → 新环境 `pip install` 后
CPU OCR 直接报错让用户自己装。已修正为：

```toml
dependencies = [
    "numpy>=2",
    "openvino>=2026.3",  # CPU OCR 唯一后端（onnxruntime 已于 2026-09-14 移除，C-48）
    "psutil>=6",
]
```

## 6. 旁路证据（本轮顺带量到，未单独立项）

- **CPU 路径 producer 缺口 0.60s（占 producer 29%）的构成**：
  `_probe_producer_profile.py` cProfile 定位 = `_segments_similar` 0.329s
  \+ `_cluster_win3` 0.211s + `_np_resize` 0.179s（全为 numpy 热内核）。
  ⚠️ `_probe_producer_gap.py` 的 `nocluster` 短路臂**不可用于归因**——
  改判据导致每帧断段、段数 1090→3000、工作量反 +93%。
- **numpy 升级（2.4.6→2.5.3）无收益**：热内核逐项对照，resize 反慢 7%，
  两版逐位指纹相同 → numpy 不是杠杆。
- **AMD Radeon 610M iGPU 是 phantom（`CM_PROB_PHANTOM`/Code 45）**：
  BIOS 里关闭 → 本机**不存在第三个硬解单元**，"加一路 iGPU 硬解"
  这条路在硬件层面就不成立（VCN 不可用）。

## 7. 复评触发

换卡（NVDEC 与 CPU 相对速率变）/ 出现带 ROI-first 的解码绑定 /
预处理升为关键路径（超宽 ROI 使 resize 占比再翻倍）/ 换 CPU 架构。
