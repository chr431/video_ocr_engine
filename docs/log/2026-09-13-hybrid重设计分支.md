## 1. 层0/1：包缓存 + 供料期 GOP 派工（fork 8698cfa/17f2beb）

### 结构

- `Push` 只做：GOP 记账（key 开/关）+ 迟到包归属（已供 GOP 直供其侧、
  未供挂 stragglers）+ 入缓存。路由决策全部移到供料泵。
- `PumpFeed`（仍在 demux 线程，每包驱动）：cursor 起**同侧保序的前瞻
  供料**；分配按供水式贪心（`assigned_frames_` 水位 vs 当下 rc/rg）；
  饥饿门=两侧银行（queue/ready 帽）；EOF 无视门排空 + 臂 flush。
- kick 延迟化：换侧时离场侧当前 GOP 未供完 → 克隆包挂 `pending_kicks_`，
  游标越过该 GOP 再发（保持流序相邻性）。
- `NeedsPackets` = 缓存字节数 < 预算 OR 某侧饥饿（逃生门防"缓存满+
  两侧等料"与 demux 停读互锁）。
- 删除：BuildPlan/plan_side_/滑动视界/盲阶段窗口/REPLAN 旋钮/
  ChooseSide 整个函数。kick_guard_ 默认 0（债务克隆在新架构=洪泛源）。

### 调试史（全部实测踩出，供复评）

1. `fed_upto` 初始化为 0 而非绝对序列 → 缓存下标为负崩溃；
2. 游标越过"暂供完但未关闭"的开放 GOP → 剩余包无人供；
3. `assigned_frames_` 累计缺失（分配时 chunk expected=0）→ 水位恒 0
   → 贪心恒选 CPU（95 CPU/5 GPU）；
4. kick 只在 arm 分支更新 last_fed_side_ → 零 kick；
5. 债务克隆洪泛（分配领先交付 ⇒ 债务快照=巨额 pending）→ 离场侧解出
   整段错侧 GOP → 陈旧帧活锁（PopSide 持续成功 ⇒ pop-stall 不触发）；
6. 跨侧乱序供料 → kick 失去流序相邻性 → ffmpeg "Could not find ref
   with POC" → 丢帧 → pending 泄漏挂死；
7. 同侧阻断误伤游标自身（GPU 整臂零喂出）；
8. ⚠️ **工程事故**：一次 `git checkout` 误回退未提交的 .cc（从会话
   补丁记录完整重放恢复）——教训：金标绿了立即 commit。

### fork 级实测（全片 decode-only，min-of-2）

| 码 | main（C-45） | redesign | 对两解码器并联和 |
|---|---:|---:|---|
| hevc | 2629 | **2949** | 3027 的 **97.4%**（main 87%） |
| h264 | 3657 | **4247** | 4699 的 **90.4%**（main 78%）——**首次显著超纯 CPU 单臂 3701** |

## 2. 层4：排空线程（引擎，默认关）

`video_ocr_engine/gpu/device.py` 的 `_batch_iter` 加 `GPU_PIPELINE_DRAINER`（默认关）：
get_batch 独占线程预取深 4 批。**实测零收益**（hevc 全片 9.418 vs
9.432，段数 8340 一致）——引擎税的构成是线程争用而非"分析阻塞排空"
（与 C-10 流水发射同判例）。代码保留供复评。

## 3. 层2/3：亲和分区（fork 17f2beb，实验性默认关）

`DECORD_HYBRID_DECODE_CORES=N`（默认关；-1=total-3）。实现：拓扑掩码 +
`avcodec_open2` 前后快照差分钉 ffmpeg 线程 + Start 差分（lander/uploader
→服务组，cpu worker→解码组）+ 存量归服务组。

⚠️ **已知故障（降级原因）**：差分把 open 期间驱动/运行时 spawn 的
非 ffmpeg 线程（~23/55）一并钉进解码组，开启后 hevc 掉到 ~10fps 量级
（12~15 核档全复现；关闭即恢复 2906fps）。疑 CUDA parser/回调线程被
错分类后与解码线程同组互卡。修法方向：CPU Sets API
（SetProcessDefaultCpuSets + 白名单）或引擎侧 psutil 编排——留待
显式立项，不在本分支强推。

## 4. 层5：ExtractionPool（引擎 `video_ocr_engine/pipeline/pool.py`）

最小可用面：`pool.run(items, backends='pair')`——nvdec/cpu 交替、
每视频一线程、NVDEC 单会话（C-01）约束下 `max_workers=min(n,2)`；
结果对象与单跑相同（无新 schema）。探针 `_probe_pool_pairing.py`：
A=全 nvdec 顺序 vs B=pair 并发，交错 + 段数/文本逐位门禁。

## 5. 引擎级 A/B（redesign DLL vs main DLL，`_probe_dll_ab.py`，全片）

| 码 | 判定 | 均值 | 符号 | 备注 |
|---|---|---:|---|---|
| h264 | **真效应 B 快** | **−4.44%** | 0正/8负 | 与 fork 级方向一致 |
| av1 | 真效应 **A 快（回归）** | +2.19% | 7正/1负 | sd 5.2%（含 +14% 离群） |
| hevc | **一轮 1800s 超时挂死** | — | — | 见下 |

**hevc 不稳定（不合入的直接原因）**：A/B 中某轮单臂 1800s 挂死；复跑
3 次均正常（9.4~10.3s），但**冷跑段数 8353 ≠ 温跑 8340**——引擎负载
时序下存在不定帧丢失（force-close 代偿路径被触发）。fork 级金标
28/28 与全片解码正常，病灶在引擎消费节奏（OCR 变速 + calibrate）与
派工器的交互。**留待下一轮：复现脚本 + pop-stall 取证 + av1 回归
归因（疑 AV1 CPU 臂在引擎争用下拖慢——可先试 av1 禁 CPU 混跑回退）。**

## 6. 附：配对 A/B（`_probe_pool_pairing.py`，racelog 三件套）

原始读数双峰（26.7/34.0s）**完美随臂序交替**——首轮臂付冷文件缓存
（视频 GB 级 NVMe 读 ~7s），加 12s 冷却不消。**同温对比：pair≈seq≈
26.7s，配对零增益**；此前的"-20%"是冷/温臂污染。

机理：三件套引擎级是 **OCR-GPU-bound**（hevc 引擎 wall 9.4s 中 OCR
~6.9s），两工作线程共享单 GPU 的 TRT 推理——解码并行化救不了 GPU 上
的 OCR 串行。层 5 的前提（解码受限批量）在本负载不成立；代码与探针
保留，配对收益需在"解码占大头"的批量（大 stride/低段密度/更多视频）
复评。编码感知派工（h264→cpu）与 LPT 调度仍为正确的默认（无害）。
