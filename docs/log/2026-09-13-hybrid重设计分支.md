## 1. 层0/1：包缓存 + 供料期 GOP 派工（fork 8698cfa/17f2beb）

### 结构

- `Push` 只做：GOP 记账（key 开/关）+ 迟到包归属（已供 GOP 直供其侧、
  未供挂 stragglers）+ 入缓存。路由决策全部移到供料泵。
- `PumpFeed`（仍在 demux 线程，每包驱动）：cursor 起**同侧保序的前瞻
  供料**；分配按供水式贪心（`assigned_frames_` 水位 vs 当下 rc/rg）；
  饥饿门=两侧银行（queue/ready 帽）；EOF 无视门排空 + 臂 flush。
- kick 延迟化：换侧时离场侧当前 GOP 未供完 → 克隆包挂 `pending_kicks_`，
  游标越过该 GOP 再发（保持流序相邻性）。
- `NeedsPackets` = 缓存字节数 < 预算 OR 某侧饥饿（逃生门防"缓存满+
  两侧等料"与 demux 停读互锁）。
- 删除：BuildPlan/plan_side_/滑动视界/盲阶段窗口/REPLAN 旋钮/
  ChooseSide 整个函数。kick_guard_ 默认 0（债务克隆在新架构=洪泛源）。

### 调试史（全部实测踩出，供复评）

1. `fed_upto` 初始化为 0 而非绝对序列 → 缓存下标为负崩溃；
2. 游标越过"暂供完但未关闭"的开放 GOP → 剩余包无人供；
3. `assigned_frames_` 累计缺失（分配时 chunk expected=0）→ 水位恒 0
   → 贪心恒选 CPU（95 CPU/5 GPU）；
4. kick 只在 arm 分支更新 last_fed_side_ → 零 kick；
5. 债务克隆洪泛（分配领先交付 ⇒ 债务快照=巨额 pending）→ 离场侧解出
   整段错侧 GOP → 陈旧帧活锁（PopSide 持续成功 ⇒ pop-stall 不触发）；
6. 跨侧乱序供料 → kick 失去流序相邻性 → ffmpeg "Could not find ref
   with POC" → 丢帧 → pending 泄漏挂死；
7. 同侧阻断误伤游标自身（GPU 整臂零喂出）；
8. ⚠️ **工程事故**：一次 `git checkout` 误回退未提交的 .cc（从会话
   补丁记录完整重放恢复）——教训：金标绿了立即 commit。

## 2. 层4：排空线程（引擎，默认关）

`video_ocr_engine/gpu/device.py` 的 `_batch_iter` 加 `GPU_PIPELINE_DRAINER`（默认关）：
get_batch 独占线程预取深 4 批。**实测零收益**（hevc 全片 9.418 vs
9.432，段数 8340 一致）——引擎税的构成是线程争用而非"分析阻塞排空"
（与 C-10 流水发射同判例）。代码保留供复评。

## 3. 层2/3：亲和分区（fork 17f2beb，实验性默认关）

`DECORD_HYBRID_DECODE_CORES=N`（默认关；-1=total-3）。实现：拓扑掩码 +
`avcodec_open2` 前后快照差分钉 ffmpeg 线程 + Start 差分（lander/uploader
→服务组，cpu worker→解码组）+ 存量归服务组。

⚠️ **已知故障（降级原因）**：差分把 open 期间驱动/运行时 spawn 的
非 ffmpeg 线程（~23/55）一并钉进解码组，开启后 hevc 掉到 ~10fps 量级
（12~15 核档全复现；关闭即恢复 2906fps）。疑 CUDA parser/回调线程被
错分类后与解码线程同组互卡。修法方向：CPU Sets API
（SetProcessDefaultCpuSets + 白名单）或引擎侧 psutil 编排——留待
显式立项，不在本分支强推。

### 5.1 hevc 不定帧丢失：根因链与两次否决的修法（2026-09-14）

- **复现率 ~1/20**（20 轮冷压测：1 挂死 + 1 次 8354≠8340 段）；12 轮
  DEBUG 压测 4 轮出现 ffmpeg "Error constructing the frame RPS"（CPU 臂）。
- **根因 = open-GOP 跨侧参考**：gop K 换侧时，新侧解 K 的前导帧缺
  K-1 尾帧参考 → RPS 丢帧 → pending 卡死（挂死）或泄漏后 force-close
  （缺帧）。fork 级金标全绿（短窗/确定性时序打不到）。
- **决定性对照**：main DLL 同窗 **RPS=0、8340 恒定、clones≈3200**——
  旧设计的债务克隆（护栏 64/换侧）就是正确性机制本身：离场侧持有
  K-1 参考，其对新 GOP 前 64 包的克隆解码补齐前导帧。"洪泛"误诊是
  同侧乱序时代的产物。
- **否决一**：16 包尾部上下文喂给（last_fed_tail_ 克隆给新侧）——
  RPS 仍 128+（前瞻供料下 last_fed_tail_ ≠ K-1 尾；且前导帧参考可能
  深于 16 包/非解码序尾部）。
- **否决二**：债务克隆直接移植（guard 恢复 64）——8/8 压测全挂死：
  延迟 kick 路径不武装 kick_side_，克隆记账不一致。
- **修法方向（下一轮）**：上下文侧发射器——换侧后的首个 GOP 由持
  参考侧（离场侧）解码交付，新侧从 K+1 起接管（其首 GOP 的参考由
  自身 K 全解获得）。需 Pop 支持"按 chunk 侧直取"已具备，工作量在
  供料侧双投与记账。
- av1 +2.59% 回归**不是** CPU 混跑所致：GPU-only 试验 = +54.5% 大回归
  （8/8，15.1s = 纯 NVDEC 水平——main 的 av1 快正因为混跑 10.6 vs
  15.2）；真实原因未归因（份额/切换模式差异），量级可接受。

### 5.2 稳定性

### 5.3 GPU-bound 侧（用户授权的方向）

- h264 引擎级已是 OCR-bound（wall 3.0-3.5s，infer ~2.3s）；hevc 仍
  解码-bound（fork 97% 并联和后 decode 8.3s > OCR 6.9s）。
- **OCR_BATCH 16→64 扫描（bench ab 同进程交错）**：h264 冷 −1.76%/热
  +0.61% 符号混乱，hevc 冷 −0.03%/热 −2.38% 混合——**判漂移内，非
  杠杆**（C-15"OCR 输入侧不是杠杆"延伸到批吞吐）。
- 深层杠杆（TRT 引擎重建大 max_batch=6→32、fp16、CTC 设备化、多流）
  量级存在（h264 理论 −20~30%）但需引擎重建工具链 + 准确率门禁——
  建议显式立项，不在本分支内做。

## 6. 附：配对 A/B（`_probe_pool_pairing.py`，racelog 三件套）

原始读数双峰（26.7/34.0s）**完美随臂序交替**——首轮臂付冷文件缓存
（视频 GB 级 NVMe 读 ~7s），加 12s 冷却不消。**同温对比：pair≈seq≈
26.7s，配对零增益**；此前的"-20%"是冷/温臂污染。

机理：三件套引擎级是 **OCR-GPU-bound**（hevc 引擎 wall 9.4s 中 OCR
~6.9s），两工作线程共享单 GPU 的 TRT 推理——解码并行化救不了 GPU 上
的 OCR 串行。层 5 的前提（解码受限批量）在本负载不成立；代码与探针
保留，配对收益需在"解码占大头"的批量（大 stride/低段密度/更多视频）
复评。编码感知派工（h264→cpu）与 LPT 调度仍为正确的默认（无害）。

## 8. 终章（2026-09-14）：根因修复、三码全绿、已合入 main

### 8.1 段数漂移根因定稿（踢翻前两轮的三个假设）

实验链：RPS/迟到包双排除（8353 轮两者皆 0）→ 帧级 hash 证明 fork 级
三轮逐位一致且 ≡ 纯 GPU（"解码器完美"）→ 引擎层 dump 定位文本损坏
聚在 ~50 帧窗口（'1'→'9' 系统性误读=遮蔽像素）→ 8346 轮恰好多一次
kick → **kick 落位错位**：

前瞻供料下，换侧 kick 无论分配时即发还是游标触发，都落在离场侧
**队列尾** = 其后续 GOP 包之后——IDR 重置打在不自然位置，cuvid 冲掉
被打断 GOP 的在途重排窗（引擎时序才触发，故 fork 级一切绿灯）。
main 的 kick 恒在 K-1 末包后的自然位置故历史无损。

### 8.2 修复：kick 泵内按流序注入

kick 一律挂 pending_kicks_，供料泵在 dst 侧 after_gop 之后首个被供
GOP 的主区间首包前注入（= K-1 末包后、后续 GOP 前，与 main 等价
位置）；EOF 兜底全发；DECORD_HYBRID_KICK_OFF=1 消融开关。

### 8.3 终验（全部符号一致判据）

| 门 | 结果 |
|---|---|
| 引擎 hevc 段数 | **18/18 轮 8340 恒定**（修前 2/6 漂移） |
| 金标 | 28/28（dev dll + wheel 各验） |
| 压测 harness | hevc/av1/h264lg/hevc-cpu ×3 trial，bad=0 |
| fork 速率 | hevc 2873 / h264 3650 / av1 2836 fps（对并联和 95/78/93%） |

| 产品路径 | wheel 重建安装（dll md5 6ec5b1ea）+ 3/3 恒定 |

av1 此前 +2.59% 回归同为 kick 错位所致，随修消失。
