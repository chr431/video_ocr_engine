# 2026-10-10 hybrid 三码缺口矩阵与机制更正（0.23.1）

> 用户裁决：三码全测（test6 同内容三码版）再定方向；"有的编码 hybrid
> 速率和较快单臂很接近"。判据面结论见 C-66（**本日更正**）；本文叙事。

## 1. thr_foreign 出生删失修复（v10.1，先修工具再测）

解码池线程常在相位中段出生（hybrid 的 CPU 臂池取决于校准走了哪条路），
边界交集会把它们整体剔除——首测 h264 hybrid 外来簇 0.3M/帧 vs 纯臂
14.7M/帧即删失假象（hevc 校准走 CPU 解码→池早生→数字自洽）。
per_phase 改携带 seen 表：区间新出生 TID 基线记 0。

## 2. 三码矩阵（test6 同内容 3000 帧 TRT OCR，预热后 3 reps 中位）

| 码 | nvdec 纯 | cpu 纯 | 理论和 | hybrid | 缺口 | CPU 臂实得 | GPU 臂 |
|---|---|---|---|---|---|---|---|
| hevc | 2052 | 837 | 2889 | 2727 | **−5.6%** | 654fps（−22%） | +1% |
| h264 | 951 | 2550 | 3500 | 2364 | **−32.5%** | 1419fps（−44%） | −1% |
| av1 | 1727 | 1273 | 3000 | 1984 | **−33.9%** | 198fps（−84%） | +3% |

- GPU 臂三码全部无损（−1~+3%）——**快臂无论怎么分都吃满**。
- 用户说的"hybrid≈较快单臂"：h264 实际**更糟**（2364 < 纯 CPU 2550，
  即 C-53 的 +6.1% 慢复现）；hevc 是唯一显著赢面（+37% vs 最快纯臂）。
- 缺口与 CPU 臂退化排序 av1≫h264>hevc。

## 3. 机制更正（推翻 2026-10-09 的"供给线封顶"判读）

决定性判别 = `assigned_c == frames_c` **三码逐 rep 全等**（hevc
720/720、h264 1800/1800、av1 300/300），且 rc_now（泵的速率 EWMA
终值）≈ 纯臂速率（hevc 760/837、h264 2440/2550、av1 1160/1273）：

- **CPU 臂分到多少解多少、解得动**——不是供给饥饿：up_cempty 是
  "等下一单"的空转计数（up_nobuf=0；cache 峰 36-81MB ≪ 512MB；
  decode-only 3118>理论和 2889——供线喂得满理论值）。
- **是泵的 GOP 粒度贪心派工欠配 CPU 臂**：GOP 粒度粗（hevc 240 /
  h264·av1 300 帧/个，全程仅 ~10-12 个可分单元）+ 速率 EWMA 冷启动
  偏置——早期低速估计把大部分 GOP 划给快臂且不可逆：
  - av1 极端：EWMA 终值≈纯臂 90% 证明臂有能力，但只分到 1/10 GOP
    （300 帧），84% 时间闲置；kicks=0（kick 再平衡机制存在但未触发）。
  - h264：分 6:4（速率比例最优 ≈8:2），CPU 臂提前 0.56s 完成闲置。
- 2026-10-09 的三连否证（非计算争用/非宿主挤压/非引擎耦合）全部
  维持；错的是把 up_cempty 读成了"包荒"——它是"单荒"。

## 4. 方向建议（fork 泵侧，收益预估）

1. **分配前瞻修正**：按 rc:rg 比例预留 GOP 而非纯贪心即时派——
   hevc −5.6%→~0；h264/av1 期望 −33%→−10% 内（GPU 臂无损前提已验）。
2. **迟臂再平衡**：EWMA 上升后从快臂未开始 GOP 回收（kick 机制已有，
   av1 kicks=0 说明触发条件太保守）。
3. 供给线并行化**降级为非优先**（供线已证明喂得满理论值）。
