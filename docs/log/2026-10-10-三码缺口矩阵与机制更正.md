# 2026-10-10 hybrid 三码缺口矩阵与机制更正（0.23.1）

> 用户裁决：三码全测（test6 同内容三码版）再定方向；"有的编码 hybrid
> 速率和较快单臂很接近"。判据面结论见 C-66（**本日更正**）；本文叙事。

## 1. thr_foreign 出生删失修复（v10.1，先修工具再测）

解码池线程常在相位中段出生（hybrid 的 CPU 臂池取决于校准走了哪条路），
边界交集会把它们整体剔除——首测 h264 hybrid 外来簇 0.3M/帧 vs 纯臂
14.7M/帧即删失假象（hevc 校准走 CPU 解码→池早生→数字自洽）。
per_phase 改携带 seen 表：区间新出生 TID 基线记 0。

## 2. 三码矩阵（test6 同内容 3000 帧 TRT OCR，预热后 3 reps 中位）

| 码 | nvdec 纯 | cpu 纯 | 理论和 | hybrid | 缺口 | CPU 臂实得 | GPU 臂 |
|---|---|---|---|---|---|---|---|
| hevc | 2052 | 837 | 2889 | 2727 | **−5.6%** | 654fps（−22%） | +1% |
| h264 | 951 | 2550 | 3500 | 2364 | **−32.5%** | 1419fps（−44%） | −1% |
| av1 | 1727 | 1273 | 3000 | 1984 | **−33.9%** | 198fps（−84%） | +3% |

- GPU 臂三码全部无损（−1~+3%）——**快臂无论怎么分都吃满**。
- 用户说的"hybrid≈较快单臂"：h264 实际**更糟**（2364 < 纯 CPU 2550，
  即 C-53 的 +6.1% 慢复现）；hevc 是唯一显著赢面（+37% vs 最快纯臂）。
- 缺口与 CPU 臂退化排序 av1≫h264>hevc。

## 3. 机制更正（推翻 2026-10-09 的"供给线封顶"判读）

决定性判别 = `assigned_c == frames_c` **三码逐 rep 全等**（hevc
720/720、h264 1800/1800、av1 300/300），且 rc_now（泵的速率 EWMA
终值）≈ 纯臂速率（hevc 760/837、h264 2440/2550、av1 1160/1273）：

- **CPU 臂分到多少解多少、解得动**——不是供给饥饿：up_cempty 是
  "等下一单"的空转计数（up_nobuf=0；cache 峰 36-81MB ≪ 512MB；
  decode-only 3118>理论和 2889——供线喂得满理论值）。
- **是泵的 GOP 粒度贪心派工欠配 CPU 臂**：GOP 粒度粗（hevc 240 /
  h264·av1 300 帧/个，全程仅 ~10-12 个可分单元）+ 速率 EWMA 冷启动
  偏置——早期低速估计把大部分 GOP 划给快臂且不可逆：
  - av1 极端：EWMA 终值≈纯臂 90% 证明臂有能力，但只分到 1/10 GOP
    （300 帧），84% 时间闲置；kicks=0（kick 再平衡机制存在但未触发）。
  - h264：分 6:4（速率比例最优 ≈8:2），CPU 臂提前 0.56s 完成闲置。
- 2026-10-09 的三连否证（非计算争用/非宿主挤压/非引擎耦合）全部
  维持；错的是把 up_cempty 读成了"包荒"——它是"单荒"。

## 4. 方向建议（fork 泵侧，收益预估）

1. **分配前瞻修正**：按 rc:rg 比例预留 GOP 而非纯贪心即时派——
   hevc −5.6%→~0；h264/av1 期望 −33%→−10% 内（GPU 臂无损前提已验）。
2. **迟臂再平衡**：EWMA 上升后从快臂未开始 GOP 回收（kick 机制已有，
   av1 kicks=0 说明触发条件太保守）。
3. 供给线并行化**降级为非优先**（供线已证明喂得满理论值）。

## 8. 引擎耦合轮（同日续）：三修三反 → 归因改写为 GPU 争用

用户裁决「进入下一步性能改善」（靶：引擎耦合 −9~19%）。三轮实验与
判别：

- **背压帽上移**（FeedStep cap 池深 1012→ReadyCap 1620）：反效果
  （2502 vs 2759，HOL +23%）——HOL 是主源、背压只是症状；放宽帽让
  GPU 跑更远、ready 堆更狠。回滚。
- **GpuWorker idle 等待 1ms→200µs**：反效果（2542 vs 2759）——高频
  让出自旋本身成为 CPU 臂解码的负载。回滚。
- **发射时间线终局账本**：消费者零空隙（100% 批内）、G/C 批耗时同侧
  等长（0.090s/256 帧=2844fps 稳态）——发射环节无损耗，节拍=批节奏。

**判别实验（终局）**：
- CPU-OCR 臂：hybrid 1814 > 纯 nvdec 1716（**+6%**）——解码混跑本身
  无损耗（微赚，CPU 臂填 NVDEC 闲置）。
- TRT 批延：hybrid **13.21ms** vs 纯 nvdec 8.57ms（**+54%**）——
  4.6ms × 464 批 ≈ 2.1s ≈ 损耗主体。

**归因改写**：引擎耦合 −9~19% 的主体 = **TRT 推理与 GPU 解码链
（NVDEC 后处理+设备侧 analyze+H2D）同卡争用**（C-47 的 GPU 链争用
判读在 hybrid 全管线下的量化确认）。hol/idle/背压是解码链被 TRT 挤
慢后的下游排队影子（GpuWorker idle 40103 次、ready 中位 1204 等均
此因），非独立瓶颈——三个"直接修"全部反效果正是因为它们优化的
是影子。

**修复方向（留给下一轮，fork/引擎两侧）**：①TRT 流级优先级/独立流
时间片（引擎侧，DEFER_SYNC 已有关联面）；②TRT 批加大（464 批×
8.57ms=4s 纯臂基线，批大小是吞吐杠杆）；③CPU-OCR 混跑部署模式
（本机 +6% 无损耗）。

**方法论教训（记档）**：hol_ev/hol_us/ready 水位/背压阈值这组信号
是"排队论影子"，位置在下游；优化前必须先做"影子 vs 本体"判别
（本例：TRT 延迟 × 批数 ≈ 损耗，一次判别胜过三次修复尝试）。

**本轮代码变更**：零（三修全回滚；插桩 [hybrid-w] idle 行增
pend/gpf/eq/cache 读数保留在 build-dev，未推 master）。


## 9. TRT 争用改善轮（同日续）：三杠杆证伪 → 目标本身达成 92%

用户目标：「TRT 推理时 hybrid 全流程速率接近 nvdec+CPU 之和」，授权
自行决策。四个杠杆逐一实测：

| 杠杆 | 结果 | 判读 |
|---|---|---|
| TRT 批 16→36 | **2444 vs 2625，反降** | 批延 25.5ms ≈ 2×13.1（线性于批大小，吞吐不变）；攒批更久 |
| 流优先级 | 未试 | 2026-09-10 已试已回退（先例：瓶颈非 SM 调度）；本轮判别补证 |
| DEFER_SYNC=1 | 2461，批延 12.88ms 不变 | 提交/收集分相不减少 GPU 侧占用本身 |
| CPU-OCR 判别 | hybrid+CPU-OCR 1748 ≈ nvdec 纯臂 1713 | TRT 不在时引擎耦合几乎消失（同带 ±15% 会话方差）|

**判别补证**：decode-only 本身会话方差 2109-2489（±15%）——fork 混跑
调度受主机态影响，读数比较须同会话配对。

**收官账本（av1 23970 帧，TRT 口径，中位）**：
- 纯臂 nvdec 1720 + cpu 1216 = 理论 **2937**
- hybrid 现状 2600-2760 → **达成率 92%**（多次会话复测一致）
- CPU-OCR 口径对照：理论 2769，hybrid 1748 → 63%（CPU 臂被 OV 挤，
  C-50 争用税——部署敏感面）

**结论**：TRT 口径的「接近双臂和」**已基本达成**（92%）；剩余 8% =
TRT 与解码链同卡争用，四个软件杠杆全部证伪——同卡架构下的剩余空间
需要驱动级手段（CUDA MPS 分时/独立编码会话）或硬件分离（解码/OCR 异
卡，C-60 复评触发），引擎侧无免费解。CPU-OCR 口径的 63% 是另一独立
问题（OV 线程与解码线程争核，C-50 域）。

**方法论**：本轮再次验证「影子 vs 本体」判别的价值——批延线性实验
（36≈2×18）一次证伪最大杠杆，避免在错误方向上继续投入。


## 10. 三码达成率补测（同日续，同会话配对）

用户要求 h264/hevc 也测「是否接近最优」。同会话配对（消 ±15% 会话
方差），23970 帧 TRT 口径中位：

| 码 | nvdec | cpu | 理论和 | hybrid | 达成率 | vs 最快纯臂 |
|---|---|---|---|---|---|---|
| hevc | 2060 | 897 | 2957 | 2727 | **92%** | **+32%** |
| h264 | 944 | 2602 | 3546 | 2903 | **82%** | +12% |
| av1 | 1720 | 1216 | 2937 | 2727（上轮） | 92% | +25% |

**h264 的 82% 构成判别**（vs 另两码 92%）：
- hybrid 内臂速：CPU 臂实得 1925 vs 纯 2602（**−26%**）；NVDEC 臂
  903 vs 944（−4% 轻）。
- CPU-OCR 判别臂（10 线程档）：rc_now 1437 vs 纯臂档位速率——CPU 臂
  深度受损。
- **机制（与 av1/hevc 的 GPU 争用不同源）**：h264 主臂=CPU（32 解码
  线程档），hybrid 下 CPU 臂解码线程 × 上载器 H2D memcpy（CPU 工作）
  × 泵/发射在 16 物理核上互相挤——**H2D 上载×ffmpeg 解码争核**；
  NVDEC 臂不受此税（GPU 解码）故 −4%。

**收官结论**：三码达成率 92/82/92——「接近最优」在 hevc/av1 成立
（+25~32% vs 最快纯臂，hybrid 是正确选择）；h264 打八二折但**仍然
快于最快纯臂 +12%**（C-53 的 hybrid 选择在全长片上首次转正——此前
3000 帧窗口 h264 hybrid 比 CPU 纯臂慢 +6%，长片分配自愈后转正）。
h264 的剩余 18% 修复方向 = CPU 臂线程档在 hybrid 下降档（32→16，
减上载/解码争核）——引擎 decode_caliber 按 gpu_pipeline_mode 分叉
即可，属 C-50 域的微调，预期收益 ~5-8%。


**线程降档验证（h264，当轮闭环）**：DECODE_THREADS 16/12 档实测
2498/2237 vs auto(32) 2912——降档反降（32 线程并行度收益 > 上载争核
损失）。h264 的 82% 为当前架构实际水平，auto 档维持；剩余 18% 若要
追，方向在 fork 上载器（GPU 直写绕过 staging memcpy）而非线程档。

**三码最终口径（本轮入档）**：hevc/av1 达成率 92%、h264 82%（均
+12% 以上 vs 最快纯臂）——C-53 的 hybrid 选择准则在全长片三码全部
转正。
