## 1. decord 性能数字口径修正（用户纠正的落点）

**问题**：README 的性能表虽标注了 `get_batch` 顺序读（已无 OCR），但：
① 数字来自旧轮次、未随 fork 清理复测；② **英文版数字与实测严重不符**
（1761/2216/1852，实测 ~1484/1978/2074）；③ 缺少明确的「纯解码 vs 引擎
e2e」口径声明，易被误用。

**修正**：
- 新增 `tests/bench_decode_only.py`——**可复现的纯解码基准**（三编码 × 三
  后端，全帧顺序读，批 250，全片 23970 帧 × 5 轮中位），任何人在 decord 仓
  内一键复跑；
- README / README_EN 重测更新（2026-09-19 `v0.8.4` 口径）：

| 解码方式 | H.264 | HEVC | AV1 |
|---|---:|---:|---:|
| `cpu`（线程 h264/hevc 32、av1 24） | 1386 | 841 | 996 |
| `gpu`（NVDEC 全帧） | 864 | 1782 | 1511 |
| `hybrid_gpu`（实验性） | **1484** | **1978** | **2074** |

- **两处口径声明**（中英各一）：明确「本表=纯解码，不含引擎侧耦合（推理/
  分段/消费线程）；引擎 e2e 在 video_ocr_engine 仓，**两者不可混用**」。

**要点更新**：hybrid 三码全胜最优单臂（+7% h264 / +11% hevc / +37% av1）；
新增「解码速率按码流实测而非编码名」的提醒（同 h264，软编码流 CPU 软解可慢
1.6×——这条来自工具集调查）。

```bash
pip install --force-reinstall --no-deps \
  https://github.com/chr431/decord/releases/download/v0.8.4/decord-0.8.4-cp313-cp313-win_amd64.whl
```

0.8.3 → **0.8.4**。功能验证：`hybrid_gpu` ctx / `set_decode_window` /
`hybrid_stats` / `decode_stats` 全部可用，读 3000 帧正确。

**`env_probe.decord_fact` 适配两种安装形态**（这是本轮的关键设计变更）：
- `wheel` 形态（推荐路径）：DLL 由 wheel 自带，**不该**与本地 dev 构建比对
  md5——两者是不同产物（独立构建链/版本号）；
- `dev` 形态（本地 `rebuild_dev.bat` 部署）：仍校验「构建产物 md5 == 已部署
  md5」，防「改了 C++ 忘了部署」；
- `auto` 依据 wheel 元数据（`importlib.metadata` 的 files 里是否有
  `decord.dll`）自动判定。

`env_doctor` 现报「环境就绪」（此前会因 wheel 与 dev 构建 md5 不同而误报）。

## 4. 引擎侧清理（第一批：假配置面）

**发现**（技术债调查）：`RunConfig` 有 **6 个字段解析后无人读取**——消费者
直读 env（`config.env_bool(...)`）：
`ocr.trt_fp16` / `ocr.trt_defer_sync` / `pipeline.gpu_stream` /
`pipeline.gpu_drainer` / `diag.subprobe` / `diag.bounds_debug`。

**危害不止是死代码**：`config_digest` 覆盖全部解析值，而这 6 个不决定行为 →
**A/B 对账拿到与实际行为不符的假指纹**。

**修复（最小正确方案）**：
- `registry.Knob` 增 `env_live_only: bool = False` 标记；
- 6 个旋钮标 True（含注释说明）；
- `resolve()` 计算 digest 时**排除**它们。

**实测验证**（精准性）：
```
TRT_FP16 1 vs 0      → digest 相同 ✓（已排除）
GPU_STREAM 1 vs 0    → digest 相同 ✓
OCR_GAMMA 1.5 vs 2.5 → digest 不同 ✓（排除是精准的，未误伤）
rc.ocr_trt_fp16 仍可读=True ✓（introspection 兼容）
```

**为何不改注入而改 digest**：把这 6 个接进 SessionSpec 需动 TRT 引擎构建
路径（`_fp16_on` 是模块级常量、在 `trt.py` 14 处热路径读；fp16 走 TrtEngine
构造且**有测试依赖**）——风险显著高于「digest 更准」的收益。且消费者读 env
是**有意设计**（子进程 A/B 可逐臂切换 env，见 `_fp16_on` docstring），
改成构造期注入会破坏该能力。
