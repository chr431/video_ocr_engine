# 2026-09-10 hybrid 联调深挖（decord 解除冻结 + 引擎消费端改造）

背景（用户 2026-09-10 指示）：decord 侧此前单独调试出 hybrid 增益，但引擎
联调反而更慢——解除冻结，本地修改（**不推送远端**），先修 bug 再做调度优化。

## H0 增益逐轴复现（tools/_probe_hybrid_axis.py）

从 fork bench 口径（yuv420/无 ROI/fork 默认线程/批 250）逐轴加引擎条件，
纯解码吞吐（fps，3000 帧窗口）：

| 编码 | bench口径 | +ROI | +引擎线程档 | +批64（引擎解码口径） | NVDEC+ROI |
|---|---:|---:|---:|---:|---:|
| h264 (test5) | 1283 | 2351 | 2311 | **2302** | 988 |
| hevc (test) | 2012 | 2396 | 1976 | 2105 | 2187 |
| av1 (test6) | 1960 | 2464 | 2773 | **2601** | 1704 |

结论：**用户记忆中的 hybrid 增益在 0.8.2 上真实存在**——h264 hybrid 纯解码
是 NVDEC 的 2.33×，av1 1.53×；但 h264 的纯 CPU 软解（~3200fps）更高，
hevc 两者持平 → 引擎最优单侧结论（C-33/C-05）不变。

## H1 av1 hybrid close 崩溃（已修，decord 本地 73e5540）

轴矩阵首跑 av1 在 `vr.close()` 时 access violation（约 1/3 概率，同进程
第 3 个 reader）；单 reader 子进程 40 次不复现。上 ASAN（configure_asan.bat，
诊断构建）后**首个 close 即命中**：

    heap-use-after-free READ @ HybridGpuBufferPool::Deleter
        (hybrid_threaded_decoder.cc:262, 锁已析构池的 mutex)
      ← NDArray::operator= ← VideoReader::~VideoReader (video_reader.cc:364)

根因：析构先 `decoder_.reset()`（连带销毁 hybrid 显存池），后释放
`cached_frame_`/`tmp_key_frame_`——两者可能仍持有引用该池的 hybrid_gpu
输出帧。池内存未被堆复用时静默，被复用/反提交即崩；av1 路径总在缓存留
GPU 池帧所以每关必中（ASAN 口径）。引擎侧 `vr.close()` 被 `except
Exception: pass` 包裹，此前一直静默吞掉。

修复：两个成员的释放挪到 `decoder_.reset()` 之前。ASAN 下 24 个 hybrid
reader（8 序列 × 3 变体 × 3000 帧）零内存错误；release dll（build-081fix）
重建后引擎全后端 sha 逐位一致。ASAN runtime 加载要点：依赖 DLL 必须
与 decord.dll 同目录（FFmpeg63 + clang_rt.asan_dynamic-x86_64.dll）。

## H2 引擎内流失定位

引擎口径 hybrid av1 消费 ~2000fps vs 同进程纯解码 ~2400fps。逐项排除：

- **TRT 并发争用：3%**（同进程 decode-only ± TRT 负载线程对照，排除）。
- **GIL 线程耦合：无**（+2 个 Python 自旋线程 -3% ~ +3%，排除）。
- **消费流耦合：成立但改造后不涨**（见 H3），说明每段成本不是流排队。
- **每段 CUDA 提交开销：主因之一**。content_range 微基准 46µs/次
  （纯 launch 10µs）；管线内 emit_autocrop 实测 ~170µs/段（驱动锁竞争
  放大）。1109 段 × 每段多次 launch+sync ≈ 消费端 0.5-0.9s。
- **轻消费对照（关 autocrop/merge/crops）：消费恢复 2423-2445fps**，
  证明剩余流失全部在消费端 emit 侧。

## H3 修复：消费流 + 批量 autocrop（引擎本地）

1. **消费专用流 `_stream_c`**（GpuFrameAnalyzer）：content_range /
   compare_pair / luma_into / rep D2H 改走消费流，同步不再等生产者在途
   批（帧数据在 analyze_batch 同步点已就绪，无需跨流依赖）；顺带修掉
   autocrop 关闭时 y_pool 帧无同步点的潜在竞态（emit 内显式 sync）。
2. **批量 autocrop 下沉 OCR worker**：新增 `col_ink_batch` 内核（block=
   一帧，判据与 col_ink 逐位一致）+ `content_range_batch`；emit 只打
   5 元组 (owner,ptr,h,w,sharp)，OcrSession.flush 一次 kernel 处理整批
   段后再按裁后宽度分组。autocropper 由 GPU 管线注入，None 时保留 emit
   内逐段路径兜底。
3. **fill_prev 收拢**：B 次 cudaMemcpyAsync → 2 次（行 1..B-1 是连续
   区段，逐位等价）。

效果（3000 帧，本地 dll，sha 全部逐位一致）：emit put 体 NVDEC
0.25→0.14s、hybrid 0.77→0.39s；hybrid av1 wall 1.74→1.70s（对 NVDEC
1.80s 从持平转为稳定反超 ~5%）。

## 边界与未竟

- 轻消费天花板 1.42s vs 现值 1.70s 的差 ≈ merge 判定（每段 2 次
  launch，控制流语义不可批量化）+ keep_crops D2H（结果输出，不可避免）
  + 残余交错损耗（机制未完全钉死，运行间方差 ±10%）。
- prefetch 钳制扫描（384/768/1536/3072）：全平，非杠杆。
- 以上 dll 均为本地构建（build-081fix，含析构修复）；pip wheel 0.8.2
  不含 H1 修复，发布需 fork 出 wheel（未推送，等用户拍板）。

## K 轮：hybrid 与两侧速率之和的差值分解（同日续）

### K1 精确测量（6000 帧 × 4 轮中位，ROI/yuv420/批64）

av1：NVDEC 1743 + dav1d(nt24) 1300 = 理想和 3042；hybrid 实测 2146。
**损耗 897fps = 29.5%**。

### K2 调度轨迹（DECORD_HYBRID_DEBUG）

- 逐 256 帧分侧发射时间线：**近似交替而非并发**——CPU 块期间 GPU 发射
  恒 0、拉取掉到 dav1d 的 1200-1400fps（占墙钟 ~95%）；GPU 块期间以
  4500-9500fps 突发清 backlog（帧早已预解码）。
- 铁证：`[hybrid-w] idle rdy=1006 crdy=0 q=786`——GPU worker 闲置，
  手握 786 个已路由包不喂。
- 无慢批（批耗时 p50 35ms、max 66ms，无切换尖峰）→ 非切换损耗。

### K3 根因链

`FeedStep` 喂包闸：`ready_ + reserve >= gpu_pool_frames_` 即停喂。而
`gpu_pool_frames_` 按**全帧**字节预算（1080p NV12 ~3.1MB/帧 → 1012 帧）
且不随 SetRoi 重算——ROI 后实际输出帧 ~5.4KB，深度虚小 ~570×。GPU 预
解码 ~1000 帧后即被池深钳死，整个 CPU 块期间只能空转。

### K4 修复与迭代（decord 本地 d94d92e）

- **池深按 ROI 帧字节重算**（SetRoi 时，clamp 8192；ROI 帧 5.4KB ×
  8192 ≈ 44MB 显存）：decode-only hybrid 2146 → ~2400-2600（+10-20%）。
- **否定结果**：DECORD_HYBRID_FORCE_SHARE 份额扫描 0.30-0.50 全平坦
  （份额不是约束）；DECORD_HYBRID_PREFETCH 扫描在池深修复前后均无一致
  收益（demux 领先不是当前卡点）；TRT 争用 3%、GIL 无涉（前轮已排除）。
- 剩余 ~15-20% 差距为弥散型：路由前瞻（av1 demux 领先钳 384 的竞态
  保护）、两侧互扰、GPU 时钟漂移（运行间 ±10%），无单项杠杆。
- 引擎口径：hybrid av1 ~1.70-1.73s vs NVDEC 1.80s —— hybrid 是 av1
  引擎内最快路径（~5%）；h264/hevc 仍为纯 CPU/NVDEC 最快（C-05）。

工具：tools/_probe_hybrid_sum_gap.py（三速率+差值）、
tools/_probe_hybrid_trace.py（调度轨迹剖析）。

## K6 轮：逐位等价门禁 + demux 领先功效实验（判平）

- **逐位等价**：hybrid（默认/1536/2980 prefetch）× 6000 帧输出与 NVDEC
  参照逐位一致 ✓ —— 池深修复与深 lead 喂包时序均不破坏帧序/像素
  （tools/_probe_hybrid_bitwise.py）。这也是本系列 fork 改动的正确性门禁。
- **demux 领先功效**（配对交错 6 轮，9000 帧）：复测的 384 基线自身漂移
  -10%（热态），1536/2980 相对 0.958-0.969 ≈ 噪声内无收益。深 lead 会
  放大 av1 跨侧交界竞态（历史实测 8 帧错位）→ **不抬钳制，判平**。
- 状态：池深修复后 hybrid decode-only 典型 2400-2700（理想和 3042，
  剩余差距弥散型）；引擎口径 hybrid av1 反超 NVDEC ~5%。迭代收敛。
