> 任务（用户）：性能轮暴露了 decord C++ 侧若干缺陷（flush 早发、异常逃逸、
> Debug 构建），怀疑 Python 侧还有更多；本轮力求彻底修复不留后患。
> 方法：两个并行子代理按「并发/锁/唤醒」与「异常处理」两轴全量审计

## 1. 已修缺陷清单（13 项，按严重度）

### P0（挂死 / 静默错误 / 资源泄漏）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | **池 recycle 顺序反了**：`frame.pool = None` 后入列 → 对象带 None 进空闲列，下次复用时 GC 的 `__del__` 撞 None 被 `except: pass` 吞掉 | `video_ocr_engine/gpu/device.py` 的 `_YFramePool`/`_DevBatchPool` | 每轮 acquire/recycle 循环泄漏一块显存（长驻进程必 OOM）；`release_all` 也回收不到 |
| 2 | **注入引擎路径从未接通**：`_ocr_engines` 只用于判定 `_owns_engines`，从未存入 `self._engines` | `video_ocr_engine/pipeline/ocr_stage.py:215` | 任何注入路径（GPU 校准失败回退宿主）必崩 `IndexError`，且注入引擎既不使用也不归还（TRT 上下文泄漏） |
| 3 | **看门狗失败路径不停止**：`_diag.stop()` 只在成功路径 `_assemble_report` 调用 | `video_ocr_engine/extractor.py` 的 `finally` | 每次失败的 extract 泄漏一个 watchdog 线程，持续每 30s 写 stall JSON |
| 4 | **snapshot 是排干语义而看门狗在 run 中途调用** | `video_ocr_engine/domain/metrics.py` + `video_ocr_engine/domain/diagnostics.py:204` | 一次停顿后最终 RunReport 只剩停顿后的样本 → PI-3/PI-10 阈值指标偏小 → **门禁静默放行** |
| 5 | **worker 的 `except Exception` 接不住 BaseException** | `video_ocr_engine/pipeline/ocr_stage.py` | 线程死而 `self.err` 恒空 → `put`/`finish` 自旋挂死（实测 rc=124）；同族三处（`_put_infer`、GPU 生产者） |

### P1（错误语义丢失 / 性能缺陷）

| # | 缺陷 | 修复 |
|---|---|---|
| 6 | `assert tier in (...)` 做运行时校验：`VOE_TELEMETRY=FULL` 撞**无消息** AssertionError，`-O` 下静默降级 | 改显式 `ValueError`（带消息）+ `resolve._parse` 对枚举 str 做大小写/空白归一 |
| 7 | `cudaMalloc` 失败丢弃 `_err` → `int(None)` 报 `TypeError` | 检查 err 抛 `MemoryError`（显存不足的真实原因可见） |
| 8 | 池淘汰自噬：`popitem(last=False)` 会选中刚 append 的同 key 引擎 | 优先淘汰**其他 key** 的最旧条目 |
| 9 | 池 key 缺 gamma/gpu_ctc（构造期冻结）→ 同进程改 env 后旋钮静默失效 | 两者入 key |
| 10 | 池 `acquire`/`_recycle` 无锁 check-then-act（并发 `pop` 空列表） | 加锁（`release_all` 同步） |
| 11 | `finish()` 无超时 join：worker 卡设备调用即永久挂死 | `join(timeout=10s)` + 告警 |
| 12 | GPU 生产者 `except Exception`：BaseException 逃逸 → run 报成功但帧数静默截断 | 改 `BaseException`（与 `video_ocr_engine/gpu/device.py` 的排空线程对齐） |
| 13 | `ensure_gpu_initialized` 无锁 → 并发首调时后者 `clear()` 掉前者 DLL cookie | 加锁 + 双检 |

### P2（可诊断性）

- NVDEC 打开失败丢原始异常文本 → 保留 `%r` + `exc_info=True`（与 hybrid 分支一致）
- `codec` 探测失败静默 → 记 `degraded_reason`
- `color_range` 读取失败静默归零 → 记 `degraded_reason`（full range 流被当 limited 会错误拉伸 Y）
- `RunJournal._last_err` 只写不读（且 `__init__` 未初始化，`report()` 读它会 AttributeError）→ 报告含 `last_error`
- `pool.run([])` → `ThreadPoolExecutor(0)` 抛 ValueError → 空输入直接返回 `[]`
- `engine_sm()` 把**失败的探测**也缓存整个进程 → 只缓存成功（参照 `nvdec_available`）

## 2. 与 decord C++ 侧缺陷的同族关系（方法论）

本轮确认两类跨语言的**同族**缺陷模式：

| 模式 | decord C++（性能轮已修） | Python 侧（本轮修） |
|---|---|---|
| 「等一个永不到来的事件」 | 排空标记早发（`gi<0` ≠ 已派工作喂完） | worker 死而 `err` 恒空 → `put` 自旋；`finish` 无超时 join |
| 异常静默逃逸 | 工作线程未包 try/catch → terminate → 静默 abort | `except Exception` 接不住 BaseException；`__del__` 撞 None 被吞 |
| 状态被记录但无人读 | `[hybrid-EXC]` 打到 stderr 而 Pop 未转达 | `_last_err` 只写不读；降级原因只进 logger（包根 NullHandler） |

**新纪律（入审计）**：等待循环的出口必须**独立于单一错误信号**（以「对端线程存活」为主判据）；工作线程异常收口必须覆盖 `BaseException`；析构路径的资源归还不得依赖可能已被置空的引用。

## 4. 未修项（登记为已知边界，非遗漏）

- **`_YFramePool` 空闲列溢出时的显式 `cudaFree`**：设计上刻意不在析构上下文释放
  （B6），溢出告警 + `release_all` 兜底。保持。
- **`Diagnostics` 跨下划线读 `watchdog._th`**：实测可产生 2 个 watchdog 线程，
  但共享同一 `_stop` 事件、实测无泄漏（`leftovers = 0`）。若将来 `_loop`
  引入非幂等副作用需升级。
- **`nvml_handle()` 无锁双检**：并发首调会 `nvmlInit_v2` 两次，无泄漏（不
  `nvmlShutdown`），仅 ~20ms 重复成本。低优先。
- **`_batch_iter` 排空线程 `finally: _q.put(None)` 无超时**：默认关
  （`GPU_PIPELINE_DRAINER=False`），列为已知边界。
