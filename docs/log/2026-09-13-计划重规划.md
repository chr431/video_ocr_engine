# 2026-09-13 工作项 3：计划重规划（opt-in）——hevc 全片 −5.42%，但**编码相关**

## 一、动机（由工作项 2 的负结果反推出来）
fork 自陈的 v1 取舍是"规划冻结规划时的速率比；运行中速率漂移不做重规划"。工作项 2
用"上一次运行的速率"播种计划（等价于冻结一个**外部**速率），在 w=3000 上倒亏
**+8.5%** —— 这恰好证明"冻结错速率比的代价真实存在"。于是让计划能随**实测**漂移重建。

实测漂移有多大（`[hybrid-replan]`，hevc 全片 24000 帧，PCT=10 时触发 3 次）：
`rc 902→878→1027→913`、`rg 1782→2281→2196→2557` ⇒ **CPU −3%~+17%、GPU +4%~+28%**，
份额在 0.26~0.34 之间摆动。**这就是"冻结"要付的账**。

## 二、实现（opt-in，铁律 10）
- `MaybeReplan(key_pts)`：计划预路由命中处调用；当实测速率相对计划速率漂移超阈值、
  距上次重规划 ≥GAP 个 chunk（迟滞）、两侧速率均已知 ⇒ 以当前实测份额重建计划
  （从当前 keyframe 覆盖未消费部分；`assigned_frames_` 累计量保留，全局配比不失衡）。
- 旋钮：`DECORD_HYBRID_REPLAN_PCT`（阈值 %，**未设=关闭**）、
  `DECORD_HYBRID_REPLAN_GAP`（最小间隔，缺省 8）。
- 机制生效证据：PCT=10 下 chunks 96→85→32→20、份额 0.34→0.28→0.32→0.26，
  **段数不变（2101）**；金标 **28/28**（PCT=25 开启状态下复核）。

## 四、判读：为什么 h264 反向
- **hevc/av1**：GPU 腿显著快于 CPU 腿（2118 vs 909 / 1762 vs 1292），计划份额
  ≈0.28；运行中 GPU 落地速率一路走高（+28%）⇒ 冻结计划把太多块留在慢腿，
  重建后跟着实测走 ⇒ **−5.42%**。
- **h264**：CPU 腿反而快 3.7×（3701 vs 998），计划份额 ≈0.79；而**混跑时的实测
  CPU 速率含自我争用**（软解线程与喂包/消费线程抢核）⇒ 重规划把份额往 GPU 挪，
  对 h264 是错的 ⇒ **+1.11%**。
  这与工作项 2 的失败同源：**"运行中实测的速率"在本混跑结构下不是干净的产能估计**。

## 五、结论与处置
- **保留为 opt-in**（默认关）。它是本项目第一个**可选的、有实测正收益**的 fork 旋钮：
  hevc 全片 −5.42% 已经拿到手。
- **不改成默认**：它在 h264 上是真回归（+1.11%，符号 6/6），默认开会在 h264 上
  倒亏；而"按编码开关"需要一个能判"哪条腿快"的可靠信号——那正是工作项 2 卡住的地方。
