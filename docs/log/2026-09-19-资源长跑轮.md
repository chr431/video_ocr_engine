## 3. 显存泄漏：一处已修 + 一处待专项

### 3.1 已修：池 GC 兜底被切断（审查轮修复引入的回归）

**现象**：长跑 40 轮 CUDA 显存 +24 MiB（+1.0 MiB/轮，无收敛）。

**定位链**（每步都有实测）：
1. 分配点追踪：**253 次 `cudaMalloc`/轮**（每次 3498 B = ROI 帧大小）
   全部来自 `video_ocr_engine/gpu/device.py` 的 `_YFramePool._malloc_frame`
   ——即池**每轮都在新建**而非复用。
2. 池自身复用逻辑正确（10 次 acquire/recycle 零新增分配）。
3. 真因：**审查轮（da70772）为"防双入列"把 `recycle()` 改成置空
   `frame.pool`**——而大量池帧是随 payload **跨线程传递、只靠 GC 回收**的
   （见 `gpu_backend._similar_device` 注释），`pool` 一置空，它们的
   `__del__` 撞 `None` 被 `except: pass` 吞掉 = 永久泄漏。

**修复**（本文件所在提交）：防双入列改用 `_recycled` 标志位，
**保留 `pool` 引用**；`acquire()` 复用前清标志。回归钉子同步更新
（`tests/test_review_round_fixes.py` 两条用例改写为锁定"循环复用不新增分配"
这一最终判据）。

**验证**：反向对照（注入旧顺序）**+1.0 MiB/轮** vs 修复后……见下节。

### 3.2 待专项：TRT OCR 路径 +0.9~2.0 MiB/轮残余

**现状**：修复池问题后，长跑仍有 **+0.9~2.0 MiB/轮**（40 轮 +23 MiB，无收敛）。

**已完成排除**（每项都是独立实测）：

| 假设 | 测法 | 结果 |
|---|---|---|
| 池内部泄漏 | 同进程 acquire/recycle 循环 | ❌ 零新增（复用正常） |
| TRT 引擎内部 | 同一引擎 15 次推理 | ❌ 1410 MiB 恒定 |
| 引擎构造/释放 | 8 次 `OcrEngine` 创建→release | ❌ 每轮回到 1082 基线（净 −326） |
| 引擎含推理后释放 | 同上 + 一次真实推理 | ❌ 同样零净增 |
| 池复用语义 | `acquire_ocr_engine`→推理→`checkin` ×10 | ❌ 1410 恒定 |
| GPU 分析器 | `GpuFrameAnalyzer` 创建/release ×10 | ❌ 1082 恒定 |
| kernel 模块缓存 | 进程级 dict（复用，非累积） | ❌ |
| 解码侧 | NVDEC/hybrid only（ocr=cpu）×8 | ❌ 1084 恒定 |
| OCR 后端对照 | **OV-OCR vs TRT-OCR** | ✅ **TRT +2.0/轮，OV 零** |
| 桌面合成干扰 | NVML vs CUDA runtime 口径 | 已改用 CUDA runtime 口径 |

**追加排除**（本轮末段）：
- CUDA stream 创建/销毁（含"创建不销毁"对照）×20 → 零增长（排除流泄漏）；
- 清空引擎池后重跑 → **泄漏仍在**（+0.67 vs 默认 +0.89），且基线低
  354 MiB → 与池内引擎无关，泄漏在**每轮重建的管线侧**；
- 泄漏率与是否清池弱相关（差值 0.22 MiB/轮，在噪声量级）→ 单一来源。

**结论**：泄漏在 **TRT OCR 的管线组合路径**（TRT 特有——OV-OCR 零泄漏），
但**只在完整 extract 组合下出现**：所有独立组件（引擎、池、analyzer、
preprocessor、流、模块缓存）单独测试均干净。指向
`_gpu_release_partial` ↔ `checkin_ocr_engine` 的**交互**，
或 TRT `IExecutionContext` 在动态形状下的内部缓存累积。

**量级评估**：+1 MiB/轮 ≈ 每 1000 轮 1 GB。对批量剧集（数十~数百轮）
影响可忽略；对**常驻服务**（数千轮）需修。

**下一步建议**（留给专项）：
1. 在 `_gpu_release_partial` 与 `checkin_ocr_engine` 前后各打一次
   `cudaMemGetInfo`，定位是"释放前就没释放"还是"释放本身不生效"；
2. 用 `cuda.core` 的 memory pool 统计（或 `torch.cuda.memory_summary`
   式 hook）看是否 CUDA 分配器缓存增长；
3. 检查 TRT `IExecutionContext` 是否为每个新 shape 分配 workspace
   且旧的不释放（引擎内 `_out_shape` 恒定，但 `set_input_shape`
   可能按 batch 维缓存多份）。

## 4. 内存（RSS）检测

- 40 轮 RSS **锯齿**（涨到 847 后回落 661，再涨再落），**无净增**；
- 反向对照（旧池顺序）RSS +8.9 MiB/轮（与显存泄漏同源——池帧对象
  泄漏同时钉住 Python 侧引用）；
- 结论：Python 侧无独立泄漏，RSS 波动是分配器缓存行为。
