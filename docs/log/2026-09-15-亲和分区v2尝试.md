# 2026-09-15 亲和分区 v2 尝试：按名识别落地但方向整体判死

> 命题（用户）：hevc 解码独绑（decode 8.4s > OCR 6.9s），亲和分区重做
> （层2 已知故障=差分错钉 CUDA 线程 → hevc 10fps 灾难）能否兑现收益。

## v2 方案（已实现，patch 留档 decord/ab/affinity_v2.patch）

发现 FFmpeg 9 帧线程自带命名（pthread_frame.c:185 ff_thread_setname →
SetThreadDescription，格式 `av:<codec>:df<idx>`）→ **按名识别**取代差分
无差别钉：`PinFfmpegThreads` 与 Start 差分块改为只钉 `av:` 前缀线程
（31/58 命中，27 个 CUDA 线程正确排除），PinRemaining 排除未识别线程。

## 结果：钉核动作本身即触发供料停摆（五数据点穷尽）

| 配置 | hevc hybrid 结果 |
|---|---|
| 不钉（默认） | 0.46s/600帧、8.6s 全片——正常 |
| v1 全钉 58 | 10fps 灾难（层2 已知） |
| v2 按名钉 30/31 + 存量钉 service | **全零卡死**（idle rdy=0 crdy=0 q=0 刷屏） |
| v2 按名钉 30 + 存量不钉（PINOFF） | **全零卡死**（同上） |
| 块空转（X0，无任何钉） | 仍钉——**真凶=PinFfmpegThreads（401 行独立重钉函数，Start 块外的第二处差分）**，初次排查漏判 |

v2 最终形态（PinFfmpegThreads 也按名化）仍卡死 ⇒ **任何 SetThreadAffinity
动作（哪怕只钉正确识别的帧线程）都触发供料泵停摆**——障碍在钉核与
供料泵/解码器线程交互的深层，非"钉谁"的识别问题。机理未定位
（候选：亲和切换触发内核调度/内存分配路径变化与泵的条件等待互锁）。
