## B 暴露的功能性缺陷（阻塞项）

release 构建在 NVDEC ctx + `output_format='yuv420'`（CropRoiYuv420）必挂：

```
video_reader.cc:1044 Check failed: err == 0 (3 vs. 0):
cudaMemcpy2D failed in CropRoiYuv420 (Y)
```

定位链条：shim `Err()` 把所有驱动错误折叠成 3（cudaErrorInitializationError），
`DECORD_CUDART_DEBUG=1` 显示真实驱动错误为 **201（CUDA_ERROR_INVALID_CONTEXT）**；
裸 ctypes 复刻实验（绕开 decord）证实：nvcuda.dll 的 **v1 导出 `cuMemcpy2D`
在现代驱动/UVA 下恒返回 201**，而 `cuMemcpy2D_v2` 完全正常（H2D/D2H 往返
数据校验通过）。shim 的 X-macro 里 MemAlloc/Memcpy 全系用 `_v2` 导出，
唯独 2D 拷贝漏了。修复三处：`nv_gpu_dyn.cc` X 条目、`nv_gpu_dyn.h` 声明、
`cudart_shim.cc:238` 调用点。修复前 gray 路径不受影响（走 `cuMemcpyDtoH_v2`）。

排错过程中的两个岔路（记录防重踩）：
- 宏体内插中文多行注释 → MSVC 在 GBK 代码页下吞掉 `*/`，宏断裂报
  C2061/C2065 级联。宏体内注释用 ASCII 单行且行尾带 `\`。
- 0.8.1 起 CMake 硬性要求 FFmpeg 9（`ffmpeg_common.h` #error）：FFmpeg 7/8
  支持被删（跨版本关键帧索引与 seek 落点正确性，fork 内 D4 决策）。
  本地重编需 BtbN n9.0 shared 构建（含 .lib/include）。

## 追查轮（同日）：av1"seek 变慢"翻案 + 引擎 av1 线程策略修正

上表的 av1 seek 数字（CPU 339→660ms 等）是 **NT=4 探针口径**的结果
（`probe_decode_rates` 硬编码 `num_threads=4`）。分解探针
（`tools/_ab_decord081/_probe_seek_decomp.py` / `tools/_ab_decord081/_probe_seek_sweep.py` /
`tools/_ab_decord081/_probe_seek_landing.py`）翻案：

1. **seek 本身两构建完全一样**：`seek_accurate` 是同步前向解码（耗时
   ≈ 2.6ms/帧 × 关键帧距离 + demuxer seek ~50ms），旧/新 dll 斜率相同；
   NT=16 下 8 片扫掠 seek 合计 1.47s vs 1.49s。取帧几乎免费（落点校验
   把帧还给后续读取）。FFmpeg8/9 的 av1 包级关键帧标记也完全一致
   （ffprobe 各 80/23970 个 K）。旧 dll 落点 12/12 像素级正确。
2. NT=4 下新构建 read64 慢 5× 的现象，随线程数上升单调消失——
   **FFmpeg9 的 dav1d 帧线程扩展性大幅改善**：顺序解码 NT16 797fps →
   NT24 1164fps → NT32 1178fps（饱和）。
3. 引擎 av1 线程策略是 FFmpeg8 时代口径：`cores//2`（本机 = 8 线程），
   依据"av1 吞吐不随 FFmpeg 帧线程数扩展（8/16/24/32 全 5.8~5.9s）"——
   那次实测被 OCR 墙钟掩盖（OCR 受限时段内解码线程数自然不可见），
   且 FFmpeg9 已不再成立。

### "fork 分支单独实验的提升为何引擎口径没复现"的答案

fork 的基准（decord 仓库 tests/ 下的 bench_hybrid_gpu.py 等）测的是**纯解码吞吐**
（get_batch 循环、无 ROI、yuv420 全帧、顺序从 0 读、线程 = fork 默认
hw/2=16），发布表里的 1938/1756/1796 fps 是这个口径；引擎 e2e 是
**管线墙钟**（解码+分段+OCR+D2H），且引擎传自己的 ROI / 线程策略 /
stride 窗口。三个具体原因：

1. **瓶颈错位**：fork 提升集中在解码供给率（pinned 帧池消 D2H、NV12
   直出、调度器），而引擎墙钟由 OCR/分段阶段共同决定，解码供给已达标时
   供给侧提升不进墙钟（同 C-10 的"流水发射零收益"机理）。
2. **参数不同**：fork 口径不带 ROI 全帧解码；引擎恒带 ROI 灰度/裁切，
   转换与拷贝路径完全不同；batch 64 vs 250；线程策略引擎自有分档。
3. **一个真被埋没的收益点**：FFmpeg9 dav1d 的线程扩展性提升被引擎
   FFmpeg8 时代的 av1 线程策略（8 线程）挡住——策略修正后 CPU 后端
   −50%、hybrid 反超基线，fork 侧的提升在引擎口径下兑现了。
