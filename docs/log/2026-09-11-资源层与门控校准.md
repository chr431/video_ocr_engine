## 1. L1 资源差分（std 档即开，纯 stdlib）

`video_ocr_engine/domain/resources.py::ResourceProbe`：在粗相位边界
（`open`/`calibrate`/`decode`/`ocr`）各采一次进程级读数、相邻边界做差分，
产出 `report["resources"]["per_phase"]`：墙钟、**平均并行核数**（Δcpu/Δwall）、
活跃线程、RSS 增量、磁盘读写 MB/s、显存占用。

**成本实测决定实现选择**（本机 Windows）：

| 调用 | 单次 | 备注 |
|---|---:|---|
| `time.process_time()` | 0.05µs | 含全部线程 CPU，替代 psutil.cpu_times |
| kernel32.GetProcessIoCounters | 2.5µs | ctypes，磁盘速率 |
| psapi.GetProcessMemoryInfo | 4.6µs | ctypes，RSS |
| `threading.active_count()` | 0.1µs | 线程数 |
| `cudaMemGetInfo` | 0.9µs | 但**首调会隐式建主上下文（100ms 级）** |
| ~~`psutil.Process.threads()`~~ | **43,000µs** | 地雷：逐线程开句柄 |
| ~~`psutil.Process.num_threads()`~~ | **5,100µs** | 同上 |

→ 一次边界 ≈10µs、每 run 4 个边界 ≈40µs。**两颗地雷已固化为测试**
（`test_no_psutil_thread_enumeration_in_product_code`：AST 扫产品代码禁
`.threads()`/`.num_threads()` 属性调用；decord 的 `num_threads=` 关键字不受限）。
CUDA 侧只在**本进程已导入** cuda 绑定时才探（`sys.modules` 查表），宿主路径
永不触发 import/建上下文；不可用的读数一律记 `"unavailable:原因"`，
**不用 None/0 冒充真值**（`sources` 字段逐来源交代）。

顺手修掉一个真 bug：`Metrics.record_span` 的 off 档守卫曾被编辑截成
`return self._check(name)` —— off 档**每次记录都在查注册表**，"一行关闭"
名不副实。现恢复为纯 return，off 档 138 次记录实测 **0.012ms/run**。

## 2. L2 设备峰值采样（full 档专属）

`NvmlSampler`：ctypes 直调 NVML（不新增依赖），~200ms 低采样率、上限 600 点、
**产品路径不建线程**（只在显式 `start()`/`stop()` 之间存在，B6）、关停丢弃
最后一帧半间隔、失败次数计入 `sample_failures`（不静默）。产出
`report["hardware"]`：GPU% / **NVDEC%** / 显存的 min/p50/p99/max。

单次调用实测 0.3–1.7µs（`GetUtilizationRates` 0.3 / `GetMemoryInfo` 1.7 /
`GetDecoderUtilization` 0.5µs）→ 一轮 full 采样的总成本 ~13µs，
**不可能是任何百分比开销的来源**（这点后来把 §3 的排查方向直接钉死）。

**探针不可自嗨**：h264-**cpu** 配置下 `nvdec_util_pct` 必须读 0（实测
min/p50/max 全 0，同时 `gpu_util` p50 7%/max 34% 来自 OCR）——传感器在
"应该没数"的地方给出 0，才说明它有数时可信。

同一会话把 NVML 也用于**环境指纹**：`gpu_identity()` 取代 `nvidia-smi` 子进程
（实测 43.1ms → 20.8ms，且免起子进程），失败自动回退 nvidia-smi 并记
`gpu_source`。这笔开销落在**报告组装路径**上，进程级缓存 → 只有首 run 付。

## 3. 首批真读数（回答过去只能猜的问题）

`h264-cpu / 3000 帧 / TRT`（热轮差分，`tools/_probe_phase_cores.py`）：

| 相位 | 墙钟 | **平均并行核数** | 线程 | RSSΔ | 读 MB/s | 显存 |
|---|---:|---:|---:|---:|---:|---:|
| calibrate | 0.065s | 9.18 | 4 | +267MiB | 967 | 1662MiB |
| decode | 0.953s | **21.21** | 4 | +72MiB | 109 | 1668MiB |
| ocr 尾 | 0.068s | 7.38 | 2 | **−350MiB** | 0 | 1668MiB |

三条直接结论：
- **CPU 软解确实用到 ~21/32 逻辑核** → hybrid 的 CPU 分片必然与引擎自身
  线程争核，C-05 的"引擎吃掉 10–27%"第一次有了机理证据（不是队列、不是
  预取，见 §5 否定结果）。
- OCR 尾一次性**释放 350MiB**（设备侧临时缓冲回收），与 C5 的池释放一致。
- calibrate 相位的 967MB/s 读 = TRT 引擎/首帧数据在冷页上的读取（进程级
  计数器含 decord 的读），不是"引擎自己造出来的流量"。

## 4. PI-15 门控：从噪声门改成可分辨门（用户授权放松）

原门禁：`std ≤ +0.1%`、`full ≤ +1%`，判据是"三档各自中位再相减"。它在本机
**必然**误报，四条实测证据（全部保留）：

| 阶段 | 现象 | 根因 |
|---|---|---|
| a | 同码两判给出 std **−0.50%** 与 **+0.93%** | 三档各自取中位 → 公共漂移没被减掉 |
| b | 固定 off→std→full 时 full 稳定 **+3.32%** | **轮内位置效应**：每轮先跑的那一档系统性偏慢 |
| c | 子进程模式 A/A（同档两槽）\|Δ\|p50 0.24% / p95 2.33% | 解释器/CUDA/TRT 冷启方差 ≫ 被测量 |
| d | 同进程 25 对 A/A 中位 **−1.04%** 但均值 −0.18% | 轮转后差值呈 ±X **双峰**：**中位数落在峰上、均值对消** → 统计量改用均值 |

现门禁（`tools/bench.py telemetry-check`）：
- **同进程交替**（共享热池/OS 缓存，唯一差别是插桩本身）+ 每槽 `inner=3` 次取均值；
- 档位顺序**按轮轮转**（拉丁方）消位置效应；
- **同轮配对差分的均值** + `SE`，判失败需"超阈 **且** 符号多数一致（≥70%）"；
- 阈值由 **A/A 现测**标定，规则写死：`|A/A 均值偏差| + 3×SE` 上取整到 0.05%、
  下限 0.30%。本机标定（n=25、inner=3）：偏差 −0.179%、SE 0.211% → **0.85%**。
- 设计目标 +0.1%/+1% 仍然打印（可分辨时应当达到），但不再当作硬失败线。

**独占机器复测（25 对）**：off 1.2106s / std 1.2096s / full 1.2053s →
std **+0.029% ± 0.291%**、full **+0.140% ± 0.257%**，符号均 13/25（不一致=
噪声内）→ **通过**。注意 std 的点估计其实**优于**原设计的 +0.1%，只是本机
分辨力（SE 0.29%）不足以证明它——这正是"不能证明≠不存在"的口径。

## 5. 严格性没有消失，只是搬到有分辨力的地方

`tests/config/test_telemetry_cost.py`：**直接量插桩路径本身**——按真实
3000 帧 std run 的记录量（9 个 span 键 / **138 个样本** / 10 个 counter /
8 个 gauge / 4 个资源边界 + 一次 `snapshot()` + 一次 `build_report()`）重放
300 次取中位，断言 **≤2ms/run**。分辨力比墙钟高约 10⁴ 倍：真把记录塞进
per-frame 路径会立刻在这里亮灯，而 GPU 热降不会。另含 off 档零成本、
L1 单点 <200µs、`environment()` 缓存生效（首调 <300ms、之后 <50µs）三条守卫。
