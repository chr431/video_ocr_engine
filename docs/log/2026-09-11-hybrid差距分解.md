# hybrid 的差距分解（S6 续轮，2026-09-11）

> 用户点名的方向：**v1 的 hybrid 靠 decord 侧实现，距理论性能仍有很大差距，
> v2 值得引入**。本文件是"入门诊断"——把差距按层拆开、每层给出实测数字与
> 归属，供后续（S5 解码器内联 + fork 侧改造）立项用。方法学同 S6：
> 交错 A/B（`bench ab`）、报告口径、金标 28/28 逐位一致。

## 1. 三层分解法

| 层 | 测什么 | 怎么测 |
|---|---|---|
| **L1 解码器能力** | 纯 `get_batch` 扫掠（无分段/无 OCR） | `tools/_probe_hybrid_gap.py`（同 ROI / gray / 批 64 / 3000 帧） |
| **L2 并行理想和** | 两路吞吐**相加**（并行分摊；不是调和平均） | `cpu_fps + nvdec_fps` |
| **L3 引擎口径** | 真实 extract 热轮墙钟 / `pipeline.decode` | `bench run` / `bench ab` |

`L3 损耗 = 1 − L3/L1(hybrid_gpu)`（引擎消费侧）；`L1 损耗 = 1 − L1/hybrid 理想`（解码器调度侧）。

## 2. L1：解码器能力（3000 帧，本机 7945HX + RTX 4060）

| 视频 | cpu | nvdec | hybrid(宿主) | **hybrid_gpu(设备)** | 理想和 | hybrid_gpu/理想 |
|---|---:|---:|---:|---:|---:|---:|
| h264 (test5) | 3573 | 983 | 3783 | **3052** | 4556 | 67% |
| hevc (test6_hevc) | 754 | 2036 | 1833 | **2116** | 2790 | 76% |
| av1 (test6) | 1112 | 1694 | 2686 | **2174** | 2806 | 77% |

（fork dll `build-081fix`；stock 0.8.2 wheel 对应 2821 / 2311 / 2187）

**三条结论**：
1. **`hybrid_gpu`（设备输出，GPU 管线实际用的 ctx）比 `hybrid`（宿主输出）慢
   19–24%**（h264 3052 vs 3783、av1 2174 vs 2686）；hevc 反向（2116 vs 1833）。
   设备输出路径的上载/池周转是**可指名的优化点**。
2. **调度侧仍差 23–33%**：hybrid_gpu 只到并行理想和的 67–77%。
3. **fork 未发布修复的实际收益**（`DECORD_LIBRARY_PATH=build-081fix` vs stock wheel）：
   h264 hybrid_gpu **+8.2%**、av1 持平、**hevc −8.4%（回退！）** →
   发布前需在 hevc 上复核（fork 的 chunk 预路由/池深改动对 hevc 是负收益）。

## 3. L3：引擎口径与"引擎吃掉多少"

| 配置（3000 帧热轮中位） | h264 | hevc | av1 |
|---|---:|---:|---:|
| nvdec | 3.107 s（966 fps） | **1.528 s（1963）** | 1.818 s（1650） |
| cpu | **0.994 s（3018）** | 4.249 s（706） | 2.898 s（1035） |
| hybrid（**出厂 dll**，改档位后） | 1.384 s（2168） | 1.577 s（1902） | 1.37–1.47 s（区间见下） |
| hybrid（fork dll + ct16） | 1.195 s（2511） | 1.68 s（1786） | — |
| L1 hybrid_gpu | 3052 | 2116 | 2174 |
| **引擎吃掉** | **18%** | **10–27%** | **0%** |

> 口径提醒：`av1-hybrid` 与 `h264-hybrid` 的单次 `bench run` 会给出 8–16% 的
> 轮间散布（分片比例/机器状态敏感），所以**只认交错 A/B 的中位与符号一致性**；
> 上表单点值仅作量级参考（av1-hybrid 在多次独立测量中落在 1.37–1.47s）。

**读法**：
- **av1 hybrid 已经贴着解码器能力跑**（2187 vs 2174，引擎 0% 损耗）——
  S6 的消费端优化（提交并批、窗口自适应、归约异步）正是把这块让开的。
- **h264/hevc 的引擎损耗 10–27%**，与"hybrid 需要 CPU 分片"正相关：
  解码的 CPU 侧与引擎自身的 Python/OCR 线程**抢同一批核**（C-08 早就点出
  这个代价，本轮第一次量化）。
- 因此 **hybrid 的剩余收益分两块**：①解码器调度侧（fork 工作，23–33%）；
  ②引擎侧 CPU 争用（10–27%，可用线程/优先级/分片策略优化）。

## 4. 今天的实测最优路由（本机口径）

| 编码 | 最优 | 次优 | 当前 `auto`（C-08：恒 NVDEC） |
|---|---|---|---|
| h264 | **cpu 0.994 s** | hybrid 1.195 s | nvdec 3.107 s（**慢 3.1×**） |
| hevc | **nvdec 1.528 s** | hybrid 1.577 s | nvdec（已最优） |
| av1 | **hybrid 1.372 s** | nvdec 1.818 s（慢 33%） | nvdec |

> `auto` 恒 NVDEC 优先是**用户刻意决策**（C-08：弱 CPU 上软解可能更慢、
> 且 CPU 解码必带争用/功耗），本轮**不改**——但上表说明：在这台机器上
> h264 走 `decode_backend="cpu"`、av1 走 `"hybrid"` 分别快 **3.1×** 与 **25%**。
> 路由策略属产品决策，留 C-08 复评。

## 5. 本轮已落地的小修

**hybrid CPU 线程档位 12 → 16**（`extractor._open_vr` hybrid 分支）：
交错 A/B 实测 h264-hybrid **−6.5%**、hevc-hybrid **−12.7%**（stock wheel；
fork dll 同向 −3.9%），av1 走自己的分支不受影响。旧档位"核数 3/8=12"来自
项目层 hybrid 时代；据此**取消按 `_decord_has_hybrid_preroute` 的版本门控**，
两分支合并为"核数//2 钳 [8,16]"。金标 28/28 逐位一致。

## 5.1 引擎侧损耗的两条**否定结果**（别再重复试）

引擎吃掉 10–27% 一度看起来像"生产者队列太浅 → 解码器被消费者卡住"
（默认 `buffer_size=128` 帧 ≈ 2 个解码批）。实测（交错 A/B，3000 帧热轮）：

| 变量 | h264-hybrid | hevc-hybrid | 判定 |
|---|---:|---:|---|
| `buffer_size` 128 → 512 | +0.51%（符号 +-+） | **+2.00%（+++）** | 无收益，且更深队列略劣 |
| `GPU_PIPELINE_STREAM` 0 → 1（预取流） | +0.71%（+++） | — | 无收益（与 C-10 一致） |

→ 引擎侧损耗**不是**队列/预取造成；剩余候选是 CPU 争用（解码的 CPU 分片与
引擎 Python/OCR 线程抢核，量级上 Python 每帧 25µs×3000 ≈ 75ms 只能解释其中
约 1/3）与 decord 侧 CPU chunk 上载路径，需要线程时间线级剖析——归入
hybrid 立项（§6）。

## 6. 给后续 hybrid 立项的清单（按性价比）

1. **`hybrid_gpu` 设备输出路径的 19–24% 损耗**（解码器侧）——影响所有
   GPU 管线 + hybrid 用户，是最大的单点。
2. **fork 修复发布前复核 hevc**（当前 fork dll 在 hevc hybrid_gpu 上比
   stock 慢 8.4%）。
3. **引擎侧 CPU 争用**：线程/优先级/分片策略（本机 10–27%）；可先用
   `HYBRID_CPU_THREADS` / 线程优先级做小规模实验。
4. **能力探测取代版本号门控**（v2 §17.4 D-2 `ctx.capabilities()`）——
   本轮实测已撞到它的坑：`DECORD_LIBRARY_PATH` 换 dll 不改包版本号，
   版本门控会给出与实际 dll 不符的判断。

## 7. 动手改 fork：先修掉挡路的死锁（fork `99b8785`）

要拆"混跑损耗"，就必须能用 `DECORD_HYBRID_FORCE_SIDE` 拿到"只用单侧"的反事实
速率——而这条诊断臂**本身就是挂的**：`force=cpu` 下 300 帧即死锁（一次残留
worker 烧掉 735s CPU 仍未退出）。fork 自带诊断给出确切状态：

```
[pop-stall] side=1 crdy=637 rdy=0 head=(side1,0,end=80041,exp=299,em=293) pend=655/7
```

队头 chunk 归 **GPU 侧**、期望 299 帧，但 force 让其余 chunk 全走软解 → 这个
chunk 永不被喂包；**637 帧已上载完成的 CPU 存货排在它后面**（严格的
pts/chunk 保序发射 ⇒ 队头阻塞）；force-close 安全网因 `side_pending_[GPU]=7≠0`
而正确地不敢关它。根因是两处绕过了 `ChooseSide()` 里的覆盖：

1. **Push 的 bootstrap（主因）**：首包无条件 `cur_side_ = SIDE_GPU`（NVDEC
   平价起步的设计），压根不查覆盖 → chunk0 恒归 GPU；
2. **`BuildPlan` 预路由**：按贪心份额自算 side，同样不查覆盖（本例中规划器
   根本没跑——`[hybrid-plan]` 一行未出现——但同一类不一致，一并收口）。

修复：抽出 `ForcedSide()`（未设时返回哨兵 `Side(-1)`），bootstrap、
`BuildPlan`、`ChooseSide` 三处共用。**未设 FORCE_SIDE 时逐字不改行为**（两处
都只是哨兵比较）：非强制 2000 帧 mixed 复测 2833/3077/3041（修复前
2980/2994/3071，落在本机 ±7.7% 漂移带内），且**引擎金标换本 dll 后 28/28
逐位一致**（矩阵含 hybrid 用例）。

### 7.1 修好后立刻拿到的事实：mixed 低于最优单侧

600 帧、每臂独立子进程、两遍取最优（短窗含暖机，只看相对量）：

| 编码 | 纯 NVDEC 臂 | 纯 CPU 臂 | **mixed** | 两臂理想和 | mixed vs 最优单侧 |
|---|---:|---:|---:|---:|---|
| h264 | 920 | **2200** | 1588 | 3120 | **−28%（比纯 CPU 还低）** |
| hevc | **1976** | 898 | 1334 | 2874 | **−32%（比纯 NVDEC 还低）** |

→ **当前"混跑"相对最优单侧是净亏损**（⚠️ 2026-09-12 更正：本表是 EWMA
估计器口径下的产物，"净亏损"很大程度为估计器伪影——见 §8.1 与
`hybrid_cpu_rate_ratchet`，hevc 在诚实速率下混跑**超**最优单侧）。这与 §2/§3 的"hybrid_gpu 只达理想
67–77%"是**两笔不同的账**：前者是混跑本身的调度损耗，后者是调度器距并行理想
的差距。源码注释（`ChooseSide` 顶部，2026-09-07 用户拍板）早已自陈"混跑时
软解与消费/喂包线程抢核致有效供给缩水 + 块交替发射固有损耗……后续优化方向
是压低混跑损耗而非代用户跳过"——本轮把这句话第一次变成有反事实数据的结论。

### 7.2 下一步（按此结论排序）

1. **队头阻塞（首要嫌疑）**：发射严格按 chunk 保序，而 chunk 边界 = 关键帧
   （本机 GOP 实测 ~299 帧 → 一次请求只有个位数 chunk）→ 慢臂的一个 chunk
   卡住快臂已完成的全部存货（`crdy=637` 的巨额积压就是它的直接显形）。方向：
   把**分配粒度**与 GOP 解耦（IDR-like 流允许更细边界），或收缩慢臂队头
   chunk 的期望帧数。
2. **H2D 批次被 `cpu-empty` 打碎**（`UploadStep` 的 `bufs[]` 是栈上局部量，
   队列一空就整条流 sync；观察值 3000 帧 764 次 flush / ~2340 CPU 帧 ≈ 每批
   3.1 帧，设计批 8）。**诚实标注：这条本轮只做了观察、归属未成立**——
   `no-buf=0` 与之相悖，且计数取自开 `DECORD_HYBRID_DEBUG` 的运行（13 万行
   stderr，墙钟 2940 vs 3100 fps，已被打印严重扰动）。重采方式：把计数器
   改成不带打印的 stats getter，再与 `kUploadBatch` 单变量 A/B 对照。
3. **不要动水填充判据**：`ac*rg <= ag*rc` ⇔ `ac/rc <= ag/rg`，即按**时间**
   而非帧数配平，本身是对的；要改的是粒度与发射顺序。

## 8. §7.2-1 落地：估计器才是主账（2026-09-12，fork `75b8602`）

非打印 stats 层（`DECORD_HYBRID_STATS`，热路径零 stderr，析构一次性输出）
+ 三臂矩阵（decode-only 3000f，`tools/_probe_hol_stats.py`）把 §7.2 的
"首要嫌疑"判决翻案了：

### 8.1 队头阻塞不是主因，CPU 产能估计器才是

- 实测 hevc-hybrid（EWMA 计划）：plan rc=2217-3043（真值 ≈754，虚高 3-4x）
  → CPU 臂被分 48-57% → 墙钟被慢臂实时供给钉死；`DECORD_CPU_RATE_DEBUG`
  折率轨迹给出机制：filter 每次从背压封堵脱封，头 1-3 折读到的是**解码器
  预跑存货的排空速度**（r=2491/5390/5981/9138 孤峰），"快升 1.3x/慢降 5%"
  的容量 EWMA 逐峰上抬永久卡 1200-2500 —— §6.2 时代"EWMA 防混跑相位污染"
  的设计选择，把**排空伪影当成了产能**。
- HOL 计数器（时长/episode/对侧搁置峰值）显示真实队头损失只有 7-25%，
  且大头是错分配的果（GPU 早完成干等：strand_c 实测 1000-1800 帧）。
- 修正口径（`DECORD_CPU_RATE_SUSTAINED=1`，滑窗 8 折内"连续 4 折最小值"
  的最大值 + 0.997/折慢降锁）：排除排空孤峰（撑不满 4 折）、保留 h264
  真实突发产能（连续 20+ 折；纯中位数会被 h264 饿供相位骗到 rc=995，
  实测否决）。结果：**hevc hybrid 2688-2778 > 纯 nvdec 2036**，达并行
  理想 2790 的 96-99%；av1 持平；h264 −13%（3167 vs 3537，EWMA 的高估
  恰好把 h264 推回"几乎全 CPU"的正确答案——其突发段内含 feed 低谷使
  sustained 只能读 ~2500）。**§7.1 的"混跑净亏损"很大程度是伪影**，
  保留该表的只有 h264 行与 GPU-out 路径；结论已改写进
  `hybrid_cpu_rate_ratchet`。

### 8.2 新发现：hybrid_gpu 倾斜计划死锁（sustained 暂缓默认的原因）

GPU 驻留（引擎 GPU 管线口径）+ sustained 计划在 hevc 上 ~2/8 概率挂死
（EWMA 对照 8/8 慢消费者 + 28/28 全矩阵干净）：

- 签名一：`[pop-stall] head=(CPU chunk, em=124/240) crdy=0 rdy=673
  pend=1080/3394`——CPU 子解码器携千余帧路由中量**停摆产出 0**；
- 签名二：`head=(side1, em=235/240) rdy=0 q=0 pend=538/6`——队头尾 5 帧
  滞留 NVDEC reorder，等待"进不来"的后续包解算。
- 预算/窗口核算排除 `NeedsPackets` 拦包（window≈7470≫在途），方向指向
  CPU 输出缓冲（VideoReader `ndarray_pool_`）在倾斜计划下的回收停摆。
- 份额倾斜只是改变撞窗概率——这是**先于本轮改动存在**的 bug，99b8785
  修的是它的 FORCE_SIDE 变体。复现配方（无需引擎）：慢消费者（get_batch
  + asnumpy 保留）× hevc 全片 × hybrid_gpu × sustained=1。
- 决定：sustained 保持 opt-in；默认口径 = 发布行为（金标 28/28 复验通过，
  本轮实测中 `DECORD_HYBRID_STATS` 层对默认路径零扰动）。

### 8.3 §7.2-2 的账第一次不带打印成立

hybrid_gpu hevc 非打印实测：avg_batch=**1.1**（设计 8）、nobuf=0、
cpuempty≈18k/3000 帧——批次被 `cpu-empty` 打成帧级同步，归因成立；
`kUploadBatch` 单变量 A/B 排入死锁修复之后。

### 8.4 下一步（替换 §7.2）

1. **修 hybrid_gpu 倾斜计划死锁**（签名一优先：CPU 解码器停摆）；
2. 死锁修好后 sustained 转默认 + 引擎侧 e2e 复测（hevc 预期 hybrid 显著转正）；
3. `kUploadBatch` A/B（账已立，见 8.3）；
4. h264 的 sustained 低位（feed 低谷在突发段内）：若要转正 h264，
   需要"分相位"的产能口径（如给 CPU 臂首 chunk 连续喂足再测）——收益
   排序靠后（引擎 h264 走显式 cpu）。
