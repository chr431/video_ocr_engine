# hybrid 的差距分解（S6 续轮，2026-09-11）

> 用户点名的方向：**v1 的 hybrid 靠 decord 侧实现，距理论性能仍有很大差距，
> v2 值得引入**。本文件是"入门诊断"——把差距按层拆开、每层给出实测数字与
> 归属，供后续（S5 解码器内联 + fork 侧改造）立项用。方法学同 S6：
> 交错 A/B（`bench ab`）、报告口径、金标 28/28 逐位一致。

## 1. 三层分解法

| 层 | 测什么 | 怎么测 |
|---|---|---|
| **L1 解码器能力** | 纯 `get_batch` 扫掠（无分段/无 OCR） | `tools/_probe_hybrid_gap.py`（同 ROI / gray / 批 64 / 3000 帧） |
| **L2 并行理想和** | 两路吞吐**相加**（并行分摊；不是调和平均） | `cpu_fps + nvdec_fps` |
| **L3 引擎口径** | 真实 extract 热轮墙钟 / `pipeline.decode` | `bench run` / `bench ab` |

`L3 损耗 = 1 − L3/L1(hybrid_gpu)`（引擎消费侧）；`L1 损耗 = 1 − L1/hybrid 理想`（解码器调度侧）。

## 2. L1：解码器能力（3000 帧，本机 7945HX + RTX 4060）

| 视频 | cpu | nvdec | hybrid(宿主) | **hybrid_gpu(设备)** | 理想和 | hybrid_gpu/理想 |
|---|---:|---:|---:|---:|---:|---:|
| h264 (test5) | 3573 | 983 | 3783 | **3052** | 4556 | 67% |
| hevc (test6_hevc) | 754 | 2036 | 1833 | **2116** | 2790 | 76% |
| av1 (test6) | 1112 | 1694 | 2686 | **2174** | 2806 | 77% |

（fork dll `build-081fix`；stock 0.8.2 wheel 对应 2821 / 2311 / 2187）

**三条结论**：
1. **`hybrid_gpu`（设备输出，GPU 管线实际用的 ctx）比 `hybrid`（宿主输出）慢
   19–24%**（h264 3052 vs 3783、av1 2174 vs 2686）；hevc 反向（2116 vs 1833）。
   设备输出路径的上载/池周转是**可指名的优化点**。
2. **调度侧仍差 23–33%**：hybrid_gpu 只到并行理想和的 67–77%。
3. **fork 未发布修复的实际收益**（`DECORD_LIBRARY_PATH=build-081fix` vs stock wheel）：
   h264 hybrid_gpu **+8.2%**、av1 持平、**hevc −8.4%（回退！）** →
   发布前需在 hevc 上复核（fork 的 chunk 预路由/池深改动对 hevc 是负收益）。

## 3. L3：引擎口径与"引擎吃掉多少"

| 配置（3000 帧热轮中位） | h264 | hevc | av1 |
|---|---:|---:|---:|
| nvdec | 3.107 s（966 fps） | **1.528 s（1963）** | 1.818 s（1650） |
| cpu | **0.994 s（3018）** | 4.249 s（706） | 2.898 s（1035） |
| hybrid（**出厂 dll**，改档位后） | 1.384 s（2168） | 1.577 s（1902） | 1.37–1.47 s（区间见下） |
| hybrid（fork dll + ct16） | 1.195 s（2511） | 1.68 s（1786） | — |
| L1 hybrid_gpu | 3052 | 2116 | 2174 |
| **引擎吃掉** | **18%** | **10–27%** | **0%** |

> 口径提醒：`av1-hybrid` 与 `h264-hybrid` 的单次 `bench run` 会给出 8–16% 的
> 轮间散布（分片比例/机器状态敏感），所以**只认交错 A/B 的中位与符号一致性**；
> 上表单点值仅作量级参考（av1-hybrid 在多次独立测量中落在 1.37–1.47s）。

**读法**：
- **av1 hybrid 已经贴着解码器能力跑**（2187 vs 2174，引擎 0% 损耗）——
  S6 的消费端优化（提交并批、窗口自适应、归约异步）正是把这块让开的。
- **h264/hevc 的引擎损耗 10–27%**，与"hybrid 需要 CPU 分片"正相关：
  解码的 CPU 侧与引擎自身的 Python/OCR 线程**抢同一批核**（C-08 早就点出
  这个代价，本轮第一次量化）。
- 因此 **hybrid 的剩余收益分两块**：①解码器调度侧（fork 工作，23–33%）；
  ②引擎侧 CPU 争用（10–27%，可用线程/优先级/分片策略优化）。

## 4. 今天的实测最优路由（本机口径）

| 编码 | 最优 | 次优 | 当前 `auto`（C-08：恒 NVDEC） |
|---|---|---|---|
| h264 | **cpu 0.994 s** | hybrid 1.195 s | nvdec 3.107 s（**慢 3.1×**） |
| hevc | **nvdec 1.528 s** | hybrid 1.577 s | nvdec（已最优） |
| av1 | **hybrid 1.372 s** | nvdec 1.818 s（慢 33%） | nvdec |

> `auto` 恒 NVDEC 优先是**用户刻意决策**（C-08：弱 CPU 上软解可能更慢、
> 且 CPU 解码必带争用/功耗），本轮**不改**——但上表说明：在这台机器上
> h264 走 `decode_backend="cpu"`、av1 走 `"hybrid"` 分别快 **3.1×** 与 **25%**。
> 路由策略属产品决策，留 C-08 复评。

## 5. 本轮已落地的小修

**hybrid CPU 线程档位 12 → 16**（`extractor._open_vr` hybrid 分支）：
交错 A/B 实测 h264-hybrid **−6.5%**、hevc-hybrid **−12.7%**（stock wheel；
fork dll 同向 −3.9%），av1 走自己的分支不受影响。旧档位"核数 3/8=12"来自
项目层 hybrid 时代；据此**取消按 `_decord_has_hybrid_preroute` 的版本门控**，
两分支合并为"核数//2 钳 [8,16]"。金标 28/28 逐位一致。

## 5.1 引擎侧损耗的两条**否定结果**（别再重复试）

引擎吃掉 10–27% 一度看起来像"生产者队列太浅 → 解码器被消费者卡住"
（默认 `buffer_size=128` 帧 ≈ 2 个解码批）。实测（交错 A/B，3000 帧热轮）：

| 变量 | h264-hybrid | hevc-hybrid | 判定 |
|---|---:|---:|---|
| `buffer_size` 128 → 512 | +0.51%（符号 +-+） | **+2.00%（+++）** | 无收益，且更深队列略劣 |
| `GPU_PIPELINE_STREAM` 0 → 1（预取流） | +0.71%（+++） | — | 无收益（与 C-10 一致） |

→ 引擎侧损耗**不是**队列/预取造成；剩余候选是 CPU 争用（解码的 CPU 分片与
引擎 Python/OCR 线程抢核，量级上 Python 每帧 25µs×3000 ≈ 75ms 只能解释其中
约 1/3）与 decord 侧 CPU chunk 上载路径，需要线程时间线级剖析——归入
hybrid 立项（§6）。

## 6. 给后续 hybrid 立项的清单（按性价比）

1. **`hybrid_gpu` 设备输出路径的 19–24% 损耗**（解码器侧）——影响所有
   GPU 管线 + hybrid 用户，是最大的单点。
2. **fork 修复发布前复核 hevc**（当前 fork dll 在 hevc hybrid_gpu 上比
   stock 慢 8.4%）。
3. **引擎侧 CPU 争用**：线程/优先级/分片策略（本机 10–27%）；可先用
   `HYBRID_CPU_THREADS` / 线程优先级做小规模实验。
4. **能力探测取代版本号门控**（v2 §17.4 D-2 `ctx.capabilities()`）——
   本轮实测已撞到它的坑：`DECORD_LIBRARY_PATH` 换 dll 不改包版本号，
   版本门控会给出与实际 dll 不符的判断。
