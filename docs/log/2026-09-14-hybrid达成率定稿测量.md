> C-46。

## 1. 此前读数为什么摇摆

同一个 wheel（fef3c4b，dll md5 `6ec5b1ea`）在一天内出现过三个 h264
达成率读数：78%（committed，重设计终验 §8.3）→ 87%（未提交草稿，
gamma 实验轮）→ 91%（`_probe_h264_hybrid.py` 首轮 min-of-3）。三个
根因，全部实证：

1. **分子与分母不同会话、不同构建**：committed 的 95/78/93 用 09-13
   会话（4cebeef 时代）的单臂数字（h264 3701/998 = 4699）配 09-14 凌晨
   fef3c4b 的 hybrid（3650）——除数与被除数隔着一次构建和一天。
2. **外部负载污染**：上一会话遗留的 `_probe_dll_ab.py --rounds 16` 与
   `bench ab` 进程树各吃 12~14 核，同期一切读数作废；`bench/dll_ab.json`
   的 gamma A/B 即受害者（mean −2.0%、SE ±11.7%、单轮摆幅 ±40~50%，
   符号判定 false = 不可判定）。
3. **口径混用**：fps_b（批计时和，剔冷首批）与 wall（含首批端到端）、
   窗口与全片在早期叙事中互换（《2026-09-13-hybrid解码率与理论并联和》
   的五次更正即此史）。

绝对速率的跨会话漂移量级（同探针同机同 wheel）：h264 CPU 单臂
3701→3422 fps_b（−7.5%）、hybrid 3650→4080（+11.8%）——单看任何
绝对速率都不稳，比值才是可迁移量。

## 2. 定稿协议（本轮执行）

- **同会话三臂**：cpu-single / gpu-single / hybrid-default 在一次会话内
  交错测完，比值的分子分母本轮内同源。
- **逐轮交错 + min-of-N**：rep 内臂序正反交替（探针内置）；h264
  min-of-6、hevc/av1 min-of-4。
- **每臂独立子进程**：避免同进程顺序伪影（续五的教训）；fps_b 与 wall
  双口径分记账，达成率分子分母同口径。
- **污染门**：每臂前后采机器忙闲（psutil），>40% 当轮作废重试（默认
  3 次）；启动前扫外部重负载进程树（本轮启动时 6.4%，无遗留进程）。
- **线程 = 引擎生产档**：h264/hevc 32、av1 24（`_decode_num_threads` 的
  TRT 分档：`DECODE_THREADS_GPU_OCR_MAX=32`、av1 逻辑核 3/4 钳 24）；
  ROI-first + gray + DECODE_BATCH 粒度，与 `_probe_gap_decomp.py` 同口径
  （C-45/C-46 数字互认）。
- **被测对象 = 发布 wheel**：decord 0.8.3（dll md5 `6ec5b1ea` =
  fef3c4b），不设 `DECORD_LIBRARY_PATH`。fork 本地 `72237ad`（gamma）
  与其后的死区 WIP **不在**被测面内（见 §5）。

命令：`_probe_h264_hybrid.py --codec <c> --reps {6,4,4} --arm
cpu@cpu-single --arm gpu@gpu-single --arm
hybrid_gpu:t{32,32,24}@hybrid-default`；逐轮读数
`bench/hybrid_ratio_final.log`，结构化落盘 `bench/h264_hybrid.json`。

## 4. 协议复现性（对「不稳定」的直接回应）

- **同协议复测**：18:58 轮（min-of-3/2/2）vs 本轮（min-of-6/4/4），
  间隔约 30 分钟。达成率 h264 92.40→92.40%（fps_b，Δ0.01pp；wall
  91.3→90.6）、hevc 96.9→96.2（wall 96.3→95.5）、av1 95.3→95.6
  （wall 94.8→95.3）——两轮差全部 **±0.8pp 以内**。
- **会话内逐轮 spread**：单臂 0.0~6.9%，hybrid 4.2~10.1%（移动部件多，
  方差天然更大）——min-of-N 同时压分子分母的右尾。
- 同期绝对速率仍在漂（18:58→本轮：cpu +5.6%、hybrid +4.3%）：
  **比值稳、绝对值不稳**。跨会话对比的可用量是比值；绝对 fps 只在
  同会话内可比。

## 5. 旧数字对账

- **78%（committed）**：分母取 09-13 会话的臂速率（4699）。换成本轮
  同会话分母（4416），同一 wheel 的 hybrid 4080 → 92.4%。缺口主要来自
  分母的会话漂移（−7.5%），hybrid 自身会话漂移（+11.8%）进一步改变
  绝对速率但方向相抵。
- **87%（未提交草稿，归因「gamma 水位」）**：gamma = fork `72237ad`
  （本地构建，未进 wheel）。其报告的 hybrid 速率 ≈4088 fps_b 与**本轮
  无 gamma 的 wheel**（4080）同量级，而其 A/B 证据
  （`bench/dll_ab.json`）被污染判为不可判定（§1 根因 2）；87% 与
  92.4% 之差可由分母的会话漂移（4080/4699 = 86.8%）完整解释。
  「gamma +9pp」的归因因此**当前证据不成立**——gamma 的真实效应需按
  本协议（`DECORD_LIBRARY_PATH` 指 dev 构建、三臂同会话交错）另测。
- gamma 之后 fork 工作区又有未提交的「份额死区 + 服务线程降优先」WIP
  （替换掉 gamma 块）——整条线在途、未发布；验收时沿用本协议。
