# 2026-10-11 争用微观定位轮：CPU 解码 × H2D 共存假设的检验（负结果）

> 用户假设：CPU 解码从未吃满整机（hybrid 内 CPU 臂大量闲置）→ 应存在让
> CPU 解码与 H2D 上载共存而互不影响的方法。本轮按 C-66 开出的修法方向
> （比例预留/再平衡）实施并实测——**负结果**：该方向在现粒度下结构性
> 不可行，已撤销；判据面结论见 C-68（同时修正 C-66 的修法候选）。

## 1. 实施的两个变体（fork pump/budget，均经 rebuild+矩阵验证）

- **v1 逐遍配额 + f_eff 置信折扣**：未熟期（双侧交付 < 2×GOP 均长）每遍
  扫描只派 1 chunk；份额 f 按置信拉向 0.5 先验。实测 h264 hybrid 掉到
  **1008fps ≈ 纯 nvdec**——配额把派工节流到扫描遍的触发节奏（消费事件），
  双臂在途时 hold 连同空侧一起饿。
- **v2 空转再平衡优先**：任一侧 pending=0 直接派空侧（kick 承接换侧），
  配额只在双侧都在途时生效。h264 仍 1008、hevc 反降至 −19.3%。

## 2. 分配账本揭示的真机制（v2 带 STATS 实测）

```
chunks c=7 g=3   assigned c=2100 g=900（=70%，接近最优 72%）✓
kicks c=2 g=3（=5 次换侧）✗
busy cpu_us=0.83s gpu_us=0.56s / wall 1.79s——双臂各闲置一半
cpuempty=2885（换侧等待期 CPU 臂输入空轮询）
```

**分配比例本身可达标，但每次换侧 = 离场侧 IDR 冲刷 + 重排窗重填
（~50 帧），5 次换侧的切换税 ≈ 分配收益**。三码对照（vs 基线
−5.6/−32.5/−33.9%）：v1 −16.3/−71.4/−40.3%，v2 −19.3/−71.5/−40.8%
——全劣。GOP 粒度 300 帧 × 窗 3000 = 仅 10-12 个可分单元，最优分配
需要在流序里交替两侧 → 每次交替一对 kick → 税随交替次数线性涨。

## 3. 处置与推论

- **撤销**：pump.cc/budget.cc 全部还原到已提交态，rebuild 后 h264 hybrid
  恢复 2222fps（会话噪声内）；矩阵 ×5 在修复态验证过位级无损（说明
  改动本身正确实现了意图——是方向错，不是实现错）。
- **C-68（负结果入账）**：比例预留/再平衡结构性不可行；C-66 的
  "修法候选" 同步更正。收益路径收窄为：亚 GOP 派工（fork 重设计级，
  未立项）或无 kick 双臂管线。
- **用户假设的部分成立**：CPU 解码与 H2D 在**计算层**确实共存无害
  （10-09 已证每帧周期成本不变、绑定实验 +4.3% 无退化）；当前缺口
  不在"共存"，在"派工粒度 × 切换成本"。h264 在臂 −26% 税中 GPU 侧
  （TRT×NVDEC 同卡）归 C-60（MPS/异卡触发）；宿主侧修法（pinned
  上载缓冲、上传线程亲和）未测——列为下轮候选（engine 侧，独立于
  fork 粒度问题）。

## 6/7. 追记（同日第二轮）：H2D 争用实测与供给上限闭合（C-69）

用户指令"实际测量并解决 H2D 争用"。测量链：

1. **H2D 路径代码事实**：H2D 源 = `np.ascontiguousarray(batch_luma(crops))`
   ——**ROI 裁切**（~105×32 ≈ 3.4KB/个），pageable（普通 NumPy）；
   3000 帧窗总上载量 10-30MB——**带宽与页锁化均非可测因素**（原假设
   的整帧 H2D 不存在，引擎是 ROI-first）。
2. **逐执行器归因**（contention_map --hybrid-gap --video h264）：三臂
   consumer/ocr/infer 单位成本持平；外来簇/帧 9.5M vs 纯臂 14.2M×0.94
   ——**无计算争用税**；duty：cpu 纯 17.2 核 / hybrid 11.3 核（未吃满）；
   up_cempty=2296、双臂各空转 0.4/0.2s——**墙钟 1.17s ≈ 3000/1.17 =
   2564fps = 供给上限形态**。
3. **供给上限实测**（tools/_probe_hybrid_supply.py，无 OCR 直读）：
   h264 3011 / av1 2770 / hevc 2899 fps。双臂胃口（理论和）超供给
   h264 24% / av1 10% / hevc 3%。引擎内 TRT-OCR hybrid 再损失 13~16%
   （消费耦合：consumer 等帧 ≈ 全墙钟、OCR/调度 Python 线程参与）。
4. **E-B 判别臂失效说明**：hybrid+OCR=cpu 被 OV 产能封死（1516fps），
   不能用于供给判别（负结果记录）。

**处置**：修法分两级留档（本轮预算内未实施）——①fork 供给线并行化
（demux/parse 与 push 分线程，pkt_cache 512MB 预算余量充足）；②engine
消费解耦（OCR 队列化/Pop 重驱降频）。①后 h264 hybrid 理论顶 ≈3011
（缺口 -32.5%→-19%）；①+② ≈3300（→-11%）。"解决 H2D 争用"的原命题
按实测更正：H2D 无争用可解，瓶颈在供给与耦合。

## 8. 追记（第三轮）：两档方案执行情况

- **Tier-1（fork 供给）落地一半**：串行化根因定位到**按序合并 × 浅前视**
  （FORCE_SIDE 分臂：cpu 2806/gpu 2745 vs 均衡 2787 = 串行和；queue_frames_
  384 ≈ 1.3 GOP 前视）。修复 = CPU 侧前视 384→1536（RAM ~5MB）：h264 纯
  双臂解码供给 2787→**3358fps（+20%）**，矩阵 ×5 位级全过，fork 0.9.3。
- **Tier-2（engine 消费解耦）未动**：批尺寸旋钮先被证伪（B=64→256 引擎内
  仅 +3.3%，低于会话噪声）——真正的 Tier-2 靶点是引擎 GPU 管线内部
  （引擎 decode 相位 2541 vs 供给 3358，设备分析/同步/消费节奏），下轮。
- **结论**：供给上限已解除（3358 > 胃口修正后的约束），引擎内 h264 hybrid
  2087（本会话整体偏低）——下一增量在引擎侧。
