# 2026-10-09 纪律松绑轮：摩擦拆账 → 自动化/分层/降级三路处置 + CI 看门狗

> 用户裁决：上轮大量时间耗在金标与文档审计上，适当松绑；同时制度化
> CI 检查——CI 跑数分钟、不能每次推送后盯着，红了经常事后才发现。
> 松绑原则（上轮分析结论）：松的是"人工合规于机器可查之事"，不是
> "对机器状态免疫的证据"；正确性门禁一条不减。

## 1. 摩擦拆账（依据 2026-10-08 收口轮实录）

- 审计"跑"的成本近零：纪律 2.1s / INDEX 1.4s / render 0.2s / pytest 27s。
- 真实成本三块：①审计失败后的修复循环 ~25-30 min（conclusions 超预算
  压缩一轮、INDEX 行数三轮对账、悬空引用一处）；②金标全量重复跑
  ~15 min（33 用例 ≈3.5-4 min/次 ×4，其中发布门禁内部重复一次）；
  ③会话编排失误 ~15 min（双跑并发/管道退出码，与纪律无关）。
- 值得注意：INDEX 审计**早就有 `--fix`**——三轮手工对账纯属可用性
  失败（失败输出没指路）。本轮多项"松绑"实为"把已有机能暴露出来"。

smoke 层首跑即红：C-hevc-hybrid `ocr.segments` 差 9 处——全部为
置信度第 3-4 位小数（段/文本/rep 帧全同），**复跑与录制逐位一致**。
对照 2026-10-08 的 F-12（D-h264-w1000，像素稳定、OCR 侧翻动）：
翻动面比首判更广，既有 bit-exact 门禁存在偶发假红（此前多轮全绿

持续翻动）。FINDINGS F-12 已更新。

## 4. CI 看门狗（两仓同款 `.github/workflows/ci-watchdog.yml`）

- 机制：`workflow_run` 在被监视工作流**完成时**触发——零轮询、
  零等待，不占开发节奏。红 → 开 issue（label `ci-red`，GitHub 通知
  即达）；同 commit 重复红为评论去重。主干绿 → 自动关闭全部 ci-red
  issue（附绿色运行链接；分支绿不关主干红）。
- **首跑事故与修正**：引擎侧事件链一次打通（CI 完成 → watchdog
  success）；fork 侧 5 连 `startup_failure`——`workflows:` 名单对
  含斜杠的 "C/C++ CI" 与幽灵 BuildFailed 事件（事件名空、API 可见
  `path: "BuildFailed"`）匹配失败即整 run 标 startup_failure，真实
  完成事件也全军覆没。修正：**事件全收 + job 级 name 门卫**
  （`conclusion` 判定 + `name != 'ci-watchdog'` 排自激）——失配
  只是 skip（中性），不再产生红噪声。
- **第二轮修正（workflows 键必填）**：改"事件全收 + job 级门卫"后
  事件**静默不投递**（v2 推送后两仓 CI 完成均无 watchdog 运行，且
  push 出 0s 校验残根 failure）——`workflows:` 是 workflow_run 的
  **必填键**。终态：恢复过滤键；fork 把含斜杠的 `"C/C++ CI"` 改名
  `Build`（斜杠名匹配不了过滤键）。幽灵 BuildFailed 事件（事件名空）
  会留 startup_failure 记录但零副作用（无 job、无 issue）。
- 本地自检（与 workflow 同命令路径）：gh 建标签/建 issue/#1/关闭
  全通；自检暴露 `--search` 对新建 issue 有索引延迟 → 去重改
  `list + jq contains`（不依赖搜索索引）。
- 注意事项留档：本文件必须在默认分支才会收到 workflow_run 事件；
  GitHub Token 触发的运行不产生事件（防自激）。
