# 2026-09-13 hybrid 解码率 vs 两解码器理论并联和（第一笔）

## 口径
- 三编码为**同内容族**（test6 三件套），ROI 一致（841,994,949,1026），3000 帧。
- 消费端统一 `ocr=trt`，以**隔离解码**（TRT 几乎不吃 host CPU，避免 CPU OCR 与
  CPU 解码抢核污染对照）。
- 指标取 `pipeline.decode` 的 span sum；单臂各跑一次（**非 A/B**）。
- 命令：`SURVEY_FRAMES=3000 SURVEY_CONFIGS=cpu/trt,nvdec/trt,hybrid/trt
  python tools/_probe_path_survey.py`

## 数据
| 编码 | cpu/trt decode | nvdec/trt | hybrid/trt | 理论并联和 | 并联效率 |
|---|---|---|---|---|---|
| h264 | 1.418s（2116 fps） | 3.208s（935 fps） | 1.716s（1748 fps） | 3051 fps | **57.3%** |
| hevc | 3.438s（873 fps） | 1.520s（1974 fps） | 1.598s（1877 fps） | 2847 fps | **65.9%** |
| av1 | 2.460s（1220 fps） | 1.809s（1658 fps） | 1.514s（1982 fps） | 2878 fps | **68.9%** |

（理论并联和 = 两单臂速率直接相加；并联效率 = hybrid 实测 ÷ 理论并联和。）

## 三条读法
1. **并联效率只有 57–69%**：hybrid 拿到两解码器理想和的约三分之二，调度效率
   仍有空间（与 C-39 记的"调度器达混跑理想 94–97%"口径不同，那条是**混跑份额
   兑现率**，本条是**速率相对理论并联和**，两者不可互换）。
2. **h264 上 hybrid 输给单臂 CPU**：1748 vs 2116 fps（−17%）。而 NVDEC 在 h264
   上是硬件天花板（935 fps，C-04 记 982 fps 同级）——故 h264 的"混合"实际是在
   用一条明显更慢的腿拖累一条更快的腿。这与 C-08 记的"h264 CPU 软解快 1.7–2.8×"
   以及本仓路径普查里 `cpu/trt` 优于 `nvdec/trt` 一致。
3. hevc 上 hybrid（1877）也略输纯 NVDEC（1974，−5%）；只有 av1 上 hybrid 反超
   纯 NVDEC（1982 vs 1658，+20%）。**"混合必然更快"不成立，方向随 codec 变。**

全片、min-of-2：

| 编码 | auto（混跑） | side:gpu | side:cpu | 理论并联和 | 效率 | vs 最佳单臂 |
|---|---|---|---|---|---|---|

故 av1 的 CPU 臂速率取自路径普查（1220 fps）。

### ⚠️ 更正三：并联效率的正确分母是「单侧端到端速率」，不是「忙时速率」
先前用 `busy_g=5466 fps` 当分母算出 36% 效率是**错的**——强制 `side:gpu` 显示
GPU 臂在**独占时也只忙 43.8%**、wall 12.80s ≈ 纯 NVDEC 12.69–12.78s，说明
"忙时 5441 fps" 不是可持续速率。改用单侧端到端速率作分母后：hevc 效率 **83.9%**。

### ⚠️ 更正四：`DECORD_HYBRID_FORCE_SHARE` 是**死旋钮**（实测无效）
`BuildPlan(key_pts, cpu_share)` 的分配循环只用 `rc`/`rg`：
`Side s = (ac*rg <= ag*rc) ? SIDE_CPU : SIDE_GPU;`，形参 `cpu_share` **在 fork 源码里
只出现三次**（签名 749 / 声明 .h:495 / 调试打印 799）——**从未参与分配**。
故份额扫描（0.02→0.35）扫到的是噪声：wall 10.82–11.20s（±3.5%）、CPU 包数
6341–7561 基本不动。分配实际由「速率比 + 积压反馈 + 70% 迟滞」决定，且
**规划冻结规划时速率比、运行中不做重规划（fork 内注释自陈 v1 取舍）**。

### 瓶颈定位：host 侧，不是调度器
`ENGINE_PROFILE=1` 分相（hybrid）：

| 相位 | hevc（wall 12.144s） | h264（wall 3.452s） |
|---|---|---|
| producer `decode_batch` | **11.024s（91% wall）** | **2.993s（87%）** |
| ├ `consume_feed` | 3.136s | 1.076s |
| └ `merge_pair` | **2.610s（21% wall）** | 0.939s |
| consumer `q_get_wait` | 10.565s（**87% 空等**） | 2.887s（84%） |
| `ocr.infer` | 6.887s | 2.341s |

- **生产者线程占墙钟 87–91%**，其中近半是 host 计算（`consume_feed` + `merge_pair`）。
- 消费者 84–87% 时间在空等 → 消费侧有大量余量，瓶颈在生产者链路。
- **hybrid 实测速率三码几乎相同（2214 / 2243 / 2257 fps）** —— 与"三编码解码器
  速度差异巨大"（1571–1873 vs 816 fps）形成反差，说明 ~2250 fps 处有一个
  **与编码无关的封顶**，来自 host 生产者链路而非解码器。

### 结论（本轮）
1. hybrid 在**三编码上均快于两侧单臂**（全片口径），用户目标在"更快"这一半已达成；
   "稳定"这一半未达成——3000 帧窗口下 hevc 会输（启动期摊销）。
2. 剩余效率损失（16–30%）**不在份额分配**（旋钮是死的），而在 host 生产者链路
   与慢腿队头阻塞（hevc 的 `hol_c` 1.54s）。
3. 后续优化的靶子（按量级）：hevc 的 `hol_c`、以及三码共有的 host
   `consume_feed`+`merge_pair`（占 wall 21–33%）。

## 深挖（同日续三）："稳定"边界与两处方法论更正

### 窗口曲线（全片=23970/7761 帧；min-of-2，独立子进程）
auto（hybrid）vs `side:gpu`（纯 GPU 臂），win 者为粗体：

| 编码 | w=1000 | w=3000 | w=6000 |
|---|---|---|---|
| **h264** | **auto 1.420** vs gpu 1.638（+13%） | **auto 2.235** vs 3.751（+68%） | **auto 3.240** vs 6.932（**+114%**） |
| **hevc** | auto 1.419 vs **gpu 1.090**（gpu +30%） | 2.079 vs 2.081（持平） | **auto 3.295** vs 3.614（+10%） |
| **av1** | auto 1.286 vs **gpu 1.161**（gpu +11%） | **auto 2.013** vs 2.360（+17%） | **auto 3.207** vs 4.222（+32%） |

**读法**：
- **h264 无交叉点**：hybrid 从 1000 帧起就赢，且优势随长度放大（6000 帧已 +114%，
  全片 +153%）。原因是 h264 的 NVDEC 撞硬件天花板（885 fps），CPU 臂提供的
  增量相对巨大。
- **hevc / av1 有交叉点，约在 1000–3000 帧之间**（hevc 更靠后）：短片下
  hybrid 的启动摊薄不足，纯 NVDEC 反而更快。

hevc 线性拟合（`wall = a + n/r`）：auto r=2394 fps / a≈0.99s；纯 GPU r=1949 fps /
a≈0.59s → 交点 ≈4165 帧。即 **hybrid 稳态快 23%，但多付约 0.4s 启动**。

### ⚠️ 更正五：那个"0.4s 启动"不是 GPU 校准（我的进程内实验有顺序伪影）
先在一**进程内**顺序跑 auto/side:gpu，看到 auto 的 `gpu_calib_total=0.381s` 而
side:gpu 只有 0.084s，误判为"hybrid 多付 0.29s 校准"。
实际 0.381s ≈ C-36 记的 **TRT 反序列化 0.39–0.44s**——**进程级冷启动被第一个
arm 独吞**，与路线无关。
改用**独立子进程**（工具默认方式）重测 w=1000：auto 1.419 / side:gpu 1.090 /
prefetch=8 1.360 / nopinned 1.381 → **那些池与预取旋钮均无效**，真正的差距
仍在别处（未定为单一成分）。

### 结论（至今）
1. **相对纯 NVDEC**：h264 稳赢；hevc/av1 仅在 >约 1500–3000 帧后赢。
   **相对 CPU 臂**：三码全赢（h264 1.10×、hevc 2.76×、av1 1.81×，全片口径）。
2. 因此"任何编码都**稳定**快于单臂"目前**不成立**，缺口唯一且明确：
   **hevc/av1 在短片（≤约 1–2k 帧）上输给纯 NVDEC**，代价来自启动摊薄。
3. 已知不是原因的：份额分配（`FORCE_SHARE` 是死旋钮）、池/预取旋钮（实测无效）。
4. 已知的真约束：host 生产者链路（`decode_batch` 占 wall 87–91%，其中
   `consume_feed`+`merge_pair` 占 21–33%）、hevc 的慢腿队头阻塞（`hol_c`）。

### 建议的下一步（按证据）
- **短窗口启动期**：需要 fork 侧的启动期可视化（`DECORD_HYBRID_DEBUG` 的
  `[hybrid-budget]`/`[hybrid-plan]` 行）才能定位那 0.4s 的具体成分。
- **host 链路**：`merge_pair`（hevc 占 wall 21%）跑在生产者线程，而消费者
  84–87% 时间空等 —— 把合并工作移出生产者线程是结构性收益点。

### 读法与一处方法论说明
- **决策口径取热池**（引擎复用），与既有各轮一致。w=1000 热池：纯 GPU 臂快 **40.5%**；
  w=6000 热池：hybrid 快 **11.5%**（符号 +++ 一致）→ **交叉点被交错 A/B 确认在
  1000~6000 帧之间的 hevc 上**，与窗口曲线的方向一致。
- **冷启动行系统性偏向 B**：w=1000 冷 差 0.383s、w=6000 冷 差 0.309s，两者量级都≈
  进程级冷启动（TRT 反序列化 0.39~0.44s，C-36）。即**每轮先跑的 A 臂独吞进程冷启动**，
  与「更正五」同一机制。故冷启动行的**方向不可用于判据**，只作参照。

### 换算出的启动差（这是"稳定性"缺口的定量形式）
- hevc 稳态混合速率 2257 fps → 1000 帧理想 0.443s；实测热池 0.9992s ⇒ **启动摊销 ≈0.56s**。
- 纯 GPU 臂稳态 1873 fps → 理想 0.534s；实测 0.5947s ⇒ **启动摊销 ≈0.06s**。
- 差额 **≈0.49s**，即 **hybrid 比纯 NVDEC 多付约 0.5s 启动**，在 ≤约 1000 帧的短片上
  直接决定胜负。这与此前线性拟合（auto a≈0.99s vs 纯 GPU a≈0.59s，差 0.40s）互相印证。
## 深挖（同日续五）：启动摊销的根因已定位到 fork 的盲阶段路由（源码级证据）

用 `DECORD_HYBRID_DEBUG=1` + `DECORD_LIBRARY_PATH=<fork build>` 跑 hevc 600 帧，
抓到的前几条调度行：

```
[hybrid-sched] key=240240 rc-unknown -> CPU-sample      <- chunk 0 -> CPU
[hybrid-sched] key=480480 rc-unknown -> CPU-sample      <- chunk 1 -> CPU
[hybrid-plan] k0=3 chunks=97 frames cpu=30 gpu=67 (share=0.32)
```

### 根因
`ChooseSide()` 的盲阶段首判是：

```cpp
if (rate[SIDE_CPU] <= 0) { ... return SIDE_CPU; }   // 采样 CPU 产率
```

而 `rate[SIDE_CPU]`（`cpu_.ProductionRate()`，16 帧段速率首折才就位）在开头**连续多个
keyframe 都还是 0** -> **chunk 0 与 chunk 1 都被判给 CPU**；water-filling 计划直到
**k0=3** 才建立（此后才是 share=0.32 的混跑）。由于交付严格保序，**队头被慢腿
（hevc CPU 臂 816 fps）串行占住**，GPU 臂在启动期几乎无活可干（日志里大量
`[hybrid-u] cpu-empty` 即 CPU 队列空/被窄窗限制）。

### 与代码自述的意图不一致（这可判为缺陷）
同一函数上方注释写的是：

> rc 未学得：给一个 CPU chunk 采样……**该 chunk 与 chunk0 的 GPU 发射重叠，
> 且 GPU-first 下盲决策全落 GPU**，采样安全

即**作者假定首块走 GPU**；但实现里首判返回 CPU，chunk0 与 chunk1 都落 CPU
——**实现与其注释描述的形态相反**，这正是那约 0.5s 启动摊销的来源。

### 拟用修复（源码已试改，但**未重新构建 DLL**）
在 `ChooseSide()` 开头插入首块路由（10 行）：

```cpp
if (chunks_assigned_[SIDE_CPU] + chunks_assigned_[SIDE_GPU] == 0) {
    return SIDE_GPU;            // 首块恒走 GPU；CPU 采样仍由下一块完成
}
```

CPU 采样保留（下一块），与 chunk0 的 GPU 发射重叠 —— 正是注释假定的形态。

**未能落地的原因（工具环境限制，非技术风险）**：重编 `decord.dll` 需经
`vcvars64.bat`（.bat）建立 MSVC 环境，而本会话的指令策略**禁止从 Bash 工具
或 PS 工具调用 `cmd.exe`**（直接调 .bat 只开出交互 shell、不执行）；
且 Windows 会锁住已加载的 DLL，构建必须在无进程持有它时进行。
故本轮**已把 fork 源码回退到 HEAD**（`build-081fix/decord.dll` md5
`2f4c9a1a...` 经校验未变），保持源码与二进制一致，不留"两套真相"。
