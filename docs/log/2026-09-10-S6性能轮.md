# S6 性能轮（v2 §11，2026-09-10）

> 口径声明：本文件是**实验叙事**；结论一行进 `docs/CONCLUSIONS.md`（C-35…C-39）。
> 所有数字来自 `bench/registry.jsonl` 的 RunReport（§8.6 N-4），不是探针输出；
> 每个子项单独 A/B、单独门禁（S6 铁律：禁止把子轮合成一个"性能优化"提交）。

## 0. 基线复测与前置结论（先量后做）

四配置热轮中位（3000 帧窗口，本机 7945HX + RTX 4060 Laptop 8G）：

| 配置 | 实测墙钟 | 实测 fps | 解码上限 fps | 实测/上限 | 绑定侧 |
|---|---:|---:|---:|---:|---|
| h264-gpu（NVDEC） | 3.13 s | 958 | 1013 | 95% | **解码**（硬件天花板） |
| h264-cpu（软解） | 1.13 s | 2655 | 2979 | 89% | **OCR** |
| hevc-nvdec | 1.53 s | 1963 | 2127 | 92% | **解码** |
| av1-nvdec | 1.82 s | 1652 | 1780 | 93% | **解码** |

**判读**：除 h264-cpu 外全部解码受限在 92–95%——S6 能动的只有
①OCR 侧（h264-cpu 的绑定侧、其余配置的尾部）②一次性冷启动成本。
"每帧 Python 翻 C++"的 3–6% 上限（§7.2）依旧不值得投入。

冷启动分解（h264-cpu，进程内首个 extract，3000 帧）：

| 相位 | 冷 | 热 | 说明 |
|---|---:|---:|---|
| `pipeline.setup` | 0.050 | 0.025 | 打开 reader + hybrid_begin + fps |
| `pipeline.calibrate` | 0.50 | 0.088 | **含 NVRTC 编译（首次 0.4s，磁盘 cubin 缓存后 0.09s）** |
| `ocr.engine_init` | 0.41 | 0.00003 | cuda.core 导入 0.22s + TRT 反序列化 0.39–0.44s |
| `ocr.infer` | 1.11 | 1.01 | 1083 段 × 186 子批 |
| `pipeline.ocr_tail` | 0.155 | 0.149 | 解码结束后的 OCR 余量 |
| 合计（wall） | 1.799 | 1.215 | 冷启动多付 0.58s |

**关键结构**：`engine_init` 与 `calibrate` 天然并行（worker 线程 vs 主线程），
所以冷启动的净成本 ≈ max(0.41, 0.50)，不是两者之和；而 h264-cpu 的墙钟
≈ `engine_init + infer + tail`（OCR 比解码慢 → OCR 是绑定侧）。

## 1. 测量底座（S6-0）与"漂移"这个真问题

**同一份代码连跑两次 `bench run`，差值可达 −7.7%**（h264-cpu 1.2567→1.1599s、
hevc 1.6603→1.5329s，均被判"硬失败"）。原因：笔记本 dGPU 功耗/热状态变化
（`nvidia-smi -q -d PERFORMANCE` 累计 `SW Thermal Slowdown 87.7s` / 功率封顶
32.5s）+ 常驻后台进程。**顺序 A 全跑再 B 全跑 = 把漂移记到 B 头上。**

处置：`tools/bench.py ab` —— 每个 variant 独立子进程（含各自预热轮）、
A/B/A/B 交错、逐对符号一致性判读、GPU 状态串记录、组间冷却 8s。
**S6 全部结论以下面这种"符号一致"的形式给出。**

底座本身的门禁：

| 项 | 结果 |
|---|---|
| PI-15 三档互比（3000 帧；**交错 5 轮 × 每档热轮 2 次**） | off 3.1260s / std 3.1296s（**+0.115%**）/ full 3.1272s（**+0.038%**） |
| 金标 28/28（单进程全矩阵） | 通过（重录两次，见 F-9/F-10） |
| 单测 / 审计 | 186 通过 / 21 项审计 0 违规 |

> **PI-15 的 0.1% 阈值低于本机分辨力**（诚实结论，不是豁免）。三条证据：
> ① `full` 记的比 `std` 多，却测出**更小**的开销（+0.038% vs +0.115%）——
> 残差的符号都能翻转，说明它落在噪声里；② 同一实现早前测过 **−0.152%**
> （std 比 off 还快，物理上不可能）；③ 本机噪声底（D10 冷/热轮散布）本来
> 就是 1.3%，交错测量把它压到 ~±0.1%，正好与被测量的量级相同。
> 实务结论：**std 档的插桩成本 ≈0.1%（2.4 µs/帧），在预算内但不可分辨**；
> 门禁按"三档互比"继续跑，判读用 `bench ab` 的交错口径；若要把 PI-15 变成
> 硬门禁，需要先把阈值改成可分辨量级（如 0.5% 预警）——该改动属 §14 决策，
> 本轮不动（不为了让门禁变绿而改门禁）。
>
> 顺带：`telemetry-check` 原实现"三档各自连跑"把机器漂移记进了档位差
> （曾测出 std +0.354% / off 首轮还要付 72s 引擎重建），已改为**逐轮交错 +
> 独立子进程**（与 `bench ab` 同一方法学），并加了子进程间隔（连续起进程会
> 让 TRT 的 CUDA 初始化瞬态失败，见 §7 尾部）。

> 口径警告（F-8）：金标 `--verify` **必须一次进程跑完整矩阵**。单用例单进程
> （冷池）会让前几十段走宿主预处理而非 GPU raw 直通，个别浮点敏感段置信度
> 漂在第 4–5 位小数（段结构 / 文本 sha 不变）。`git stash` 掉 S6 全部改动后
> 现象依旧 → 与改动无关；`tools/_probe_golden_diff.py <case>` 同进程连跑两次
> 可复现"冷≠录、热=录"。

## 2. S6-a / S6-d：**先量后否**（不实现）

| 子项 | 量到的上界 | 结论 |
|---|---|---|
| S6-d 生产者双缓冲（decode∥analyze 重叠） | `decode.stream_analyze` 全 run **0.0105s**（47 批，3000 帧） | 重叠空间 ≤0.35% → **dead**，不实现（省下一处高风险设备缓冲改造） |
| S6-a FrameBatch 引用计数零拷贝 | 宿主路径 `g[k].copy()` ≈ 3.5 KB/帧 ≈ 10 MB/3000 帧（~1–2 ms） | 墙钟上界 <0.2% → **暂缓**；其真实价值是"消灭缓冲覆写缺陷类"（PI-6），需独立立项并配 `frame_batch.leaks` 守卫 |

> 这两条正是 v2 §7.1"算法与 kernel 层已无肉"的量化版：**先量后否**比"改了但
> e2e 无感"（R4/C-33 的教训）便宜得多。

## 3. S6-e：冷启动（显式预热 API；调用点前移**否**）

- **调用点前移（把 cuda.core 预热提到 open 之前）**：交错 A/B 冷启动
  h264-cpu +0.02% / h264-gpu −0.40%（符号混乱）→ **零收益，已回退**。
  原因：TRT worker 本来就与校准并行，0.22s 的 import 已被 0.41–0.50s 的
  校准覆盖，往前挪没有可重叠的新窗口。
- **显式 `FieldExtractor.warmup()`（§7.5 P-b）**：实测（1500 帧 h264-cpu）
  `warmup()` 0.500s → 随后首个 `extract()` **0.798s**（`ocr.engine_init`
  0.00007s、OCR 0.638s），而冷 `extract()` ≈ 1.2s → **首个视频延迟 −33%**。
  总吞吐不变（预热只是把成本提前）——**C-24 的边界照旧成立**，因此本 API
  不自动触发、不改 `extract()` 内部行为，只服务"调用方知道要跑很多视频/
  要稳定首帧延迟"的场景。守卫：`tests/pipeline/test_warmup.py`（池 key 同源
  + 热池 `engine_init <0.1s`）。

## 4. S6-b：keep_crops 的 D2H 并批（保留）

- 改动：设备代表帧的 D2H 从"每段一次 async + 一次流同步"改为**有界窗口
  （16 段）收集 + 每窗一次流同步**；窗口有界是为了不把过多 decord 批 owner
  钉住（PI-5）。
- A/B（1500 帧，交错 3 对）：冷启动 **h264-gpu −2.45%（符号 ---）**、
  h264-cpu −0.16%；热轮 +0.13%/−1.72%（符号混乱 = 噪声内）。
- 判读：收益集中在"代表帧留显存"的 raw 直通路径（keep_crops 段数 495/1500 帧）。

## 5. S6-c：归约 D2H 阻塞拷贝 → 异步（保留）

- 改动：`GpuOutputReducer.reduce` 的两次阻塞 `cudaMemcpy`（隐式**设备级**
  同步，会顺带排干生产者/分析流上在飞的工作）改为 `cudaMemcpyAsync` ×2 +
  本流同步 ×1。守卫 `tests/test_lifecycle.py::test_reducer_d2h_is_async_...`
  用假 cudart 锁死"async≥2、同流同步=1、阻塞拷贝=0"。
- A/B（1500 帧，交错 3 对）：冷启动 **h264-cpu −5.19%（符号 ---）**、
  h264-gpu +0.24%；热轮两侧 +0.2%（噪声内）。
- PI-14 守卫（`tools/_probe_gpu_ctc.py`，test5 2000 帧 stride=1）：
  `GPU_CTC=0` vs `=1` **全段（帧号, 文本, 置信度）逐位一致 OK**。
- 附带抓获并修复一处 **P1-9 类竞态**：`prewarm_cuda_core()` 先发布
  `_CUDA_CORE_PREWARM` 再 `start()`，另一线程会 join 到未启动的 Thread
  （`RuntimeError: cannot join thread before it is started`）。改为持锁
  **先 start 再发布** + `ident is not None` 守卫；8 线程 × 50 次压测 0 错误。

## 6. S6-f：填充率与批/窗口 sweep

- **生产口径填充率 = 40.2%**（1083 段：pad 恒 224 列 × 48 行，内容均宽 90px，
  `ocr.padded_cols` 242,592 / `ocr.content_cols` 97,465）。R5 预估的 79–83%
  不成立于本内容。
- **但 pad 不是可动杠杆**：A/B `OCR_PAD_SMALL` 224 vs 320（+43% 列）
  热轮仅 **+3.66%** → OCR 成本对 pad 宽并不敏感；且 160 已被生产口径证伪
  （误读 150→190，test5 7→26，constants.py:240-266）。故 224 保持（C-15）。
- **`reorder_window` 的"按宽分组"在本内容上是纯负担**：实测（3000 帧，
  交错 4 对，符号 4/4 一致）

  | 对比 | 冷启动 | 热轮 |
  |---|---:|---:|
  | rw1 vs **rw64（原默认）** | **−1.66%** | **−5.05%** |
  | rw1 vs rw256 | — | −11.16%（方向同） |

  原因可证明：分组只可能改变**由内容宽决定**的 pad 宽（R5 的 −23.9% 场景）；
  本 ROI 107×33 的上界宽高比 3.24 < 下限比 224/48 = 4.67 → **任何分组都改变
  不了 pad 宽（恒 224）**，等待窗口剩下的只有代价：推迟首次 flush、拉长
  关键路径、多钉住 decord 批 owner。
- **落地方案（自适应，不做全局默认变更）**：`ocr_stage.effective_reorder_window`
  用"ROI 上界宽高比 ≤ 下限比"这一**可证明判据**把生效窗口收敛到 1；
  宽 ROI（字幕 407×25 → 16.3 > 4.67）与 `force_aspect>0` 场景保留原窗口。
  门禁：金标 **28/28 逐位一致**（批组成变了，但 pad 恒 224 → 预处理逐位同）。
- `OCR_BATCH` 16 vs 32（4 对）：冷启动 −2.96%（符号 4/4）、热轮 −0.82%（3/4）
  → **不改默认**（证据强度不足，且 ONNX 路径的 chunk 语义另有约束）；
  记录为 TRT 用户的调参建议，复评触发见 C-37）。

## 7. S6-g′：TRT profile batch 6→18（本轮最大单项收益）

- **动机（先量）**：`ocr.infer` 的**每子批提交开销**（launch + 归约 kernel +
  D2H + 形状 sync）与 profile batch 成反比；batch=6 时 3000 帧要 181–186 次
  子批提交。微基准（`tools/_probe_trt_maxbatch.py`：同一份 ONNX 构两个
  profile，同批 1116 张走同一条提交路径）：

  | profile batch | 子批 | 1116 张耗时 | 吞吐 |
  |---|---:|---:|---:|
  | 6（原值） | 186 | 0.663 s | 1683 张/s |
  | **18** | 62 | **0.557 s** | **2003 张/s（−16.0%）** |

- **端到端交错 A/B**（`tools/_probe_engine_ab.py`，同一份产品代码、只换引擎
  产物；3 对 A/B/A/B）：

  | 配置 | 旧引擎热轮 | 新引擎热轮 | Δ | 逐对符号 |
  |---|---:|---:|---:|---|
  | h264-cpu（OCR 受限） | 1.0636 s | **1.0013 s** | **−5.85%** | --- |
  | h264-gpu（解码受限） | 3.1012 s | 3.1183 s | +0.55% | +++ |
  | `ocr.infer`（中位） | 0.828 / 0.750 s | **0.555 / 0.565 s** | **−33% / −25%** | — |

  子批数 181→61；`ocr.syncs_per_chunk` 落到 **1.0**（PI-3 对齐的理想态：
  chunk=B 的整倍数且 ≤ max_batch → 每 chunk 仅 1 次同步）。
- **结构影响**：h264-cpu 的 OCR 相位已不再是绑定侧（0.555 s < decode 0.93 s）
  ——**S6 之后四个配置全部接近解码受限**，剩下的量级收益只在解码（S5/S6-g）。
- **对账**：段结构 / 文本 sha **逐位不变**，仅置信度第 4 位小数漂移
  （§8.5 可白名单类别）→ 按 §10.2 声明 + 金标重录；真值匹配率 99.9% 不变
  （FINDINGS F-10）。引擎文件名加 `_b{batch}` 标记，防"改 profile 被旧缓存
  静默掩盖"（首次重建 68s，一次性）。

## 8. S6-f′：NV12 limited→full 展开 LUT（宿主管线）

- **量到的浪费**（§7.3 的第二项）：宿主路径（`GPU_PIPELINE=0`）3000 帧 yuv
  + keep_crops，`decode.luma_batch`（`_nv12_batch_luma_full_out`）**0.090 s**
  = 墙钟 7.7%，且每批分配 B×h×w×4 的 float32 临时数组（107×33 ROI、B=64 时
  约 0.9 MB/批）。
- **做法**：Y 是 8-bit → 展开是**单字节纯函数** → 256 项 LUT（构造期用同一串
  float32 运算建表）替换逐元素浮点；`_nv12_batch_luma_full_out` 与
  `video_utils` 的三个入口共用同一张表（单一出处）。
- **实测**：`decode.luma_batch` **0.090 → 0.052 s（−42%）**；墙钟 1.168 →
  1.135 s（同口径冷/热两轮）。
- **逐位保证**：新增 `test_luma_limited_lut_is_bitwise_exact` 全枚举 256 个
  输入 + 批量/单帧/full-range 三路比对；金标 28/28 逐位一致。

## 9. 录制期发现（→ `tests/golden/FINDINGS.md`）

- **F-8**：金标置信度的冷池/热池敏感性（raw 直通 vs 宿主预处理，F-7 同源）；
  门禁口径 = 单进程全矩阵。
- **F-9**：`meta['report']` 增补使 28 例**只**出现 `calib.meta_keys` 一处差异
  → 按 §10.2 显式声明并重录（重录基准记在 manifest）。
- **F-10**：TRT profile batch 6→18 —— 文本/段结构逐位不变、置信度第 4 位漂移
  （可白名单类别）+ 真值 99.9% 不变；声明 + 重录。
- **F-11**：**金标与引擎产物强绑定**——同 profile 的两次 TRT 构建 tactic 选择
  不保证一致，重建后置信度仍会漂（文本不变）。manifest 现记引擎指纹
  （`文件名@sha256[:16]`），使"代码回归"与"引擎重建"可区分。
