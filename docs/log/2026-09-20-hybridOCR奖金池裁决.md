# 2026-09-20 hybrid OCR 奖金池裁决（R0''）：负结果封板（C-60）

> 问题链：裁切复测轮暴露 CPU 争用 → 用户问"动态分配 CPU + 在线学习是否
> 值得" → 评估结论（同日对话）：负载比例随分辨率/编码/stride 变化大，
> 纯静态分配不够，但对策应是"上下文查表 + 闭环准入"，且立项前先用
> **预注册判据**的裁决实验量化奖金池：B−A ≥10% 立项 / <5% 封板。
> 本轮执行该实验。

## 1. 方法

- **素材**：新三国01 转码 hevc（x265 veryfast crf24，`ffmpeg` 经
  env_probe 解析；73430 帧验证）。注：转码使段数 26462→**48054**
  （crf24 压缩噪声在 ROI 内触发更多分段边界）——与 h264 版绝对值不可
  比，但四臂内部对比不受影响。
- **臂**（`tools/_probe_hybridocr_prize.py`，整集 3 轮交错、臂序轮转）：
  A=nvdec+单TRT（基线）；B=nvdec+双车道（理想门控的静态近似：解码
  全卸 NVDEC，CPU 留给 OV）；C=hybrid+hybrid（现状组合）；D=纯
  NVDEC 解码上限参考（同 ROI 批量拉取，无 OCR）。
- **测量卫生事故留档**：一次会话中断导致两轮探针叠加跑（后台不干净），
  数据作废；清残留进程（含孤儿 worker）+ 静置 10 分钟后从头重测——
  长测量的环境纪律：起测前 `Get-CimInstance` 核对零残留。

## 2. 结果（整集 73430 帧 stride=1，48054 段）

| 臂 | wall（3 轮） | 配对 vs A | 关键读数 |
|---|---|---|---|
| A nvdec+TRT | 65.43 / 65.50 / 65.60 | — | infer 64.3s（98.8% 忙，单车道饱和）；q_wait 0.07 |
| B nvdec+双车道 | 62.16 / 62.49 / 62.30 | **−4.87% ± 0.14**（3/3） | infer Σ 119.5s（双车道 96% 忙） |
| D 纯 NVDEC 解码 | 9.38 / 9.84 / 9.77 | −85% | **7607 fps**：解码=墙钟的 15%，CPU 全空闲 |
| C hybrid+hybrid | **>16 min 未完成** | 判死（>15×） | 首轮观测 16+ 分钟仍在跑，按病理级超时记录 |

正确性：B vs A 文本 **0 / 48054 段差异**（比 h264 上的 3 段还好）。

## 3. 机理：奖金池为何不存在

1. **"CPU 空闲"前提已兑现**（D 臂）——失败不在门控前提，而在双车道
   自身的兑换率：吞吐 747→784 段/s 仅 **+5%**，远低于 C-58 的容量
   理论 +54%（h264 实测 +18%）。
2. 由 infer Σ 119.5s / 墙钟 62.3s（双车道 96% 忙）反推：**TRT 车道
   劣化 ~−28%**（h264 上是 −20%）——争用面已从 CPU 转移到 **GPU 共享**
   （NVDEC 解码流 + GPU 分段/analyze kernel + 双车道 D2H 同卡竞争）；
   叠加 OV 产能=TRT 1/3 的短板。
3. **C 臂病理超时**（>15×）：hevc 稠密段（48054）下 hybrid 解码 CPU 臂
   与双 OCR 三层争用远比 h264（−1.8%）恶劣——"双双 hybrid"组合在
   此类负载上不可用。
4. 瓶颈既不在 CPU 分配（D 证明）、也不在解码——在双车道兑换率与 GPU
   共享。**这不是任何分配策略（静态/动态/学习）能移动的瓶颈**。

## 4. 裁决（按预注册判据）

B−A = −4.87% < 5% → **闭环准入/动态分配/在线学习均不立项**。
C-58 的触发条件（"NVDEC 纯解码 CPU 空闲时双车道会兑现"）**实测不
成立**。用户问题的完整答案：静态分配覆盖可观测变化（codec/stride/
分辨率查表），遥测反馈已存在于 fork 泵；学习器无信息增量；而双车道
本身的容量天花板让"分配优化"失去标的。

## 5. 复评触发

- OV 引擎换代（产能 > TRT 的 1/2）；
- 解码/OCR 分离部署（异卡：GPU 共享争用消失后重估）；
- 多 NVDEC 单元（C-58 原触发）。
