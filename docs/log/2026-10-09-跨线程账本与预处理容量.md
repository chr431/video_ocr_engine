## 1. ThreadLedger 实现（v8，full 档）

- `video_ocr_engine/domain/resources.py` 新增 `ThreadLedger`：进程级「名字→句柄」表 +
  `QueryThreadCycleTime` 采样；`register_thread` 在 5 个创建点登记
  （consumer=驱动调用方线程 / ocr=OCR worker / infer*·每引擎一条 /
  producer=GPU 生产者 / drain=设备排空）。句柄**惰性打开**（std/off 档
  零系统调用，遥测新增只进 full 档）；per_phase 行新增 `thr`（逐线程
  周期差分）与 `thr_duty`（占空=Δcycles/(f_run×Δwall)，等待不计）；
  `cycles_e2e.threads` 线程级全程账本。`REPORT_VERSION` 7→8。
- `bench ab` 判读扩 `cyct:*` 键（full 档 A/B 时逐线程周期差分进表）。

### 1.1 三个实测坑（都写死在代码注释里）

1. **权限矩阵**：按 THREAD_QUERY_INFORMATION(0x0400)/LIMITED(0x1000)
   打开句柄**成功**但 QueryThreadCycleTime 报 ACCESS_DENIED=5；唯
   THREAD_ALL_ACCESS(0x1FFFFF) 句柄可查（自家线程恒可全权打开）。
   伪句柄 GetCurrentThread() 正常。本机 Win11 实证，无文档依据。
2. **死线程 TID 不可再 OpenThread**：句柄须在存活期打开——懒开设计
   依赖"采样发生在 run 边界、引擎线程存活"的生命周期事实。
3. **跨轮陈旧句柄**：进程级账本跨 run 存活，`cycles_e2e.threads` 若按
   首末采样直减会撞上一轮同名死线程句柄（实测 'ocr':0 伪影）——改
   逐相位差分求和。

## 2. 线程占空实测（full 档，test5 600 帧，热轮）

**宿主臂 h264-cpu + OV OCR**（e2e 0.444s，decode 相位墙 0.326s）：

| 线程 | decode 相位 duty | 备注 |
|---|---|---|
| consumer | 0.95 | 调用方线程：拉解码+状态机（q_get_wait 0.298s 与 duty 0.95 并存=decord get_batch 等待中含自旋，两口径各自为真） |
| ocr | **0.20** | 预处理+分批线程；其 busy ≈ preprocess span（0.076s）本身 |
| infer0/infer1 | 0.61/0.64 | OV 推理双实例 |

**GPU 臂 h264-gpu（nvdec+TRT）**（e2e 0.699s）：consumer 0.058 /
ocr 0.015 / infer0 0.112——宿主几乎全闲；NVML p50 **NVDEC 99%**（e2e
被解码绑定，C-49 复证）、**SM 16%**。

## 3. 预处理容量（绑定实验，C-42 纪律：占空≠可回收）

`tools/_probe_prep_headroom.py`：给 `preprocess_standard`（宿主 seam）
注入每 crop N ms sleep，扫 N 找膝点（test5 600 帧 221 crops，3 reps
中位）：

| ms/crop 注入 | e2e(s) | Δe2e% | 判读 |
|---|---|---|---|
| 0（基线） | 0.4458 | — | 当前 preprocess=0.30ms/crop |
| 0.5 | 0.4563 | +2.4% | 近免费 |
| 1.0 | 0.4877 | +9.4% | 开始付费 |
| 2.0 | 0.6974 | +56.4% | 完全传导（+1ms/crop ≈ +0.22s=221×1ms ✓） |
| 4.0 / 8.0 | 1.126 / 2.008 | +152% / +350% | 线性 1:1 |

**宿主臂结论**：膝点 ≈ 额外 0.5-1ms/crop——重算法预算为当前的
**2.5-3×**（总 ~0.8-1ms/crop）。注意：OCR 线程 duty 0.20 曾暗示 ~4×
名义余量，膝点把它修正到 2.5-3×——批边界供给结构（infer 等整批）吃
掉一部分空转，**容量必须绑定实验**（C-42 再证）。

**GPU 臂结论**（推导，未注入）：预处理在设备侧 kernel
（GpuPreprocessor，宿主 preprocess span=0）；SM 16%、NVDEC 99%——
更重的 GPU 增强有 ~5× SM 余量且不动 NVDEC 关键路径；宿主线程 ≤0.11
兜底。上限受 SM/TRT 争用约束（C-47：GPU 链争用主导）。

**接入面**：宿主 seam=`segmentation.preprocess_standard`（C-32 单出处，
本探针即补丁此点验证）；设备侧 seam=`_gpu_kernels.GpuPreprocessor`
（NVRTC kernel，换算法须按 C-32 加真值逐位守护）。先例：预处理六变体
（C-15）就在此 seam 上换过。

**值不值得的边界**：C-15 实测预处理六变体仅一非负——更重≠更准，
容量答案是"支持"，准确率收益须另案真值判定。
