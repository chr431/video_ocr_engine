## 3. 根因与修复（decord 486aeda）

**根因（1 个）**：window_closed 的排空标记在 `gi<0`（本轮扫描无可供
工作）即发出——但 `gi<0` ≠ 已派工作喂完：**被侧容量门挡住的 GOP**
（如 GPU 值日期 `side_pending≥ready_cap`）让扫描无工作可派，而它的
包还没喂。flush 后这些帧凭空丢失 → 消费者等不到窗内帧 → chunk 被
force-close + 提前 EOF → VideoReader 的 EOF-retry 循环长自旋
（`DECORD_EOF_RETRY_MAX=10240`，表现为挂死）或报错（表现为少交付）。
「挂点漂移」假象=assigned 达窗时 delivered 的进度随臂速变化。

修复：排空前遍历 `gops_` 确认**全部已派 GOP 喂完**（`fed_upto==pkt_end`
且 stragglers 尽）才发 flush；容量门由消费推进自然解除（头部 chunk
即被消费），下一轮泵送继续喂完。

**伴生（3 个，修复过程中逐一暴露）**：
1. flush 已发出后禁止一切喂包（Pop 的 force 重驱可再入泵）——否则
   ffmpeg `send_packet after flush` CHECK（Debug CRT 下即 abort 弹窗）；
2. 排空后头部未派 chunk（窗外 GOP，永远无帧）强制移除——否则 marker
   被 `return false` 挡住，消费者静默自旋（pop-stall 取证只覆盖已派
   chunk，覆盖不到这里）；
3. 窗缘 kick 分档保留：目标 GOP 已派（窗内）的 kick 必须注入（缺 IDR
   重锚 → expected 补不满 → 少交付）；越过窗缘的才丢弃。

**配套**：Pop 头部未派时的 `PumpFeed(true)` 强制重驱（库存残帧互锁
解锁）；`DECORD_HYBRID_{HOLD_OFF,TAIL_OFF,RESPLIT_OFF,FORCEREDRIVE_OFF,
TRACE2}` 消融/二分开关（默认全开=新行为）。

## 4. 构建清账：dev 构建一直是 Debug

`rebuild_dev.bat` 从未设 `CMAKE_BUILD_TYPE`，CMakeCache 遗留 **Debug**——
昨日（及更早）全部 dev-DLL 计时跑在**无优化构建**上，Debug CRT 亦是
abort 弹窗的来源。已显式 `-DCMAKE_BUILD_TYPE=Release`（486aeda）。

**口径影响**：三臂（nvdec/hybrid/cpu）始终同一 DLL，A/B 相对结论
（交叉点、判定、±%）内部可比；**绝对 fps 偏保守**——Release 后实测
test5 hybrid 内 CPU 臂 3085（Debug 口径 3436 反而更高属机器状态差异，
不可直接对比）。今日起新测量以 Release 为准；昨日结论无需改判
（全部是同 DLL 配对差分）。
