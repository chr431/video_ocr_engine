# 2026-09-09 多轮深度性能优化（引擎+decord 联调）

目标：在 v0.11.0（71ffb3b）基础上做多轮深度性能优化。铁律：先量后做；
正确性门禁 = 段数 + 唯一文本集 sha（跨运行逐位一致）+ e2e 真值准确率。

## 工具

- `tools/_probe_perf_baseline.py` —— 基线/对比驱动（全矩阵、预热、
  timing 分相、ENGINE_PROFILE、文本 sha 门禁、`--compare`）。
- `tools/_probe_perf_sweep.py` —— 解码参数 sweep（batch/stream/threads/
  hybthreads；GPU_PIPELINE_DECODE_BATCH 为模块常量，sweep 用 monkey-patch）。
- 证据目录：`tools/_ab_perf_20260909/`。

## R2-A codec-aware auto（最大单项：test5 -63%）

实现（extractor.py）：`auto` 打开前用轻量 CPU reader 探测 codec
（`_probe_codec_cpu`，打开即关，(path, mtime_ns, size) 缓存；实测
8~50ms/次），h264 → CPU 软解（GPU 管线 P1-3 分支：CPU 解码 + H2D +
GPU 分段/OCR 零拷贝 OCR），其余 → NVDEC。显式 cpu/nvdec/hybrid 不受影响。

门禁：test5 auto 1.159s（原 3.114s，**-63%**），文本 sha 与 gpu/cpu 路径
逐位一致；test6 auto 1.815s 保持 NVDEC，sha 不变。

## R2-B emit 相位细拆（结论：不值得批量化）

ENGINE_PROFILE 细拆（emit_autocrop/emit_d2h/emit_put）：test6/nvdec
0.118/0.094/0.278s、test5/cpu 0.166/0.010/0.192s。占 wall 15~17%，但
OCR worker qwait 0.6~1.7s 证明消费端有大量空闲 —— emit 批量化
（content_range 每段一次流同步 → 搬进 OCR worker）**不做**（改不了墙钟）。

## R2-C 参数 sweep（结论：默认配置已达优）

- `GPU_PIPELINE_STREAM` 0 vs 1：test6 1.800 vs 1.801s —— **零收益，
  C-10 在 decord 0.8.2 上复确认**。
- 解码批：test6 32/64/128 持平（1.80~1.81s）、256 劣化 1.96s；
  test5 64 最优 1.115s、128/256 劣化。**64 保持**。
- h264 解码线程：8→2.26s、16→1.48s、24→1.21s、**32→1.18s**、48→1.18s
  （平台）→ `DECODE_THREADS_GPU_OCR_MAX=32` 正确。
- hybrid av1 CPU 线程 12~32 全部 ~1.81s（NVDEC 主导）→ 无旋钮可拧。

## R3 sweep 撞出并修复一个先在的设备缓冲越界 bug ⚠️→✓

`sweep batch=32`（test5）触发 TRT `enqueueV3: cudaError 1 (invalid
argument)` + 同配置两次运行段数漂移（1082/1093/1097 vs 1083）+ 文本集
漂移；batch=64 恒正常；128/256 也正常。batch=16/32 均 100% 复现。

根因（`_gpu_prepare_calibration`，P1-3 引入的先在 bug）：
`_DevBatchPool(GPU_PIPELINE_DECODE_BATCH * fnb)` 按解码批定池尺寸，但
校准批 H2D 与 analyze kernel 都按 `calib_n=50 行` 访问 —— 只要
`DECODE_BATCH < 50`，校准批就越界写/读 18 行设备内存，破坏同 context
内其他分配（TRT 工作缓冲），异步错误延迟到 TRT enqueue 才爆出，并污染
analyzer 后续结果（段数/文本漂移）。默认 64 ≥ 50 从未触发。

修复：池尺寸取 `max(GPU_PIPELINE_DECODE_BATCH, calib_n) * fnb`。修复后
batch=32/16 × 8 轮全部 1083/265/dfe2d50b2923，TRT 错误消失。

## R6 并发批量与两个先在 bug

**cuda.core 首导竞态（先在，已修）**：两个 extract 线程同时首次执行
`from cuda.core import Device`（GPU 管线校准）会撞 Python 包部分初始化
竞态 —— 一个线程看到未初始化完的 cuda.core.cu13 命名空间 → ImportError。
nvdec∥nvdec 并发探针稳定复现（文档化的多线程批量场景，引擎池本身支持）。
修复：`_gpu_kernels._cuda_core()` 双检锁惰性导入，进程级一次；三处
__init__ 与 _compile_module 改经此入口。修复后 nvdec∥nvdec 并发跑通。

**OCR 重排窗口自适应（否定结果，未采纳）**：假设"段数不足窗口的短
clips 全部 OCR 压在 tail，缩窗可提前启动"。实测（480/240 帧窗口，w64 vs
w16 vs 自适应）：首轮显示 wall -10~16%、tail 减半，但清洁复测（2 runs×2
轮）收益落入噪声（±20ms，短 clips 的 OCR 总量仅 15~30ms），且 sha 全
一致。按铁律 1 回退，不改行为面。

**并发批量（新 auto 的副产品收益）**（s8 全片 t5∥t6 双线程）：

| 配对 | 总墙钟 | 单视频 |
|---|---:|---|
| 旧 auto：nvdec∥nvdec | 21.78s | t5 15.33 / t6 21.78 |
| 新 auto：cpu∥nvdec | **13.95s** | t5 2.51 / t6 13.95 |
| 顺序 auto t5→t6 | 16.32s | — |

混合编码批量并发**自动互补**（C-01 的 NVDEC∥CPU 格局不再要求显式
`decode_backend="cpu"`；C-07/C-08 已翻 superseded(C-33)）。文本 sha 与
单跑逐位一致。注意：**同编码 h264 批量并发**会争 CPU 解码核（多个 32
线程软解超订），这类场景仍建议错峰或限并发 —— 与 C-01 的会话争抢结论
并行不悖。

## 复盘：本轮什么有效、什么无效

- 有效：codec-aware auto（-63%~-68%，一轮顶全部）；撞出并修复两个先在
  bug（校准批设备缓冲越界、cuda.core 首导竞态）。
- 无效/不必做：emit 批量化（消费端大量空闲）、stream 取帧（C-10 复
  确认）、解码批/线程/hybrid 线程参数（已在平台）、OCR 窗口自适应
  （收益低于噪声）。
- 解码本身已达硬件口径上限（h264 CPU ~3200fps @32T、av1 NVDEC
  ~1800fps），默认路径的墙钟由解码供给决定，OCR/分段/合并全部藏在
  流水线里。

## R7 hybrid 在 0.8.2 上的全面复测（结论：任一编码都不再是赢家）

decord 0.7.x 时代 hybrid 曾在 hevc 上以 1.42× 优于纯 NVDEC（C-05）。
0.8.2 + FFmpeg9 上重测（3000 帧，GPU 管线+TRT，sha 三路径逐位一致）：

| 编码 | 最优单侧 | 最优 hybrid | 判定 |
|---|---|---|---|
| h264 (test5) | 纯 CPU 1.163s | 1.640s（ct=12） | 单侧胜 |
| hevc (test6_hevc) | NVDEC 1.515s | 1.670s（默认 ct） | 单侧胜（**优势反转**） |
| av1 (test6) | NVDEC 1.793s | 1.740~1.806s（ct 无关，flat） | 持平不赢 |

hybrid h264 对 CPU 线程数**单调变差**（12→1.64s、24→1.82s、32→1.92s）：
CPU 侧越快，水填路由把越多 chunk 分给慢侧 NVDEC，墙钟被 NVDEC 份额钉住
—— fork 的水填份额调度（rc/(rc+rg) 积压反馈）保底不恶化，但合成吞吐
敌不过"整个流喂给最快单侧"。av1 flat 的代码层解释：fork 对 av1 有跨侧
交界竞态保护（prefetch 钳 384，见 hybrid_threaded_decoder.cc），调度
开销吃掉了合成收益。decord 冻结，不深改；**引擎结论：auto 的单侧选路
（C-33）即最优，hybrid 保留给显式用户**。C-26 的非 av1 线程分档
（钳 [8,16] → 实际 12）恰为本 sweep 最优。

## R8 TRT profile batch 6→18（判停）

假设：加大 TRT profile batch（6→18）减少 enqueue/同步次数。判停依据：
① 所有推荐路径上 TRT 都有空闲（nvdec av1 infer 占 wall 53%、cpu h264
77%，tail ≤0.14s），收益落不进墙钟；② 唯一接近饱和的是 hybrid 路径
（infer 占 88%），而 R7 已判 hybrid 不再推荐；③ 改 profile 需要引擎
缓存文件名携带 batch 才能失效重建（现名不含 batch → 改常量对存量用户
静默无效），为一个不落地墙钟收益引入缓存版本化，不值。
