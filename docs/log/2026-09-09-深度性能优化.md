# 2026-09-09 多轮深度性能优化（引擎+decord 联调）

目标：在 v0.11.0（71ffb3b）基础上做多轮深度性能优化。铁律：先量后做；
正确性门禁 = 段数 + 唯一文本集 sha（跨运行逐位一致）+ e2e 真值准确率。

- `tools/_probe_perf_sweep.py` —— 解码参数 sweep（batch/stream/threads/

2.2×）；h264 转码版 CPU 1.83s vs NVDEC 3.17s。→ 选路规则：**h264→CPU

的 float32 vs 整数累加差异），门禁按「同路径内 A/B」执行。

## R2-A codec-aware auto（最大单项：test5 -63%）

实现（extractor.py）：`auto` 打开前用轻量 CPU reader 探测 codec
（`_probe_codec_cpu`，打开即关，(path, mtime_ns, size) 缓存；实测
8~50ms/次），h264 → CPU 软解（GPU 管线 P1-3 分支：CPU 解码 + H2D +
GPU 分段/OCR 零拷贝 OCR），其余 → NVDEC。显式 cpu/nvdec/hybrid 不受影响。

门禁：test5 auto 1.159s（原 3.114s，**-63%**），文本 sha 与 gpu/cpu 路径
逐位一致；test6 auto 1.815s 保持 NVDEC，sha 不变。

## R2-B emit 相位细拆（结论：不值得批量化）

ENGINE_PROFILE 细拆（emit_autocrop/emit_d2h/emit_put）：test6/nvdec
0.118/0.094/0.278s、test5/cpu 0.166/0.010/0.192s。占 wall 15~17%，但
OCR worker qwait 0.6~1.7s 证明消费端有大量空闲 —— emit 批量化
（content_range 每段一次流同步 → 搬进 OCR worker）**不做**（改不了墙钟）。

## R2-C 参数 sweep（结论：默认配置已达优）

- `GPU_PIPELINE_STREAM` 0 vs 1：test6 1.800 vs 1.801s —— **零收益，
  C-10 在 decord 0.8.2 上复确认**。
- 解码批：test6 32/64/128 持平（1.80~1.81s）、256 劣化 1.96s；
  test5 64 最优 1.115s、128/256 劣化。**64 保持**。
- h264 解码线程：8→2.26s、16→1.48s、24→1.21s、**32→1.18s**、48→1.18s
  （平台）→ `DECODE_THREADS_GPU_OCR_MAX=32` 正确。
- hybrid av1 CPU 线程 12~32 全部 ~1.81s（NVDEC 主导）→ 无旋钮可拧。

## R3 sweep 撞出并修复一个先在的设备缓冲越界 bug ⚠️→✓

`sweep batch=32`（test5）触发 TRT `enqueueV3: cudaError 1 (invalid
argument)` + 同配置两次运行段数漂移（1082/1093/1097 vs 1083）+ 文本集
漂移；batch=64 恒正常；128/256 也正常。batch=16/32 均 100% 复现。

根因（`_gpu_prepare_calibration`，P1-3 引入的先在 bug）：
`_DevBatchPool(GPU_PIPELINE_DECODE_BATCH * fnb)` 按解码批定池尺寸，但
校准批 H2D 与 analyze kernel 都按 `calib_n=50 行` 访问 —— 只要
`DECODE_BATCH < 50`，校准批就越界写/读 18 行设备内存，破坏同 context
内其他分配（TRT 工作缓冲），异步错误延迟到 TRT enqueue 才爆出，并污染
analyzer 后续结果（段数/文本漂移）。默认 64 ≥ 50 从未触发。

修复：池尺寸取 `max(GPU_PIPELINE_DECODE_BATCH, calib_n) * fnb`。修复后
batch=32/16 × 8 轮全部 1083/265/dfe2d50b2923，TRT 错误消失。
