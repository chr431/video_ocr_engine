## 1. 先纠正上一轮评估的一个错误判断

上一轮答「NVML NVDEC% 能分辨忙闲」——**在本卡上被本轮实测证伪**：
hevc hybrid 的 GPU 臂按自身记账只忙 **35%** 的墙钟，NVML 却全程读
**97-98%**；nvdec-only 臂（100% 忙）读数相同。即本卡（4060 Laptop）的
`nvmlDeviceGetDecoderUtilization` 是「解码器在用」指示器，**不是占空比**。
忙闲判别只能靠 fork 侧 busy 计数；NVML 的真实价值在**时钟与热降原因**
（这两个是新数据，此前热降证据只在 bench harness 的 nvidia-smi 串里）。

## 2. 重评结果（三码全片，引擎口径，GPU 管线+TRT，热轮）

| 码 | nvdec | hybrid | 收益 | CPU 臂（忙占比/有效帧率） | GPU 臂（忙占比/有效帧率） | gpu-head HOL |
|---|---:|---:|---:|---|---|---:|
| h264 | 8.67s | 3.54s | **2.45×** | 58% / 2756fps | 43% / 1620fps | 0.02s |
| hevc | 12.67s | 10.50s | 17% | **91% / 655fps** | **35%** / 4757fps | **2.09s** |
| av1 | 15.23s | 10.59s | 30% | 71% / 1036fps | **42%** / 3655fps | **3.30s** |

设备状态（①的直接产出）：三码全片 SM 2685 / VIDEO 2145-2160 MHz
**全程贴顶**，`ticks_throttled=0`——hybrid 的收益不是靠降频换的，
「本身降速」在当前温度/功率条件下**不存在**。

归因（②的直接产出）：

- **h264**：两臂 58%/43% 忙、HOL 近零——收益 = 甩掉 NVDEC 单元天花板
  （883fps）与快速 CPU 软解（2756fps）的互补，调度损耗可忽略。
- **hevc**：CPU 臂 **91% 忙而只有 655fps**——「忙而慢」的教科书样本
  （hevc 软解服务能力低是绑定侧，非调度不公）；GPU 臂 74% 帧数只忙 35%
  ——「调度闲置」：其份额提前完成 + CPU chunk 独占 demux 期间无包可解
  （gpu-head HOL 2.09s）。与并行理想（23970/(655+~2400)=7.8s）的差
  2.7s ≈ HOL 总量 2.9s——**剩余差距几乎全是串行化/调度闲置**。
- **av1**：与 hevc 同签名（GPU 臂 42% 忙、gpu-head HOL 3.30s 为主要
  闲置项）。

## 3. 方法学记录

- **av1 的 `pkts` 是 epoch 数不是包数**：AV1 批量 send 循环只在首包起表
  （整批算一个 epoch），故 av1 的 busy fps 显示为 0——忙**时**不受影响，
  CPU 臂真实帧率用 `fc/cpu_us`（1036fps）。
- hevc 的 `pkts`(7866) > `fc`(6240)：包≠帧（非帧包/丢弃），臂速率口径
  用 `fc/cpu_us` 与 `pics/gpu_us`。
- 上一轮的「NVML 200ms 粒度」担心被一个更大的事实盖过：粒度再细，
  本卡的 NVDEC% 语义也不支撑忙闲判别。

## 4. 指路（未做）

hevc/av1 的剩余优化空间 = **调度闲置主导**：①BuildPlan 的 rg 学习值
（hevc ~2360）显著低于 GPU 臂提交速率（4757fps）——份额向 GPU 再倾斜
的空间存在；②chunk 边界/demux 单流争用（HOL 的本体）是 fork 侧课题。
「忙而慢」侧（hevc CPU 臂 655fps）是服务能力物理瓶颈，调线程档已到顶
