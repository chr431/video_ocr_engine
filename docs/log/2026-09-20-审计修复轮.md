## 2. 泄漏专项：真根因 = CPython 复活语义 × 池复用（推翻「TRT 特有」归因）

### 2.1 定位链（每步实测）

新探针 `_probe_leak_pinpoint.py`（双层打点，不改产品代码）：
**A 层**=释放边界（checkin_ocr_engine / _gpu_release_partial 前后
cudaMemGetInfo 差）全为 0——泄漏不发生在任何已知释放边界；
**B 层**=全局包 `cuda.bindings.runtime.cudaMalloc/cudaFree` 按调用点聚合
存活量——直接命中：**每轮 ~530 块 × 3498B（ROI 帧大小）分配后永不
释放 = 恰好 +2.0 MiB/轮**。

归因翻案三则（诚实记录）：
1. B 层首版 `site_of()` 从 depth 3 起找引擎帧，**跳过了真正的分配行**，
   把 trt 侧分配误记到 device.py——修正后真凶就是 `_YFramePool` 的
   malloc 位点；
2. 资源长跑轮的「TRT 特有」是**混淆对照**：OV-OCR 对照组根本不走
   GPU 管线（ocr=cpu → 宿主路径），无 Y 池——差异源是管线而非 TRT；
3. 该轮「池内部泄漏排除（acquire/recycle 循环零新增）」成立但无效：
   紧循环里帧永远停靠在空闲列、最终被 release_all 释放——**泄漏需要
   「停靠→复用→最终死亡」序列**，隔离测试构造不出。

### 2.2 真根因（最小复现实测）

```python
class A:
    def __del__(self):
        calls.append(1)
        if len(calls) < 3: keep = [self]   # 复活
# del a → __del__ #1 + 复活；del keep → 二次死亡
# 实测 calls == 1 —— 二次死亡不再触发 __del__（CPython 语义）
```

池的机制撞上这条语义：帧死亡 → `__del__` → 入列 `_free`（**列表持有
引用 = 复活**）→ `acquire()` 弹出复用（对象继续活）→ 最终死亡时
**`__del__` 不再被调用** → 既不入列也不 cudaFree = 每块永久泄漏。
证据链完全对上：每轮 ~516 次 malloc（复用失效=反复新建）、
`release_all` 只能释放从未被复用的块（实测入口列长仅 7）、逐 ptr 对账
2134 块泄漏全部有且仅有一次 `__del__` 记录（死亡时 released 恒 False
= 全部死在中途、非收尾波）、gc 快照存活 _YFrame=0（对象消失而缓冲在）。

### 2.3 修复（两层，均在引擎 `device.py`）

1. **复用换壳**：`acquire()` 弹出停靠帧时新建 `_YFrame` 继承 ptr（新
   对象有全新的 `__del__` 名额），旧对象失能（ptr 清零 + 断池引用，
   `_recycled` 恒 True → 死亡早退不误释）。`_DevBatchPool` 同构同修。
2. **放弃路径直释**：`_recycle` 返回布尔；列满 / 池已 release 时由
   `__del__`/`recycle()` 直接 cudaFree（旧版「告警放弃」在多轮下=
   永久泄漏；`release_all` 置 `_released` 堵孤儿池回收入环）。

### 2.5 探针侧两个盲区修复（同样实测驱动）

- 长跑探针采样口径是 **NVML 全卡**——注入 +10 MiB/轮的泄漏在该口径
  完全不显（资源长跑轮 §1「必须用 CUDA runtime 口径」的教训只进了
  文档没进探针）。改 `cudaMemGetInfo` 优先，NVML 仅回退。
- 探针 `--keep-crops` 默认 False，而 **FieldExtractor 默认 True**——
  探针跑的配置从不启用 Y 池，对池类泄漏结构性盲（反向对照也测不出）。
  改 `BooleanOptionalAction` 默认 True 对齐引擎默认（=泄漏触发面）。
- 反向对照注入从「旧 recycle 顺序」改为「放弃语义模拟」（`_recycle`
  恒返 True 不入列）——旧序注入已被直释修复自然化解，测不出泄漏。

## 3. H2D 聚合（方向二）：机制成立、收益不成立，默认关

### 3.1 实现（fork，UploadStep）

积攒窗：cpu 断流时不立即冲刷，窗内（250µs 粒度重试）等续流攒大批
（批均≈rc×W），批末一次 sync；marker/EOF/池尽仍立即冲刷；等待期释放
池槽。旋钮 `DECORD_HYBRID_UPLOAD_WAIT_US`。对症启动轮 §10 的实测
病灶：批次化骨架虽在（fef3c4b）但批均仅 2.4 帧（cpu-empty 即冲刷），
`UPLOAD_BATCH 8→64 无差`的根因即实际批从未变大。

### 3.2 A/B 裁决（bench ab，臂序轮转+时钟门禁，h264/hevc hybrid 全片）

| 项 | h264-hybrid（test5 全片）| hevc-hybrid（test6_hevc 全片）|
|---|---|---|
| 判定 | 不可判定（偏慢 +2.8%，SE 2.0%）| 不可判定（+0.49%，SE 0.97%）|
| 机制指标 | `q_put_block` **−22.8%**、`consume_feed` **−6.1%**（双显著，符号 0/4 全负）= 聚合确实发生 | 平价 |
| 反作用 | `decode.batch` +3.7%（3/4 正）= 积攒延迟经 HOL 传到解码 | — |

关键发现：**当日 A 臂（旧行为）`ocr.infer` Σ=1.31s 已等于 cpu 路径
水平**——启动轮 §10 的 8.6→14.1ms infer 暴露在本机当日状态没有复现，
A/B 测的是无暴露基线，无收益可兑现。含义：§10「帧上载的执行者与
粒度」的排除法归因**未获干预实验支持**（聚合改变了提交模式而 infer
不动，暴露的驱动另有其物）。裁决：默认改 0=关（新功能默认关纪律），
机制与旋钮保留，暴露复现的机器状态下复评。

另：当日 h264 绝对墙钟波动大（A/B 冷带环境异常对告警；sanity 单跑
3 轮 5.13/4.07/2.41s、散布 51%），判读只用配对差分，绝对值不可比。

## 4. 硬窗界谓词（P2）：审计结论翻案——谓词是防线，fork 有真缺陷

### 4.1 调查过程

fork 侧语义核实：`SetDecodeWindow` 按 `assigned_frames_` 计数、seek
（ResetRouting）清零重计、锚点 GOP 前缀 < GOP 尺寸 ⇒ 数学上可证窗
覆盖安全。据此先删了引擎谓词 `start < 窗长`（晚起点设窗，实测 assigned
1196 vs 无窗 7761=全片喂包）——然后**位级对照翻案**：

| 配置（fork 级，[5000,6000)）| 帧哈希 | 判 |
|---|---|---|
| hybrid seek_acc + 无窗 | `f3eda080…` | **== nvdec == cpu（基线）** |
| hybrid seek_acc + 窗 | `19d77df4…` | **≠ 基线：尾 20 帧损坏**（980~999，其余位级正确）|
| hybrid keyframe-seek（窗无关）| `bc38e868…` | ≠ 基线（另一形态）|
| start=0 × 窗（3000/1000）| — | **0/3000、0/1000 mismatch = 干净** |

引擎级对应：修复前 hybrid+晚起点段数 272（文本哈希 == cpu/nvdec），
设窗后 269（哈希变）——窗口改变的是**帧内容**而非段数口径。

### 4.2 fork 缺陷定性（trace 实证）

`DECORD_TRACE_FRAMES` 取证：POP 止于 5979，其后 RETRY 串（eof=1），
尾 20 帧无 POP 记录 = 由 `FetchCachedFrame` 的 **EOF 容错替补**给出
（VideoReader 把「窗界停喂导致的排空 marker 早到」当 EOF，用缓存帧
替补缺失请求，帧数守恒、像素错）。test5 GOP=50 帧，损坏区 [5980,6000)
= 末 GOP 尾部（迟包在窗界关断后永不送达，chunk force-close 接受缺失）。

### 4.3 处置

- 引擎谓词**恢复**（extractor.py）：`start < 窗长` 是晚起点窗口的唯一
  防线，注释重写为带实测证据的防线说明（不再是「无依据谓词」）；
- `_run_common.begin_reading` / `host_backend` 的 `hybrid_begin` 化石
  注释修正（fork 从未实现该 API；hasattr 恒 False；hybrid 走
  seek_accurate，引擎级 start=5000 实测通过；`_with_dev` 恒 True 对
  fork hybrid(CPU-out) 实测无害——其帧有 to_dlpack、采到 CPU 指针且
  仅 GPU raw OCR 消费，而该组合下 OCR 恒为 CPU）；
- `_probe_window_repro.py` 扩展可选 start 参数（默认 0 行为不变），
  起点矩阵入库；fork 调度修复（迟包供给覆盖已派侧 GOP / 排空 marker
  与真 EOF 区分）留专项轮——冻结后调度改动需专属门禁，未在本轮仓促做。
