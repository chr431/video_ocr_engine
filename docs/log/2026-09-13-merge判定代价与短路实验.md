# 2026-09-13 工作项 1：`merge_pair` 的代价拆解与"短路实验"——结论是不值得做

## 一、代价拆解（为什么不能想当然）
C-42 记的是"段边界的相似判定是引擎生产者链上最重的一笔"（全片 hevc 2.61s ≈ 21% 墙钟，
8340 边界 × 313µs）。**但"span 大"不等于"在关键路径上"**。两条临时插桩
（用完已回退，非产品代码）：

### 拆 1：那次 sync 在等什么？
在 `compare_pair` 之前先插一次 `cudaStreamSynchronize` 并计时（"排空"）：

```
n=2100  排空=0.012s  本体=0.444s  →  每边界  排空 6µs / 本体 211µs
```

**排空只有 6µs** ⇒ 那 211µs 不是"等前面排队的活"（不是与 OCR 线程争 `_stream_c`），
而是调用本身。

### 拆 2：调用本身的 211µs 落在哪？
```
n=2100  Buffer=0.006s  launch=0.238s  memcpy+sync=0.228s
      → 每边界  Buffer 3µs / launch 113µs / memcpy+sync 109µs
```

| 段 | 每边界 | 读法 |
|---|---|---|
| Buffer 构造（3 个 `Buffer.from_handle`） | 3µs | 可忽略 |
| **`cuda.core.launch`（Python 侧打包 8 个参数）** | **113µs** | 可优化：改走原生 `cudaLaunchKernel` 打包缓冲 |
| **`cudaMemcpyAsync`(24B) + `cudaStreamSynchronize`** | **109µs** | 可优化：输出改 pinned/mapped 宿主缓冲，省掉 memcpy |

⇒ 若两项都做完，理论可降到 ~30µs/边界，全片省约 0.4s（6000 帧口径 3.45s 的 ~12%）。

## 二、但短路实验说明：这 0.4s 根本不在关键路径上
把 `_similar_device` 直接短路成"恒不相似"（**零 GPU 调用**；该窗口内 `merges` 实测为 0，
故分段结果与短路前**完全相同**），跑同一配置：

| 运行 | 段数 | wall |
|---|---|---|
| 短路（无 merge GPU 调用） | 2101 | **2.849s** |
| 正常 | 2101 | **2.672s** |

**段数逐位相同（2101）、wall 无改善**（短路臂反而在噪声内偏慢 0.18s，属热漂移方向）。
⇒ merge 判定那 0.49s 的消费者线程时间被**完全隐藏**（消费者 `q_get_wait` 占 84~87%），
把它批量化、换流、或者彻底删掉，**都不会让墙钟变快**。

## 三、结论与更正
- **工作项 1 不值得做**（与工作项 2 同类的"零收益"，但这次是用**上界实验**直接测出来的：
  不是"我实现得不好"，而是"这段工作整体不在关键路径上"）。
- **更正 C-42**：它仍是生产者链上**最大的 span**，但**不是关键路径**；因此以
  "merge_pair 占墙钟 21%"来推算优化收益是错的（那 21% 与解码并发、被消费侧空等吸收）。
- 顺带确认：引擎相对 fork 上限的那 **15%** 差距**不是 merge 造成的**（短路后无变化），
  其成分仍待查（候选：analyze/autocrop 的 kernel 与解码争 GPU、OCR 线程的 preprocess、
  或 hybrid 解码器在宿主侧被消费节奏拖慢）。

## 四、附：本轮量测方法（可复用）
1. 拆"排空 vs 本体"：在调用前插一次同步并计时 —— 一眼分清"争用/串行"与"本调用成本"。
2. 拆"Python 打包 vs 数据往返"：在 cuda.core 调用前后与 memcpy 前后各取时间戳。
3. **上界实验**：把被测工作整段短路（保持输出不变或用不变语义的窗口），
   看墙钟是否跟着降 —— 这是判断"在不在关键路径上"最省事的判据。
