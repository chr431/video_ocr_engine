## 0. 缺口分解（新增 `tools/_probe_gap_decomp.py`）

与工作项 0 的 `_probe_decode_rate.py` 同口径（ROI-first + gray +
DECODE_BATCH 粒度 + 首批丢弃），差异：**全片** + 解析
`[hybrid-stats]`（DECORD_HYBRID_STATS=1）拿到分臂账目（delivered
c/g、busy、plan rc/rg/份额、HOL），把 fork 级缺口拆成三个成分。

**基线 = f42e22e 的全对象干净重建**（varA2，md5 `c45a0ebc`；会话在用
的 `82c62e3f` 与其相差 ≤2%，历史连续性成立——见 §5 构建陷阱）：

| 码 | hybrid 全片 | 两臂单臂 | 并联和 | 效率 | CPU 臂 | GPU 臂 |
|---|---:|---|---:|---:|---|---|
| h264 | 3185 | 3701 / 998 | 4699 | 68% | 2285fps，busy 77%（**23% 闲置**） | 845fps |
| hevc | 2330 | 909 / 2118 | 3027 | 77% | 720fps，**busy 100%** | 1601fps（活动率 ~1990） |
| av1 | 2679 | 1292 / 1762 | 3054 | 88% | 932fps，busy 81% | 1732fps（≈单臂，无退化） |

三个成分（按可修性）：

1. **CPU 臂银行帽太浅（h264 23% 闲置的主因）**：`queue_frames_`
   在 `ComputeBudgets` 里按**全帧**字节算出 1536 帧帽（4.8GB RAM 时代的
   界），且解码线程背压把 raw（全帧 3.1MB/帧）与 frame（滤镜后 ROI，
   KB 级/帧）**合并计价**——ROI 银行被按全帧内存错杀。对侧（GPU）值日
   期发射停顿盖不住：h264 GPU 头阻塞 1.45s，CPU 臂银行只够 ~0.5s，
   之后解码线程停转。
2. **计划份额失真（hevc 主因）**：冻结计划用的 rg 取自 EWMA 爬升期
   （基线实测 1746，活动能力 ~1990+；上一次会话同码两次运行
   1742~2221 漂 ±13%），hevc 份额偏 CPU 0.04+，GPU 臂队尾闲置
   ~2s（基线 hol g=... 队尾 + busy g 仅 52%）。直接验证（82c62e3f 上）：
   `FORCE_SHARE=0.27` → 2369→**2648（+11.8%）**、GPU 有效 1607→1924。
   另有变长 chunk 贪心量化过冲（h264 目标 ~0.75 实排 0.818，GPU 少分）。
3. **每臂混跑内干扰（本轮不修）**：CPU 臂 busy-rate 3701→~3100（h264）
   / 909→720~753（hevc），GPU 998→845 / 2118→~1990。线程档扫描
   （hevc/h264 × {24,28,32}T，82c62e3f 上）证明 **32T 仍最优**
   （hevc 32/28/24 = 2369/2302/2189）——非简单过订阅，是 SMT/LLC 级
   排挤，留作残余。

## 1. 修复（fork `4cebeef`，两处）

### 1a. ROI 银行解耦（`SetRoi` out_cuda_ 分支 + FFMPEGThreadedDecoder）

- `queue_frames_` 按 ROI 帧字节重算（帽 96..4096；4096×3.4KB≈14MB）。
- 新增 `SetRawQueueFrames(n)`：解码线程背压只看 raw 队列，按**全帧字节
  预算**（768MB → 1080p 246 帧）独立封顶；frame 队列仍由
  `max_queue_frames_` 约束。raw 全帧内存风险由 raw 帽独立承担，
  ROI 银行不再被合并计价错杀。**默认 0 = 旧行为，仅 hybrid 调用**
  ——cpu/gpu 后端路径零变化。

### 1b. 计划滑动视界（`DECORD_HYBRID_PLAN_HORIZON`，默认 4096 帧，0=关）

- `BuildPlan` 只规划 [k0, plan_end_k_)；demux 路由到视界末时
  `ChooseSide` 以**当时实测速率**重建（累计分账 `assigned_frames_`
  保留，全局 water-filling 配比不失衡）。rg 爬升噪声与贪心过冲的
  影响都被限制在一个视界内。
- `NeedsPackets` 窗口同缩（min(旧公式, 视界+3072)）：否则 demux 深预售
  （旧窗口 ~17k 帧 ≈ 全片 71%）会让所有重建发生在速率收敛前，等于
  没重建。
- **删除 REPLAN_PCT/GAP**（C-44 的速率漂移触发）：漂移触发被 h264
  证伪（混跑实测速率含自我争用，+1.11% 真回归）；视界重建不判漂移
  方向、只按节奏用成熟速率重排尾部，两个方向的失真都收敛。该 knob
  从未随 wheel 发布，无迁移面。
- stats 增 `horizon/rebuilds/rg_now`；盲阶段 debug 标签修正（旧打印
  把「回 GPU 直供」也标成 CPU-sample）。

## 3. 引擎级 A/B（`_probe_dll_ab.py`，A=varA2 / B=varB2，全片，inner=2）

（数字见文末附表；配对差分 + 符号多数。）

单臂带 stats 的对照（hevc 全片，修后 DLL）vs 基线（varA2）：

| | 基线 | 修后 |
|---|---|---|
| wall | ~10.7 | **10.08** |
| CPU 臂 busy 率 | ~690fps（busy 94%） | **761fps（busy 90%）** |
| hol cpu-head | ~3.0s | **1.64s** |

银行修复在引擎内同样生效（CPU 臂 busy 率 +10%——旧「busy」里混着
银行帽等待）。但引擎 wall 的改善小于 fork 口径：引擎侧 hevc 的 binding
约束是 CPU 臂 busy 率（761fps，比 fork 口径 753 略高、比单臂 909 低
16%）与生产者宿主税（consume_feed+merge_pair，工作项 0 记的 15% 引擎税）。

h264 引擎分相（修后）：wall 3.53 = calibrate 0.44 + decode 2.73 + 尾
0.36。**calibrate 0.44s 是首帧管道暖启被计入**（Otsu 校准顺序读前 N 帧，
付 hybrid 起步 + TRT 反序列化），非每帧成本；decode 2.73 vs fork 2.12
= 生产者宿主税 0.6s。OCR 相位 3.2s 已与 decode 并驾——h264 引擎侧再
提速解码的边际收益被消费端吃掉。

## 4. 残余与不做清单

- **每臂混跑干扰**（CPU busy-rate −15~17%）：SMT/LLC 级排挤，线程档
  扫描无解（32T 最优）。要再收需绑定/亲和级改造，收益上限 ~10%，
  复杂度高，**不做**（记录于此供复评）。
- **av1**：GPU 臂 ≈ 单臂速率 = 物理瓶颈；CPU 臂已 90% busy。
- **引擎生产者税**（15%）与 calibrate 暖启：工作项 0/1 已归因
  （merge 短路无收益，C-42）；h264 消费者空等 84%→43% 说明解码提速的
  余量正被逐步兑现到消费端。
- **并联和的诚实上限** ≈ 87/78/90%（hevc/h264/av1）：剩余成分=每臂
  混跑干扰（共享 SMT/LLC 的结构性代价，单臂各自跑时不存在）。

## 5. 构建陷阱（必须留档，本轮踩了两次）

**本机 ninja 对 `video_reader.cc.obj` 无头依赖记录（`#deps 0`）**：
`hybrid_threaded_decoder.h` 改**类布局**后增量构建不重编 video_reader，
留旧布局对象。后果取决于改动位置：

- 本轮 build#1（成员移位）：构造期访问崩溃（`0xFFFFFFFFFFFFFFF8`）。
- 本轮 varA#1（stash 回退后构建）：**静默行为损坏**——`NeedsPackets`/
  `SuggestPrefetchDepth` 是 .h 内联函数，旧对象按**新布局**读
  `plan_horizon_frames_` 等成员=读垃圾（窗口闸读错值，av1 busy 73%
  假象；据此产生的一轮引擎 A/B 判定作废）。
- 历史为什么没炸：6da2957 等提交的新成员都加在**类尾部**，旧对象访问
  的早段成员偏移未移位——stale 但良性。82c62e3f 经数字比对（2369/3200/2747
  vs 干净基线 2330/3185/2679，≤2%）确认为良性 stale。

**规矩**：改这两个头文件后必须 `rm` 掉 `video_reader.cc.obj`（或
touch video_reader.cc）再构建；**换 DLL 的 A/B 两臂都要全对象干净重建**
（本机 MSVC 构建非确定性，md5 异不代表行为异，反之亦然——以行为判别）。
