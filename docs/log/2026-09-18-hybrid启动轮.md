## 1. 机理定位（先量后做，_probe_hybrid_startup.py 新探针）

fork 级冷进程诊断（hevc w3000，hybrid_gpu ctx，硬窗界+TRACE 轨迹）：

| 读数 | run#0 | run#1 |
|---|---:|---:|
| wall | 1.532s | 1.876s（gpu-only 1.474s） |
| 盲派 GOP 数 | **10/13** | **13/13** |
| assigned c/g | 1200/1920 | 1680/1440 |
| 稳态份额（share_bp） | 3163 | —（速率从未双熟） |
| rg 终值 | 2168 | **13402**（爆表） |

两个机制：
1. **盲派**：demux 远快于解码（包缓存 512MB ≥ 窗口体积，一次性读至
   EOF），rc 出版要等 CPU 臂解满 4 折×16=64 帧（hevc ~85ms+启动），此间
   已关闭的 GOP 全部走 `PickFeedSide` 的 50/50 交替保守分支 → CPU 臂
   超分 ~200+ 帧 = 慢臂尾部 0.24s+。
2. **rg 爆表**：GPU 侧落地速率还是旧段式 EWMA（快升 1.3×/慢降 5%），
   冷启/排空段把"预缓冲排空速度"孤峰直接出版（13402fps → f 被压到
   6%）——CPU 侧 2026-09-12 已用 sustained 修掉的同款病；run#1 速率
   全程未双熟，13 GOP 全盲派，wall 1.88s。

## 2. 修复（decord 13d509d；全部实测/库存杠杆，无速率先验）

1. **PumpFeed 熟前挂起**：rc/rg 任一未出版 → 未分配 GOP 挂起（留在包
   缓存，零成本——包缓存即为此设计）；配套：flush 抑制（挂起未派完≠
   流结束）+ **Pop 空取路径重驱泵**（EOF 后 Push 停驱的唯一驱动源；
   Pop/Push/PumpFeed 同在消费线程，单线程不变量保持）。
2. **防饿死盲派**：某侧空转（`side_pending_==0`）时盲派给空侧——纯
   库存读数，不含速率假设；双空走 PickFeedSide（gop0 GPU 起步 / gop1
   CPU 采样语义不变，FORCE_SIDE 亦经它生效）。效果上"哪侧先饿哪侧
   拿 GOP"= 用库存读数实现了无需速率数的比例派工。
3. **rg 生产侧 sustained**：折计时从落地线程迁到 CU display 回调
   （逐帧触发，签名 +marker 标志）——落地线程排空 reorder 积压时量到
   的是 D2H 提交速度（h264 尾部假折 **689655fps**），生产侧=NVDEC
   硬件解码节奏与积压无关（与 CPU 臂 filter 线程口径对齐）；出版改
   8 折环 max(连续 4 折最小值) + 0.997/折慢降锁。

交付层事件驱动（§11.14 留档方向①）查实**早已在位**（5433bcb 已接
gpu_/cpu_ on_output + 双池 on_release → lcv_ 唤醒；wait_for(1ms) 只是
超时上限非轮询粒度）——本轮不再动。

## 9. 窗口尾收口轮（同日三段续）：ETA 派工把交叉点压到 ~w1200

**动机**：EOF 有「末段 GOP 给最少积压侧」收尾规则，窗口运行没有——
末段按供水比例可能落到慢臂，窗尾被拖满额 GOP 时间（hevc w1500/w2000
卡噪声带的主嫌疑）。

**三版实测迭代**（全部引擎 bench ab 交错+时钟门禁热轮）：

| 版本 | hevc w1500 | hevc w3000 | av1 w3000 | 判 |
|---|---|---|---|---|
| 基线（water-fill 尾） | +1.85%（4/2 噪声） | −9.94% | −19.07% | — |
| v1 least-pending | fork 级即回归 1.6-1.7s | — | — | 弃：`side_pending_` 含按序合并的等发射帧，GPU 臂存货虚高 → 尾系统性给慢 CPU 臂 |
| v2 ETA（扣 ready_） | **−3.69%**（6/6） | −12.09% | −15.03% | av1 让 4pp |
| v2.5 tail 4→2 | +2.34%（噪声，丢交叉点） | −15.03% | −20.07% | 弃：交叉目标是主诉求 |
| **v3 tail4+记账修正** | **−6.09%**（6/6） | **−14.48%**（6/6） | −16.66% | **定稿** |

v3 记账修正：已解码存货 = ready_ + cpu_ready_ + cuvid reorder 输出队列
（`DiagDepths` 第三值）；宿主包队列/parser/转换在途属**未解码**不扣
（首版误计入存货=低估 GPU 余量）。全片（window<0）规则不触发=零影响。

**定稿交叉点：~1200 帧**（w1000 +5.35% 慢 → w1500 −6.09% 快）；
轨迹：>3000（盲派+越窗时代）→ 1500~2000（启动轮）→ **~1200（本轮）**。
w1000 残余 = 盲承诺 2 GOP（gop0+gop1）占 4 GOP 窗口一半的结构地板
（禁先验约束，见 §2）。

## 10. h264 耦合损失深挖（同日四段续）：交付损失已清零，残余=固定冷税+尾暴露

**分解口径**（h264 全片 A/B 两次独立批次，跨臂 span 中位，结论一致）：

| 相位 | cpu 臂 | hybrid 臂 | 差 |
|---|---:|---:|---:|

| pipeline.calibrate | 0.059 | 0.125 | **+58~68ms** |
| decode.batch | 2.24~2.25 | 2.15~2.20 | **−26~96ms（hybrid 更快）** |
| pipeline.ocr_tail | 0.009 | 0.078 | **+69ms** |

**判读**：+6.5% 墙钟差**不是吞吐耦合**——decode 交付反而快 2~4%
（启动轮已把旧 −28% 清干净）。差额=①冷税 ~95ms（setup+calibrate：

16 核×0.12s vs cpu 11 核×0.06s=真做功非等待）②尾部暴露 69ms。

**消费侧 infer 膨胀的机制排除链**（p50 8.6→14.1ms/批，批数恒 152）：
- ❌ GPU 解码争用：`FORCE_SIDE=cpu` 关 GPU 臂，infer 仍 2.045s
  （纯 cpu 后端 1.31s）；且 hybrid decode 相位用核更少（17 vs 23）
- ❌ 批次粒度：ocr.chunks/infer.n 两臂完全相同（152/2735）
- ❌ 上载同步节奏：UPLOAD_BATCH 8→64 无差（批均恒 2.4，cpu-empty
  驱动，与 2026-09-12 消融一致）
- ✅ **排除法收敛：帧上载的执行者与粒度**——cpu 后端=生产者批量
  H2D（~152 次大批）；hybrid=上传器线程逐帧 H2D（7761 次小提交），
  与 TRT 提交同上下文错叠。另注：14.1ms≈C-47 的 trt_call 裸价
  13.9ms——即 cpu 臂的 8.6ms 是 defer 流水重叠出来的加速，hybrid
  下回到串行价（重叠被打断而非内核变慢）
- 修法方向（未实施，h264 选 cpu 不值得专项修）：上传器批量聚合
  H2D，或上载职责移交消费侧与 cpu 路径同构——真要攻 hevc w1000
  交叉时一并考虑（该处 infer 暴露同样吃掉 decode 增益的一半）

+111ms（慢 GPU 臂税在短窗不摊销）+ infer 暴露——h264 短中窗全面
劣势是结构性的，维持 C-53 选 cpu。
