# 2026-09-17 流水线分级与瓶颈定位（四级映射 + 两路径实测）

> 问题（用户）：当前项目中有几级流水线？画架构图，并分析瓶颈具体在哪一级。
> 本轮**没有改产品代码**，只做分级映射与实测复核；顺带量到一个解码线程档位
> 的线索（§6，未验证假设）。

## 1. 分级映射（代码级）

链路名义上是「解码 → 像素分段 → 代表帧 → OCR → 相似段合并」，但**并发结构
上只有 2~3 个可重叠的执行体**，所以"级"要按两个维度分开数：

| 级 | 名称 | 代码入口 | 执行体 |
|---|---|---|---|
| L1 | 解码 | `decord.VideoReader.get_batch`（唯一入口） | 宿主路径=**消费者线程**；GPU 路径=`_producer` 线程 |
| L2 | 分段（含状态机/代表帧，含 L4 回调） | `video_ocr_engine/domain/segmentation.py` 的 `SegmentStateMachine` | 宿主路径=消费者线程；GPU 路径=主线程（win3 分数由设备 kernel 给） |
| L3 | OCR（预处理 + 推理 + CTC） | `video_ocr_engine/pipeline/ocr_stage.py` 的 `OcrSession` | 会话线程 + 每引擎一条推理线程 |
| L4 | 相似段合并 | `segmentation.similar_decision`（经 `on_similar` 回调，宿主 `_segments_similar` / GPU `_simular_device`） | **不是独立级**——住在 L2 的帧回调里，同一线程 |

代表帧选择是 L2 内的一个动作（段内 `sharp` 取最大），不是独立级。

### 生产者/消费者方向按路径相反（易踩）

用 `threading.enumerate()` 在 run 中实测（本次）：

| 配置 | run 期线程 | "生产者"是谁 | 谁在做 L1 |
|---|---|---|---|
| `cpu` + `cpu`(openvino) | `MainThread`, `Thread-1 (_worker)` | **MainThread**（3.5s 跑完全片 4.5s） | MainThread |
| `nvdec` + `tensorrt` | `MainThread`, `ThreadPoolExecutor-0_0`, `Thread-4 (_worker)`, `Thread-6 (_producer)` | `_producer` 线程 | `_producer` |

即宿主路径**没有**独立的解码线程——`_frame_stream` 生成器就在 MainThread 的
`_segment_frames` 循环里拉 `get_batch`；`_producer` 这个名字只出现在 GPU 路径。
两条路径的 `pipeline.consumer` span 指的都是"执行 L1+L2 的那个线程"。

| decode-only，`num_threads=32` | 1.3661 | 2196.0 |

## 6. 消费线程缺口 0.70s 的构成（L2 的可回收面）

`pipeline.consumer` 2.1467s − 已计 span（`decode.batch` 1.3561 + `sharp_batch`
0.0794 + `luma_batch` 0.0079 + `binarize_batch` 0.0039 = 1.4473s）= **缺口 0.6994s**。

`tools/_probe_feed_cost.py`（本次，ROI 106×33，reps=300）逐项微基准：

| 每帧操作 | µs | 全片折算(s) |
|---|---:|---:|
| `prev_bin != bin` | 0.60 | 0.002 |
| `_cluster_win3`（全 0 提前返回） | 1.00 | 0.003 |
| `_cluster_win3`（有变化） | 14.10 | 0.042 |
| `similar_decision` | 0.10 | 0.000 |
| 加权（变化帧 37%） | 6.4 | **0.019** |

合成估计只解释缺口的 **3%**——因为该探针用的随机掩码不含真实字幕结构，
而引擎里 `_cluster_win3` 的实际调用数是 4088 次（2950 帧 + 1089 次合并门），
不是 2950 次。

`bench/numpy_cost_split.json` / `bench/patch_verify.json`（2026-09-15，同一 ROI）：

| 内核 | n | 引擎内实测(s) |
|---|---:|---:|
| `_cluster_win3` | 4088 | 0.2404 / 0.1822 |
| `_segments_similar` | 1089 | 0.3504 / 0.2554 |
| ├ `_text_sep_binary`（嵌套其中） | 2178 | 0.1197 / 0.0882 |
| `_np_resize`（消费者侧，属 L3） | 1090 | 0.2837 |
| **非嵌套合计** | | **0.4968（= wall 的 22.1%）** |

引擎内 `_cluster_win3` 摊到 58.7 µs/次。两处保留意见：
① 这 22.1% 是**占比**，按 C-42 判例不能直接当可回收量；
② 引擎内 µs/次远高于 §2 微基准（14.1 µs）与 §6 表内值，与同进程 10 个 FFmpeg

`np_resize` 在争用下 119.5 → 26084 µs，即 numpy 内核在本机上会被 GIL 串行化）。

`bench/producer_binding2.json` 的双侧判据（2026-09-15）：把生产者侧三个 numpy
内核做成 **5 倍冗余计算**（输出逐位不变，段数/指纹全过），wall 只 **+5.77%**
（2.2369 → 2.3661，符号 `+++`）；把消费者侧 `_resize_norm` 同样做 5 倍冗余，
wall 只 **+5.09%**。两侧都钝——与该轮 `numpy_replace_ab`（换 cv2、内核快
29~57%）只得 −1.12% 互为印证。

## 7. 未验证假设（留待复评，勿据此改档位）

`_decode_num_threads` 在 `ocr_on_gpu()==False` 且 `stride==1` 时返回
`max(8, min(12, logical // 3))` = **10**（本机 32 逻辑核）。该档位的代码注释
里记载的实测依据来自 ONNX 时代（"多核 + stride==1（OCR 受限）：逻辑核 1/3"），
而 C-48 已把 CPU OCR 换成 OpenVINO（模型级 2.1×、h264-cpu 热池 −27.96%）。

本轮量到的事实：decode-only 在 10T 是 1.5385s、在 32T 是 1.3661s，差 **0.172s**；
而引擎内 `decode.batch` 实测 1.3561s，**低于 10T 的独立测量**——两者不自洽。
可能的解释（均未验证）：档位实际未生效、`get_batch` 在引擎内的批/调用模式
与独立扫描不同、或独立扫描受桌面负载影响。

要判定"档位是否成为新的绑定"，需要的是一次**交错 A/B**
（`DECODE_THREADS=10` vs `=32`，`tools/bench.py ab`，判据 = 同轮配对差分均值 +
符号多数一致，阈值按本机 A/A |Δ|p95 0.484% 标定）。本轮未做该实验，
故不产出结论。

## 8. 测量方法本身的精度调查（同日追加）

问题（用户）：当前测量完全依赖计时，受系统负载与硬件频率波动影响大，是否有更
精确的方式。本节是**测量学**调查，不改产品代码；`tools/bench.py` 现有的
「交错 + 轮转 + 同轮配对差分 + `--aa` 标定 + 符号多数」统计框架本身是正确
的（它已经把占主要成分的公共漂移减掉了），问题出在**喂给它的单次读数**。

### 8.1 先证伪一个直觉：噪声不是"CPU 降频"

`QueryThreadCycleTime`（TSC 口径，频率不变）与墙钟的对照（15 次固定 CPU 负载）：

| 量 | CV |
|---|---:|
| wall | 8.902% |
| cycles | 8.494% |
| **cycles / wall** | **0.701%** |

`cycles/wall` 几乎恒定（corr = 0.9971）⇒ **TSC 频率是稳的**，波动来自调度/抢占
（IPC 变化），不是降频。所以"换个不受频率影响的时钟"**消不掉**这个噪声：
cycle 计数与墙钟在本机只是同一个量的两种单位。

### 8.2 噪声的真身：GPU 时钟爬坡（冷启动）

GPU 路径连跑 8 轮（全新进程首轮 → 后续）：

| 轮次 | wall | NVML `sm_clock` min |
|---|---:|---:|
| 0（冷） | 3.6342 | **345 MHz** |
| 1..7（热） | 3.092~3.099 | 2700 / 2685 |

`sm_clock` min 从 345 爬到 2700 ⇒ **首轮整个 run 有一部分跑在低时钟上**。
同协议下 A/A 噪声带：

| 协议 | mean | CV | max/min−1 |
|---|---:|---:|---:|
| 含冷跑（n=8） | 3.1634 | 6.015% | 17.54% |
| 弃前 2 轮（n=8） | 3.1055 | **0.111%** | 0.30% |

**噪声带收窄 54×**。注意本机测得的热态 CV 只有 0.11%——远小于
`tools/bench.py` 注释里记的 2.33%（那是**子进程模式 A/A**，含冷启动）。

### 8.3 2×2 隔离：冷启动惩罚 = 引擎构建 + 时钟爬坡，两者都要预热

四个全新进程，分别控制「先跑纯 GPU 负载把时钟拉起来」与「先 `warmup()`」：

| 预拉时钟 | 预建引擎 | wall | `engine_init` | sm p50 |
|---|---|---|---|---|
| 否 | 否 | 3.6114 | 0.5105 | 2700 |
| 否 | 是 | 3.1903 | 5.8e-05 | 2685 |
| 是 | 否 | 3.4724 | 0.4468 | 2685 |
| 是 | 是 | 3.2221 | 5.6e-05 | 2685 |

`extractor.warmup()` 只预热 **OCR 引擎池**（文档明说"不改变总吞吐"），
**不动 GPU 时钟**：所以 `warmup()` 之后首轮仍可能跑在低 sm_clock 上
（本矩阵第 4 行 sm_min 1890）。两者是**独立**的两个冷启动来源。

⚠️ 本矩阵是每个格子一次采样、且机器为共享桌面，**不给结论**，只给出
"两个机制都存在、需要分别预热"这一方向；要定论需按 8.5 的协议重复。

### 8.4 `time.process_time()` 的 15.625ms 量化：短相位的真实精度上限

本机实测：`time.process_time()` 的最小非零刻度 = **0.015625 s = 1/64 s**
（采样 278 万次只出现这一个增量），即 Windows 调度器时钟节拍。

后果直击 `video_ocr_engine/domain/resources.py` 的 `cores_avg`（`per_phase()`：`dcpu/dt`）——
它用两次 `process_time()` 之差除以墙钟。用**已有报告**折算每个相位的
`dcpu` 折合几个 tick：

| 报告/相位 | wall | cores_avg | dcpu | tick 数 | ±1 tick 误差 |
|---|---:|---:|---:|---:|---:|
| span_dump_h264cpu / decode | 2.1466 | 16.94 | 36.36s | 2327 | ±0.0% |
| span_dump_h264cpu / ocr | 0.0837 | 6.53 | 0.547s | 35 | ±2.9% |
| span_dump_gpu / decode | 3.0699 | 0.46 | 1.412s | 90 | ±1.1% |
| span_dump_gpu / calibrate | 0.0856 | 0.37 | 0.032s | 2 | **±49%** |
| span_dump_gpu / ocr | 0.0233 | 0.67 | 0.016s | 1 | **±100%** |

即：**GPU 路径的 `calibrate` / `ocr` 两个相位的 `cores_avg` 只有 1~2 个 tick
的分辨率**，报告里 `0.37` / `0.67` 这种两位小数是量化伪影，不是测量值。
相位越长越可靠（decode 相位 2000+ ticks 完全够用）。
本轮 §3/§4 引用 `cores_avg` 时只用了 decode 相位（0.46 / 16.94），未受影响。

替代方案已实测可用：`QueryProcessCycleTime` / `QueryThreadCycleTime`
（`kernel32`，无需管理员、无 15.6ms 量化，分辨率 = 1 cycle ≈ 0.4ns）。
注意其语义**不是墙钟**：`sleep(0.5)` 时 cycle 增量为 0（只计 CPU 实际执行），
多线程时是**各线程之和**（4 线程忙 0.5s → 折算 2.44 GHz×s）。对
`cores_avg` 这类"占了多少 CPU"的问题它恰好比 `process_time()` 更合适
（既有更高分辨率，又天然是"CPU 时间"语义）。

### 8.5 硬件侧可用的更精确手段（本机可行性已核）

| 手段 | 本机状态 | 价值 |
|---|---|---|
| NVML `sm_clock` / `throttle.ticks_throttled` | **可用**（`resources.NvmlSampler` 已接入，full 档） | 直接判定"这一轮是否跑在低时钟"，把不可比读数剔除而不是平均掉 |
| `nvidia-smi -lgc`（锁频） | **不可用**：`does not have permission`（需管理员） | 锁频是最彻底的消除手段，但本机权限不足 |
| CUDA event（`cudaEventElapsedTime`） | 可用（`video_ocr_engine/ocr/trt.py` 已在用） | 分辨率 ~0.5µs；但实测 CV 5.07% vs 同段 host 墙钟 2.36%，**单次并不更稳**——适合测 GPU 内子相位，不适合替代端到端 |
| `time.process_time()` | 可用但 **15.6ms 量化** | 仅长相位可用 |
| TSC cycle 计数 | 可用 | 高分辨率 CPU 时间；但**不消除**本机的主要噪声（见 8.1） |
| 进程/线程优先级 | **可用**：`SetPriorityClass(ABOVE_NORMAL)` 与 `SetThreadPriority(ABOVE_NORMAL)` 均返回 True（无需管理员） | 降低被抢占概率；`ocr_stage._bump_priority()` 已在 worker 上用同款手法 |

> ⚠️ 优先级实验的注意事项：ctypes 调用 `GetCurrentThread` / `GetCurrentProcess`
> 必须先设 `restype = wintypes.HANDLE`，否则 64 位伪句柄被截断成 32 位、
> 调用静默失败（本轮第一次尝试即因此得到假的 `False`）。

### 8.6 结论方向

按性价比排序，**先改协议，再改时钟，最后才考虑锁频**：

1. **协议层（零成本、收益最大）**：单次读数前丢弃冷轮（8.2 实测 54×）；
   A/B 两臂各自预热到同一 `sm_clock` 再配对。
2. **判据层**：把 NVML `sm_clock` min/p50 与 `throttle` 位**登记进每一轮读数**，
   对"时钟未起"的轮次直接判无效，而不是让它进入中位数。
3. **仪器层**：短相位（<0.5s）的 CPU 占用改用 cycle 计数；CUDA 子相位用
   CUDA event；`process_time()` 只用于长相位。
4. **环境层**：锁频需管理员，本机不可用；退而求其次是用优先级类降低抢占。

## 复评触发

换 CPU/核数格局；OCR 侧再提速（C-48 已改变 L3 的相对位置）；GPU 解码绑定被
打破（换卡 / 出现带 ROI-first 的解码绑定）；`_decode_num_threads` 的档位依据
（ONNX 时代）被重新测量；`tools/bench.py` 的预热/时钟门禁落地后需重标 `--aa`。
