## 2. hybrid 缺口分解（hevc test6 3000 帧，TRT OCR，热轮中位）

| 量 | 值 |
|---|---|
| 纯臂速率 | nvdec 2036fps / cpu 926~1053fps → **理论和 2962** |
| hybrid 实际 | **2710fps**（decode 相位 1.11s）→ **缺口 −8.5%** |
| 臂内分率 | CPU 臂 840 帧（−25% 窗口份额）/ GPU 臂 2160（+1%） |
| in-context 速率 | CPU 臂 rc_now **914**（vs 纯 1053，−13%）；GPU 臂 1988（−2.4%） |

### 2.1 逐执行器定位表（decode 相位）

- consumer/帧 0.3M 三臂持平；duty：hybrid consumer **0.35**（未饱和，
  非合并侧天花板）、ocr 0.05、infer 0.35。
- 外来簇/帧：nvdec 0.3M(3 线程=NVDEC 后处理) / cpu **15.9M(42)**
  / hybrid 4.2M(40)。反解：hybrid 外来总量 12.6G ≈ CPU 池 720 帧×16M
  + NVDEC 后处理 2280×0.3M ✓——**CPU 解码池每帧周期成本在 hybrid 内
  不变（16M≈15.9M）**：无 SMT/CPI 计算争用税。

### 2.2 三连否证（性质判定）

1. **非计算争用**：每帧周期不变（上表）。
2. **非宿主挤压**：绑定实验——decode-only +8 自旋负载，速率 2740→2858
  （**+4.3%**，无退化）。
3. **非引擎耦合**：decode-only（`_probe_decode_rate.py`，2868-3118fps
  带宽 + 本轮 inline 复测 2562-2882）≈ in-engine（2710-2818）——
  带宽重叠，去引擎不追回缺口。

### 2.3 定位结论

**fork 供给线封顶**（demux 单线程解析+push 在双臂合计胃口 ~3089fps 下
约 ~2800 吞吐）：直接证据 = `up_cempty=1322`（CPU 臂输入空轮询 1322
次，964 包处理——饥饿直证）；GPU 臂靠快消费+深队列缓冲基本无损，
**慢臂先饿**（rc_now −13%）。water-fill 少派帧给慢臂（840:2160 ≈ 速率
比）是 makespan 最优分配，非损耗。与旧结论「三码 hybrid 稳态趋同封顶
~2200fps」同族——泵重设计（C-46）后抬到 ~2800，仍是供给单线程封顶。

**修复方向（fork 侧候选，未做）**：供给线并行化/多级缓存（pkt_cache
512MB 预算，实测峰值仅 80MB，余量充足）；或 CPU 臂输入预取深度。
