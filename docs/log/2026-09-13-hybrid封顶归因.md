# 2026-09-13 hybrid 稳态封顶归因（工作项 0）：封顶在 fork，不在引擎

## 问题
三编码 hybrid 稳态速率趋同（2214~2285 fps）说明存在**与编码无关的封顶**。判定它
落在 fork 解码路径还是引擎生产者链——这一判断决定"引擎侧优化（merge_pair 批量化）"
与"fork 侧优化（调度/重规划/交付粒度）"谁该先做。

## 方法
新增 `tools/_probe_decode_rate.py`：与引擎 GPU 管线**同参数**（ctx / `output_format
='gray'` / ROI-first / 线程档 / `DECODE_BATCH_SIZE`=16 的 `get_batch` 粒度）打开
解码器，但**不做任何 analyze / 分段 / merge / OCR**，也不消费返回数组 ⇒ 得到
"fork 上限"。每臂独立子进程、min-of-2（6000 帧）。

口径可信性自查：本探针的 `gpu` 臂 = **998 / 2118 / 1762 fps**（h264/hevc/av1），
与既有 C-04 记录的 NVDEC 能力 **982 / 2103 / 1749** 几乎逐位吻合 ⇒ 探针口径与
历史测量同源。

## 数据

| 层 | 口径 | h264 | hevc | av1 |
|---|---|---|---|---|
| **fork 上限**（只解码，6000 帧） | hybrid_gpu | **3391** | **2657** | **2706** |
| fork 单臂：gpu（NVDEC） | 6000 帧 | 998 | 2118 | 1762 |
| fork 单臂：cpu | 6000 帧 | 3701 | 909 | 1292 |
| **引擎内 hybrid**：`producer.decode_batch` | 6000 帧 / 全片 | 2593※ | 2268 / 2175 | — |
| 引擎内 hybrid：wall | 全片（23970/7761） | 2243 | 2257 | 2214 |

※ h264 的 2593 为全片口径（7761 帧）。

## 判读

1. **封顶在 fork**：引擎的 decode 相位（2268 fps @hevc，6000 帧）比 fork 上限
   （2657 fps）只低 **15%**；全片口径下引擎达到 fork 上限的 **82~85%**。
   即**引擎的分段/合并/OCR 并未成为限制因素**——它只是与解码争用，吃掉十几个点。
2. **fork 自身还有 12~28% 的调度缺口**（相对"两臂单臂速率之和"这一理想并联和）：
   h264 3391/4699 = **72%**、hevc 2657/3027 = **88%**、av1 2706/3054 = **89%**。
   这与 C-39 记录的"两臂都没跑满"（hevc GPU 臂 33% 忙、h264 两臂 41%/57%）
   是同一现象的两种观测。
3. **引擎侧另有一笔与解码无关的固定开销**：6000 帧下 wall 3.453s − decode 2.645s
   = **0.81s**（启动/校准 0.35s + 尾段 OCR 收敛），占该窗口 23%。这笔钱既不在
   fork 也不在 merge_pair，属"窗口越短占比越高"的启动类成本。

## 结论与对工作顺序的影响

- **引擎侧（工作项 1，merge_pair 批量化）的天花板 = 那 15% 的争用税**，
  不是先前按"merge_pair 占墙钟 21~27%"推算的更大值——**因为那 21~27% 是与解码
  并发的时间，不是串行叠加的时间**。这一条修正了先前的优先级直觉。
- **fork 侧（工作项 2/3/4）面对的是 12~28% 的调度缺口 + 短窗启动缺口**，
  量级与引擎侧相当或更大。
- ⇒ 原定顺序（0 → 5 → 2 → 1 → 3 → 4）**保持**，但括号里的天花板据此更新：
  2（启动，可消除短窗缺口）、3/4（调度，12~28%）、1（引擎争用税，≤15%）。

## 附：本探针首版的一个错误（已修，留档）
首版用 `len(nds)` 当批帧数，而 decord 的 `NDArray.__len__` 返回**元素总数**
（批帧数 × H × W × 通道）⇒ 速率虚高 **3456×**（报出 9.8e6 fps）。
被发现的方式正是"与手写最小复现对不上"：直接循环打印每批 `shape`，看到
`len=691200` 而 `shape[0]=200`。已改为 `int(nds.shape[0])`，并补注释。
另：批大小常量名是 `DECODE_BATCH_SIZE`（=16），首版误写成不存在的 `DECODE_BATCH`
而静默落到 200 —— 也已修。
